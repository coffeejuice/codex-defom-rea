# CP142: +0x230 property-table cells and callbacks

## Result

The retained evidence closes construction of the actual `GuiModel+0x230` manager and its initially empty Qt model, but not a later population path for its cells. It also establishes two `itemChanged -> slotItemChanged` registrations (base and derived) but does not source-close the derived slot body or any callback chain for a populated cell. There is therefore no safe populated-cell implementation cut yet; keep the current refusal.

## Owner and construction chain

- `0x140c90210` is the lazy owner accessor: if `GuiModel+0x230` is null, it allocates `0x60` bytes, calls `0x140d78100(new, model)`, stores the returned pointer at `+0x230`, and returns it. This is in `analysis/wave2-doe-stepdata-statevar-callbacks-decompile.json` (SHA-256 `fc732aea06085067cb8a061f9270d9bb3c55f51bfed53f5948c629253986b8a9`). The StepData dispatcher calls this only after child dispatch, then calls finalizer `0x140d7c260` (`analysis/wave2-doe-active-task-defaults-stepdata-decompile.json`, `analysis/wave2-doe-stepdata-successor.json`).
- `0x140d78100` calls base constructor `0x140d3d590`, installs `SfObjectManager` RTTI/vptr, stores the owning model pointer at `this+0x50`, initializes mode through `0x140d41b10(this,0)`, creates its selection model at `+0x58`, and registers another `itemChanged(QStandardItem*) -> slotItemChanged(QStandardItem*)` connection with Qt connection type `3` (`analysis/wave2-doe-stepdata-ctors-remesh-decompile.json`; bounded constructor assembly `analysis/wave2-doe-stepdata-table-constructor.asm`).
- Base constructor `0x140d3d590` calls `QStandardItemModel(QObject*)` with null parent, creates its own selection model at `+0x48`, and registers the base `SfItemModel` itemChanged slot (`analysis/wave2-doe-stepdata-table-base-constructor.asm`). The retained evidence packet `analysis/wave2-doe-stepdata-checkbox-empty-contract.json` (SHA-256 `dbf8198ef21d20104edcc9b5f04541ae92e1e03177bd4148572884c070963ad8`) records both registrations and that neither selected constructor populates rows.
- Shipped QtGui constructor `0x6552ce10` creates the model root via `0x6552b680`; the captured root has zero rows and columns. QtGui `item(row,column)` returns null for out-of-range access without growing the model (`analysis/wave2-doe-stepdata-table-qt-model-ctor.asm`, `...-private-ctor.asm`, `...-qt-model-item.asm`, and `...-tail.asm`). Thus normal `+0x230` construction itself cannot produce a checkable cell.

## What happens if a checkable cell already exists

Finalizer `0x140d7c260` updates, rather than constructs, cells. After taking the View snapshot and refreshing current object, it maps only bound, non-kind-7 Views with nonnull Settings to successive row numbers. For each such row it checks columns `1..6`; only an existing checkable `QStandardItem` receives `setCheckState` from the corresponding Settings flag. It increments the row after that View. This mapping agrees with the current eligible-View/row loop in `source/apps/moproj2mst/src/engine/viewer.cpp`.

The Qt item `setData` capture shows an attached item can notify its model when a stored role value actually changes (`analysis/wave2-doe-stepdata-table-qt-item-setdata.asm`, SHA-256 `abd162aa295255e556799afc205e3e337a9d981eed89c5832dce6a0fade5ca16`). Therefore it is not safe to equate finalizer `setCheckState` with a local flag assignment or to assume that all checkable cells are inert. A base `SfItemModel` slot body exists at `0x140d3d8c0`: it runs `0x140d41670` and calls notifier `0x1402ceae0` with the model. The derived manager has a second same-named registration, but the retained captures do not bind that receiver's actual method body or establish how it orders/effects state relative to the base slot. Both constructor captures record the raw connection-type argument as `3`; this report does not assign that enum an unverified label or claim synchronous runtime ordering.

## Exact unresolved witness

No retained source/decompile examined here links a writer of rows, `setCheckable`, or a checkable item to this exact `SfObjectManager` instance after `0x140c90210` creates it. Other nearby `QStandardItem` constructors belong to other models and are not evidence for `+0x230`. The missing edge is the **post-construction caller that installs a cell into this manager**, together with the derivation of its row from the same eligible View and the `SfObjectManager::slotItemChanged` body/any downstream receiver. A bounded next static query is to enumerate references/indirect dispatch through the `SfObjectManager` vtable at `0x142a3f748` and the stored manager pointer, then trace any discovered `setItem`/`appendRow`/`setCheckable` callsite and meta-call slot. Until that edge is found, the smallest correct implementation remains the current guarded refusal at the first populated cell.
