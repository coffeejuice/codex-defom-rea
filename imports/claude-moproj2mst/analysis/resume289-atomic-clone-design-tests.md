# CP289 creation-bound clone collector and disposable tests

The collector establishes a new directory's creation-bound Windows handle and a bounded, exact B98 copy/manifest/command receipt. It grants no permission to execute the original application. Every result retains `status=HOLD`, `original_run_ready=false` and unknown runtime loaded-module identity. This implementation lane created no real `C:\PROBLEM` clone and ran no original application, GUI, Frida or REA session. Root owns the separate single production acquisition after independent review.

## Contract and native API

`admin/color_atomic_clone_acquire.py` has no path-selection CLI. Its production entry point pins the CP214 B98 fixture, `C:\PROBLEM`, the CP280 manifest reference, the installed executable's exact argv spelling, and one output receipt. It generates one `m289_<16hex>` leaf from one `uuid.uuid4()` call. It neither checks for absence as proof of freshness nor adopts an existing path: `NtCreateFile` performs the create-new decision and returns the same directory handle used for subsequent verification and relative child creation. A collision or any other API failure stops that attempt without a new name, fallback API, overwrite, reuse or deletion.

The implementation follows Microsoft's user-mode [NtCreateFile documentation](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntcreatefile): `OBJECT_ATTRIBUTES.RootDirectory` supplies the retained parent handle and `ObjectName` is a single validated relative leaf. `FILE_CREATE` rejects an existing object. `FILE_DIRECTORY_FILE | FILE_SYNCHRONOUS_IO_NONALERT` creates directories, and `SYNCHRONIZE` is in the requested access. `OBJ_CASE_INSENSITIVE | OBJ_DONT_REPARSE` is used without inheritance, `OBJ_OPENIF`, kernel-only flags or delete-on-close. Normal create errors retain the raw signed and hexadecimal NTSTATUS, raw IOSB status, information and returned handle; they are never mislabeled as `GetLastError` values. The collector conservatively requires exact `STATUS_SUCCESS` in both status fields, `IO_STATUS_BLOCK.Information=FILE_CREATED` and a valid returned HANDLE. `STATUS_PENDING`, a success code without a handle, or `FILE_OPENED` is incomplete.

The declarations match the documented [UNICODE_STRING](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_unicode_string), [OBJECT_ATTRIBUTES](https://learn.microsoft.com/en-us/windows/win32/api/ntdef/ns-ntdef-_object_attributes) and [IO_STATUS_BLOCK](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdm/ns-wdm-_io_status_block) fields. NTSTATUS is explicitly signed 32-bit; HANDLE and IOSB Information are pointer-sized. The x64 entry gate and unit test require 16/48/16-byte structures, 8-byte pointers and the documented-alignment field offsets. The UTF-16 backing allocation, byte-counted length excluding NUL, maximum length including NUL, object attributes and IOSB remain alive across the synchronous call. Directory create options deliberately avoid combining undocumented options with `FILE_DIRECTORY_FILE`.

## Retention and copy verification

Before creation, the collector rejects reparse/symlink components, opens the existing parent with `CreateFileW(OPEN_EXISTING, FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT)`, and verifies its exact DOS final path, disk/directory attributes, volume/index/creation identity. Parent and created directory handles omit delete sharing and remain open through all copy work, source-before/clone-after/source-after manifests, CP280's complete gate, exact canonical UTF-16 argv/cwd binding and collective identities. Root and every expected subdirectory are created relative to retained directory handles with create-new semantics. These handles prevent ordinary rename/replacement of those objects during their lifetime; they do not freeze a directory's descendant namespace or guarantee exclusive access.

The SHA-pinned CP280 reference supplies exactly 33 entries including 27 files in production. Manifest paths reject absolute forms, traversal, stream colons, links/reparses, unsupported kinds and case-insensitive duplicates. Every generated fixture path and the full project path must have fewer than 100 characters. Future generated paths absent from the fixture must still be gated separately before any original execution.

Each source file opens read-only with read sharing only and exact final-path/type/size checks. Each destination file uses relative `NtCreateFile(FILE_CREATE | FILE_NON_DIRECTORY_FILE)` semantics, checks zero initial size and holds its returned write handle with read sharing only. ReadFile-to-WriteFile copying hashes source bytes, bounds total bytes to the pin, handles partial writes until completion, refuses zero/invalid write progress, and checks FlushFileBuffers. Source identity must remain exact across copy; destination object identity must remain the same and its size must match. All source and destination handles remain retained through subsequent manifests and collective comparisons. Extra entries and source directory changes are detected by manifests. The receipt does not claim to prove absence of changes between separate observations or after handles close.

Every valid handle is registered immediately after its API return, before status or metadata validation, including an unexpected handle accompanying a failed create result. A `finally` block attempts every close in reverse order. A close failure or any copy, manifest, identity or command error changes `acquisitionOutcome` to `INCOMPLETE` and preserves any partial clone untouched. A fixed output receipt is reserved with exclusive creation before the CLI acquires anything; a repeated invocation cannot overwrite it or start another clone silently. Successful acquisition is called `ACQUIRED_FRESH_CLONE_STATIC_ONLY`, while the overall status remains HOLD.

The CP288 installed-identity receipt is pinned to SHA-256 `b9260b578b177dda69e21438e8c7338c93231959a472e0ce070c4088618c3884` and must retain its static-only/unknown-runtime qualification. Its hash is carried in the clone receipt as static installed-file evidence. It establishes no runtime loader binding. The production receipt also binds the CP280 reference digest, content digest, project digest and gate source hash.

## Disposable validation

`python admin/test_color_atomic_clone_acquire.py` ran 26 tests: 25 passed, zero failures, zero errors, one explicit OS symlink test skip because this token lacks symlink privilege (`WinError 1314`). A separate passing test injects the reparse attribute into a successful real metadata response and verifies rejection/cleanup; it does not count the skipped operating-system fixture as a pass. The final receipt is `analysis/cp289-atomic-clone-tests.json` and records the collector and test source hashes.

Tests use tiny source/parent trees inside a verified TEMP child. Cleanup resolves and checks that exact child against its intended TEMP parent before recursion. Native tests cover actual creation-bound root/subdirectory/file handles, x64 ABI and UTF-16 buffers, exact final-path refusal, manifest/command correctness, all-handle lifetime at every boundary, DELETE-sharing denial, native root and nested collisions with sentinel preservation, one UUID selection, injected raw access denial/pending/wrong Information/missing HANDLE, partial-copy preservation, source changes/extra entries, extra clone entries, traversal/length rejection, short/zero writes, collective identity change and close failure. Fixed-pin mismatch and repeated receipt refusal are tested without invoking production acquisition.

The first managed-sandbox attempt could not create children in its package TEMP directory (`WinError 5`), so no native clone API was reached. The first unrestricted disposable run exposed one test-harness error (reading `call_count` from a replacement function); that harness was repaired. The final run used normal verified TEMP with escalation and passed as above. These setup/harness failures are not hidden as successful validation. Token measurements are unavailable; no speed or token-saving claim is made.

No converter C++ source or m2m ABI changed. This report and the tests establish tooling behavior on tiny disposable files. They do not establish an original B98/Open witness, loaded dependency identity, observer neutrality/failure behavior, GUI-control release, or objective completion.
