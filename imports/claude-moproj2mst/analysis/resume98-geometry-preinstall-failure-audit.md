## Query failure evidence and exact missing witness

The complete source query in w2_objarrays.cpp:506 returns0 only when its reader
argument is null. It otherwise reads actual S.u740 and directory fields into
the four outputs, compares the native version and directly sets it if needed,
then returns1. stored_version in gendb/frame.cpp:194 is a direct S+0x1b64 read;
the setter is a direct field write. There is no allocation, throw expression,
event dispatch or user callback in this closed body/callee pair.

The integrated branch already requires the actual reader nonnull under its
strong DbHandle owner and a current physically bounded receipt. Thus a normal
query-return0 or C++ callback-exception case is not generated by this admitted
path. The table's exception row is C++ source control-flow equivalence, not an
observed original failure. Invalid/concurrently replaced memory could fault;
the retained normal native range does not establish Windows SEH/unwind cleanup
or hardware-fault equivalence. Do not invent an exception/rollback policy.

The exact missing witness is a source-qualified reachable original failure
point within query0x140825440..0x140825532, with return/exception kind, which
outputs/version writes committed, and caller unwind/cleanup state. CP71 retains
normal query/loader order, not such a failure witness. A synthetic throwing
callback or corrupt live receipt would not supply it. No such experiment was
performed or is required to accept this bounded normal-path access migration.

## Owner cleanup and lifetime

The lambda captures only model/reader raw pointers, scalar index and &frame.
Its construction/destruction adds no shared owner, allocation or native cleanup.
withStep invokes it synchronously and adds no catch/RAII ownership layer.

install's by-value shared_ptr parameter performs the same metadata reference
copy/move as before. On success the model owns the parked frame independently
of the local frame; an exception destroys the local reference while retaining
that installed owner. On failure no new model owner was installed. Historical
frame->step remains outside the callback, is not dereferenced and gains no
authority from this scope.

The existing outer dbOwner shared_ptr stays alive across the query and is
released at the same branch return/unwind. The frame retains only a weak DB
owner and plain receipt observations, so it does not keep a reader/allocation
alive after return. The callback never resets GuiModel.step or invokes its
destructor; native model ownership is unchanged. Current model teardown can
destroy step before frame metadata, whose raw keys have no dereferencing
destructor. This was already the frame's behavior and CP97 adds no cleanup.

Existing low/high version, two-View/parked retry, owner/receipt/bounds and same
step endpoint checks remain meaningful for normal behavior. Endpoint identity
does not prove interval identity or exception cleanup by itself. Native-step
allocation provenance for any future resumed invocation remains unresolved;
there is still no lease, generation observer or retirement contract.
