# Session app_pal symbol dependency decision

**Recommendation: skip/defer the proposed symbol-only source change.** Registering an Unknown app_pal symbol under the actual Session runtime would be a real owner-location attachment, rather than another detached fixture helper. It would nevertheless pass no original-facing behavioral boundary: the public editor does not consume that owner, no getter/value/ref/pointer effect would run and the same private-palette refusal would remain.

This agrees with the frozen `resume87-editor300-next.md` deferral. Only this independent review report was written. No source/build/test/GUI, mutable REA or original execution changed. Deferral applies to this narrow proposal, not the overall recovery objective or a claim that editor300 is complete.

## Proposed cut and actual consumer

The considered change would call existing `observeApplicationPaletteSlot` from `ConversionSession::beginEditor300Factory`, after actual Project/Operation/GuiModel/current-model preflight, factory allocation and runtime binding, before `continueNativeBase`. It would supply this runtime's qualification and the pinned QtGui hash/RVA, leaving slot presence, palette alias and wrapper word Unknown.

That placement would correctly use the actual public Session's runtime. It would not substitute MainView or copy an external QApplicationPaletteOwnerState. Registering only the module symbol is representable without pretending the slot is null/present. The proposal is therefore not rejected for an ownership or native-state contradiction.

The missing benefit is its consumer. Current `conversion_session.cpp:242-263` binds the actual staged editor and calls its native-base prefix; it explicitly expects `EditorBaseIssue::PrivatePaletteUnavailable`. `editor_base.cpp:74-81` reads this actual widget's private-construction inputs, not `applicationPaletteOwner()`. With no selected private default palette, it returns that same issue. The new Unknown symbol would not change this condition or supply its missing value.

The real bound route in `loader_l3.cpp:666-675` invokes `beginEditor300Factory`, then retains:

```cpp
not_ported(0x6504abb0, "QtGui QWidgetPrivate palette inputs for SfPreSimControl300");
```

No subsequent UI setup, CG/page fill, thread retain, widget registration/count or operation mutation is admitted. The separate legacy no-Session fixture projection is not the original-facing path and cannot demonstrate progress of this proposed public join.

CP81's actual getter-token/partial-pointer consumer is currently the isolated `SplitViewPlaceholderCall`. It is not called by this public editor route. Merely placing its producer's symbol record into Session does not connect the selected editor to that consumer or authenticate its call/data identity. Repeating a test that the factory remains private-palette-pending would measure the new metadata location, not additional original execution.

## Native evidence supports symbol identity only

Retained QtGui getter `65016f70` loads `app_pal` at **`65016f8a`**, preferred global address `659c9690`, hence module RVA `9c9690`. Its branch tests the loaded pointer; null allocates/constructs GlobalColor2 and caches a wrapper, while nonnull proceeds to copy through `6504a8b0` at `65016fc6`. Original QtGui SHA-256 remains `c360c971d292a3c84fc59b8e38733a85a111243f1dbc44737d87b6d744725887`.

The address/hash establish the selected module symbol. They do not establish the actual loaded slot pointer, its data/word at the post-Open editor call, its native count or the history linking candidate aliases to that selected frame. Unknown is the only honest state for this proposed registration. Unknown is an epistemic guard, not an executed native null/nonnull branch or output.

The existing runtime observer (`view_manager.cpp:300-336`) would intern/reuse a diagnostic owner for that Unknown state without a native wrapper, getter read or ref event. Neither startup defaultPalette nor the class palette cache authorizes refining it. Thus the proposed source delta produces zero new native observable effects and does not remove any existing unresolved dependency.

CP82's stronger retained splitter003 qualification remains bounded: it reads the actual module slot and later shared-data counts in that process, but it does not observe the selected earlier private temporary-deref edge. Its later166/167/165 values and initial data-constructor1 cannot be moved to this editor call. A process-specific address or matching wrapper word cannot establish cross-process/candidate ownership by itself.

## Next useful original-facing increment

Resume source implementation when there is a coherent consumer and source qualification that can move the public frame to a distinct native prefix. The selected editor needs the actual same-runtime/module app_pal getter result joined to its live receiver/call and interned data. A completed qualified getter could permit one retained source token and the first private data-pointer store, with temporary deref still guarded for unknown current count. Symbol registration could then be part of that coherent change rather than a separate feature claim.

For the next atomic decision, require the current data dword at the actual `6504abc3/6504abce` edge, already including getter retain, and admit it at the real mutation sequence. Preserve pointer store → temporary deref → zero destruction guard or word0 → destination ref, then independent font/locale/thread/count guards. CP82 specifies the missing witness; this review neither acquires it nor requests a GUI session.

If a later proposal changes EditorBase to consume an Unknown registered owner and stop at that actual getter dependency, review its real caller/prefix/effect contract as a separate coordinated source cut. That is absent from the currently considered two-file symbol/test change and must not be implied by it.

For CP87, leave the tested public guard intact, release the source lane and continue independent ready work. No new same-boundary test or duplicate owner helper is recommended.
