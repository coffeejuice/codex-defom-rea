# CP274 connector callback next-leaf audit

## Decision

The completed seven-fixture connector type correction does not expose a new caller callback leaf that is ready for faithful implementation. The exact missing original witness is one real parser admission occurrence joining the caller's type-predicate callback and owner-index callbacks to the actual source/target operations and the resulting admission/link state. Keep the current bounded admission implementation and public connector claim qualified; do not infer these callback results from the controlled-function probe or test fixtures.

## Reconciliation of the completed correction

`analysis/connector-type-contract.md` defines seven fixed parser fixtures and four source-qualified representative type classes. The seven fixtures cover first-wins, rejected-first compatibility, chained occupancy, asymmetric conversion, combined types, and two self-loop admission cases. `analysis/connector-implementation-review.md` additionally records the Cycle and DoeOutput registry-flag omissions found during integration and says both entries are present in the final inspected registry. The takeover status records the type correction as implemented/regression-checked, seven regression cases, and explicitly says whole-project original parity is false.

The old review's initial-test discussion is historical: it describes five initial tests, then two missing registry initializers, and says the coordinator must bind the final candidate to its own regression receipt. It is not evidence that the final seven-fixture connector behavior was observed in an original GUI parse. The final type contract's original-function probe executed admission function `0x140074f50` for 16 controlled cases, but mocked the type predicate and owner-index callbacks. Separately, the static initializer/string evidence supports the listed class names and flags. These evidence classes support the bounded static mapping and regression result; neither supplies actual callback arguments/results in a real caller occurrence.

## Caller leaf and missing witness

The most specific candidate leaf is the type predicate at `0x140161470`, called by admission `0x140074f50` in the documented `0x14015ef80 -> 0x140161470 -> 0x140074f50` chain. Static contract evidence says the predicate is evaluated before target-input occupancy rejection. The parser loop in retained `sub0.c` creates items first and attempts sources in ascending order. This gives a candidate caller/order contract, not a live callback observation.

To admit a next leaf, one original occurrence must bind, on the same fresh original parse:

1. The source and target `DiagramItem` identities and class/type strings as passed to `0x140161470`, plus its exact return value.
2. The subsequent admission call identity and actual owner-index callback inputs/results used for source-output and target-input occupancy.
3. The original admission return and resulting `next`/`prev` identities for that pair, including any preexisting occupied endpoint state.
4. The process/image identity, module RVAs, caller/return chain, and source-attempt ordinal that join those observations into one occurrence.

Without this join, no evidence-backed callback leaf is ready to implement. In particular, the controlled callbacks in `connector-admission-original.json`, static class flags, and candidate parser tests cannot establish which callbacks the original caller actually issued or their runtime values. A fresh original project comparison remains necessary before promoting the seven-fixture matrix to caller-level or whole-project parity.
