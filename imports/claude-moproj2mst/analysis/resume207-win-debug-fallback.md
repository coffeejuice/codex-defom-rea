# CP207 owned Windows debugger fallback assessment

## Decision

A small owned debugger based on `CreateProcess(..., DEBUG_ONLY_THIS_PROCESS, ...)`, `WaitForDebugEvent`, `GetThreadContext`, and `ContinueDebugEvent` is technically feasible and avoids Frida's inline code patches. It is **not the fastest next step** for this trace. The previously reviewed two-function-boundary Frida probe has less implementation and event-loop machinery and avoids the four adjacent instruction hooks that diverged in CP206. A native debugger is a worthwhile fallback if those two function-boundary hooks also produce a CP205-divergent first exception, or if an already-installed and supported debugger interface becomes available. No debugger, target, or application was run for this assessment.

The debugger would remain an active debugger, not a passive observer. Debug events suspend target threads; `ContinueDebugEvent` resumes a reporting thread. Hardware execution breakpoints avoid modifying target code but still require changing each target thread's debug-register context and servicing single-step events. Single-step tracing is especially intrusive because it creates an exception/debug event at every instruction.

## Why it can capture the needed values

The current missing link is the return from app RVA `1d510` and, ideally, the field at the corresponding store/consumer in the same `eaf60` invocation. The current proposed Frida reduction is two function-boundary sites (`eaf60` entry and `1d510` entry/return), with an optional `a74f0` consumer entry if needed (`analysis/resume207-function-hook-plan.md`). A debugger can instead launch the exact child under debug control and set x64 hardware execution breakpoints at selected app RVAs after the module-load event reveals the current ASLR base. On a breakpoint or single-step `EXCEPTION_DEBUG_EVENT`, it can fetch the stopped event thread's x64 `CONTEXT` with `CONTEXT_CONTROL | CONTEXT_INTEGER | CONTEXT_DEBUG_REGISTERS`, read `RCX`/`RAX`/`R11`/`RSP` and use bounded `ReadProcessMemory` for `O`, `H`, and `H+38h`, then continue the debug event. It need not write executable bytes.

To observe the producer return without a function-entry inline hook, a hardware breakpoint can be placed on the selected return address `EXE+0xeb000` after validating the `1d510` caller. This is a breakpoint at the call-return continuation, not the function entry. A register-context snapshot there provides `RAX` before the subsequent `mov r11,rax` and field store. A breakpoint at the consumer continuation near `EXE+0xeb1e7` can similarly capture the loaded operand. Exact sites and caller/frame correlation must follow the existing static qualification; a generic breakpoint on every return address would be unnecessarily broad.

Hardware breakpoints are a scarce per-thread resource (x64 architectural debug address registers are limited), and the debugger must arm new threads and account for thread exit, module load/unload, recursion and concurrent callbacks. The program's initial thread can be armed before it runs, but the debugger must also process create-thread events and set breakpoints in each new thread before resuming it. This introduces setup and race surface absent from a single-thread-only assumption. A write watchpoint on `H+38h` is not a better first design: `H` is only known at runtime, it consumes a data breakpoint, reports writes from any thread, and does not alone identify the logical producer invocation.

## Minimum safe scope if selected later

1. Use a small standalone x64 debugger process that owns exactly one fresh `DEF_GUI_MO_64.exe` child. Start it with `CreateProcessW` and `DEBUG_ONLY_THIS_PROCESS`; do not attach to a pre-existing/user process and do not use `DEBUG_PROCESS` to inherit descendants. Keep the current exact image hash/version, command, cwd, fixture manifest, and process-creation identity checks from CP205.
2. Keep the debug-event loop on the thread that created the child. Handle the initial create-process/load-DLL events, record the exact main-image path and module base/size, validate image identity and target bytes, and only then arm a minimal set of hardware execution breakpoints. Do not arm every thread at guessed addresses or patch code. Track thread creation and exit, install the same bounded register capture for each target thread, and retain explicit coverage/overflow counters.
3. Begin with the CP205 exception receipt only plus one producer continuation breakpoint at `EXE+0xeb000`; add a consumer continuation only if the trace remains CP205-parity and producer/consumer pairing is still ambiguous. Keep the original CP205 first-AV tuple—QtCore RVA `0x32c0`, read address `0x58`, `RCX=0x58`, and the qualified app chain through `eb1ec` and `eaa7a`—as the hard instrumentation-parity gate. Any first-exception mismatch is divergent/inconclusive, irrespective of captured breakpoint hits.
4. For ordinary first-chance exceptions, preserve natural exception delivery using `DBG_EXCEPTION_NOT_HANDLED`; do not classify the observation breakpoint's `EXCEPTION_SINGLE_STEP` as an application fault. Capture the original AV context before continuing it as not handled. Continue non-exception debug events normally. Bound all event records and memory reads; no stack walk at each breakpoint, no dumps, no writes to target data/instructions, and no debugger prompt that can block indefinitely.
5. Preserve exact ownership and cleanup evidence. `ContinueDebugEvent` must be issued for every delivered event. A debugger exit is not a safe cleanup shortcut: Microsoft documents `DebugSetProcessKillOnExit` as a control for target behavior on debugger-thread exit, and `ContinueDebugEvent` owns closing process/thread event handles on exit events. The implementation must make its kill-on-exit policy explicit, drain or resolve any outstanding debug event, let the target's natural exit be observed, close owned handles, and independently verify process absence and unchanged fixture. Do not terminate merely to make a failed capture look complete.

This is a design boundary, not authorization to implement or run it. The current request explicitly limits this fallback to analysis.

## Key API risks and qualifications

- **First chance is control flow.** A debugger receives first-chance exception notifications before the application's handlers. Microsoft documents that `DBG_CONTINUE` marks an exception handled, while `DBG_EXCEPTION_NOT_HANDLED` resumes normal exception search; at last chance, an unhandled exception terminates the target. Therefore the debugger must distinguish its intentional single-step exceptions from the target's access violation and pass the latter through as not handled. A mistake can suppress or terminate the original fault path.
- **Debug-event serialization changes timing.** The documented debugger loop suspends target threads while a debug event is being serviced. Even a brief register/memory capture can shift races and callback timing. A debugger avoids inline instruction rewriting but does not establish observational neutrality. Preserve CP205 parity before making a causal claim.
- **Exit and child ownership are explicit.** `DEBUG_ONLY_THIS_PROCESS` limits debugging to the created target; `DEBUG_PROCESS` alone includes descendants. The debugger must continue every event, handle process/thread exit events correctly, and define what happens if its own event-loop thread exits. An owned debugger can still leave a child suspended or cause its termination if exit policy and outstanding events are mishandled.
- **x64 context is architecture-specific.** `GetThreadContext` only yields a valid context for a stopped/suspended thread, and `CONTEXT` flags and layout are processor-specific. The target is the 64-bit original; debugger and context definitions should be native x64. A WOW64 context would be wrong for this target. Avoid arbitrary `SuspendThread`/`ResumeThread` pairs while the debug event already provides a stopped-thread context.
- **TLS and invocation pairing stay per-thread.** The static path's locals include the `eaf60` frame identity and the selected event chain. Since TLS is thread-local, store invocation correlation by TID and stack/frame, not process-global order; handle recursion and thread reuse. A debugger's event loop does not automatically tell which TLS instance or logical callback occurrence a raw register belongs to. Do not inspect/modify TLS to force correlation.

## Relative speed and recommendation

The native debugger is likely slower to build, review, and qualify than the planned two-site Frida boundary probe: it needs a correct Windows debug-event state machine, process/module/thread handle ownership, x64 context extraction, hardware-breakpoint lifecycle, per-thread setup, exception classification, and a parity/cleanup receipt. It may be faster than implementing another multi-site Frida instruction-hook set if that work would repeat CP206's relocation/trampoline risk, but that is a speculative engineering comparison, not a measured timing claim. No debugger implementation or elapsed-time comparison exists.

Recommended order: preserve CP205 as the acceptance reference; first evaluate the smallest already-reviewed function-boundary Frida design with its one-run parity gate. If those hooks also diverge, stop repeating Frida variants and implement/review this owned debug-event design as the next non-inline-patch method. If the goal is immediate observation with no new tool implementation, this is not faster than continuing the current Frida route; it is the more invasive but technically cleaner fallback for code-patch-related uncertainty.

## Microsoft primary references

- [`CreateProcess` debugging flags](https://learn.microsoft.com/en-us/windows/desktop/Debug/process-functions-for-debugging): `DEBUG_PROCESS` debugs descendants; combining `DEBUG_PROCESS | DEBUG_ONLY_THIS_PROCESS` limits debugging to the created process. The creation-flags reference also defines `DEBUG_ONLY_THIS_PROCESS` and `CREATE_SUSPENDED`.
- [`WaitForDebugEvent` / debugger event-loop behavior](https://learn.microsoft.com/en-us/windows/win32/debug/writing-the-debugger-s-main-loop): target threads are suspended while the debugger services an event; the loop uses `GetThreadContext`/`ReadProcessMemory` and resumes with `ContinueDebugEvent`.
- [`GetThreadContext`](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getthreadcontext): context structure is processor-specific and valid context requires the thread to be stopped/suspended; context flags select retrieved register groups.
- [`ContinueDebugEvent`](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-continuedebugevent): semantics of `DBG_CONTINUE` versus `DBG_EXCEPTION_NOT_HANDLED`, event-thread continuation, and exit-event handle closure.
- [Debugger exception handling](https://learn.microsoft.com/en-us/windows/win32/debug/debugger-exception-handling): first- and last-chance exception delivery and consequences of handling/unhandling.
- [TLS](https://learn.microsoft.com/en-us/windows/win32/procthread/thread-local-storage): TLS slots are per-thread; [PE static TLS](https://learn.microsoft.com/en-us/windows/win32/debug/pe-format) separately describes load-time static TLS.
