# CP465 Type3 `.OPT` Save writer: ordered effects and private boundary

The original Type3 Save arm calls `FUN_140907a10(path, SUB+0x28 optimizer, DOE manager)` after saving InputTable. The writer is now byte-bound to the retained original PE. This closes visible call/write order and the returned byte, but does not supply a constructible native optimizer owner or exact Qt file bytes. Keep public Type3 Save guarded.

**Correction to the first CP465 report:** its claim that the successful-open path returns true was wrong. PE bytes show the byte at `[rsp+0x38]` initialized to zero at `0x140907a3e`, read on both the open-failure and post-close return paths, and never set nonzero in this complete function range. Both ordinary paths therefore return false. The previous successful-return conclusion and any inferred success result are invalid and superseded here. The caller still stores but ignores this false result.

## Ordered writer contract visible in the PE

1. Construct a local QFile from the supplied path and open with `WriteOnly | Text` (`QIODevice` flags `0x2 | 0x10`). If open fails, construct a diagnostic string containing the supplied path and assign it to the global QString at `0x143dd9a20`; this evidence establishes an assignment, not that a message is emitted to a user or log. The branch destroys the local QFile and path objects, then returns false. No optimizer getter is called on that branch.
2. On open success, construct a QTextStream over that QFile. The stream receives three fixed header lines, each followed by `endl`, before the first optimizer getter.
3. Emit scalar/header sections in order. The writer calls optimizer slot `+0x138`, then helper `0x14091e0b0`, emits each result, and then calls optimizer slot `+0x128`. It next processes three indexed groups for indices 0, 1 and 2: each group calls `+0x98(owner,index,collection)`; helper `0x140307410` calls `QListData::isEmpty` on that returned list data, and `+0x60(owner,firstValue)` is called only when it is nonempty, using its first value. In the helper's return convention, true means empty and skips `+0x60`; false means nonempty and reaches `+0x60`. This follows the bound helper and retained `evidence/gui_mo/s1/mdt/DB/d3.c` qualification. The writer next calls helper `0x14091e0f0`, then slot `+0x118`, then `+0x28` for the row count.
4. For each row index `i = 0..count-1`, getter order is `+0x60(i)`, `+0x50(i)`, `+0x70(i)`, `+0x40(i)`. The writer then formats and emits that row before moving to the next index. No row sorting or transaction stage is visible.
5. Next it obtains manager-owned list data through manager virtual slot `+0x1c0`; the retained decompile stores the result in a local list object and passes it to `140004ae0`, identified in the source ledger as a QList size helper. It emits that size and then emits numbers 1 through the size with a fixed literal. The visible body does not retrieve or emit the list's individual elements, so describe this as the count-and-number sequence, not as a serialization of the collection values.
6. It asks optimizer slot `+0xc0` for another row count. For a count below one it emits the empty-section line. Otherwise, for each row it calls `+0xd8(owner, buffer, i)`, applies the retained QString concatenation helpers to the returned row, and emits it in encounter order.
7. Finally it reads optimizer `+0x148` and `+0x158` in order and emits their corresponding lines/branch, emits the closing marker, closes the QFile, destroys local temporaries, and returns the byte stored in `[rsp+0x38]`. That byte was initialized to zero and is never set otherwise in this function, so the normal post-close path returns false too. The visible code does not query QFile error after close or test QTextStream status.

These are call and stream-insertion effects, not a promise that every insertion has reached the physical file immediately: QTextStream buffering, `endl` flushing, codec conversion, QFile Text translation, short writes and close-time errors depend on Qt/device behavior not independently closed here. The writer's PE unwind metadata has `UNW_FLAG_UHANDLER` (flags 2; handler VA `0x14146e20c`); that handler and any cleanup it performs are not traced in this checkpoint. No explicit rollback or stream-status branch is visible in the ordinary function body. A later getter/formatting nonreturn or fault follows an opened WriteOnly|Text file and prior stream operations; unwind cleanup and the surviving physical byte prefix are outside the established contract. Both ordinary returned paths—open failure and the post-close path—return false.

## Caller continuation and smallest private increment

At the Type3 arm, both SUB `+0x28` optimizer and SUB `+0x20` manager must be nonnull to enter the study/output sequence. The caller computes the `.OPT` path from the SUB path, project complete base name, separator and `.OPT`; it saves InputTable first, then invokes `0x140907a10`. It stores the returned byte but does not branch on it. Since the writer returns false on both visible ordinary paths, the caller continues to common Subproject_DbName output and the later project DOM path after either open failure or normal close. These effects happen after earlier public Save work and before the parent replaces the Sub_Project DOM node and serializes the `.moproj` document. Preserve that order and partial state; do not convert false into rollback or an abort.

The smallest defensible private implementation increment is a **prepared ordered output-attempt planner**, explicitly detached from `SubProject` and public Save. Supply an explicit path and already-rendered fragments in native getter/row order; record open, each attempted insertion, close, and the native false return on both ordinary paths. Do not stop later insertions or change the returned byte merely because an abstract sink reports an ordinary write error: this function makes no visible QTextStream/QFile status check. Once opened, a nonreturning getter, fault, or exception can prevent later attempts; UHANDLER cleanup/result behavior is not established here. A caller model must separately continue after the writer's false result. This establishes ordered orchestration without inventing a `DefOptModel`, its getter values, or Qt bytes.

Do not yet implement an asserted native byte serializer or attach the private parser state to `SUB+0x28`. Exact output parity still needs: concrete `DefOptModel` slot-to-field contracts for every slot used above, ordered collection/string values; QString/QTextStream numeric and codec formatting; and QFile Text/write/close failure behavior (including when insertions become physical bytes). The actual native owner constructor/lifetime and supported Open-to-Save state are separate gates already identified by CP449/145. Existing parser qualifications in CP143 also prohibit treating the current file parser's admitted byte profile as general native input support.

## Reproducibility and limits

Run `python analysis/cp465-type3-opt-save-verify.py` to reproduce the disassembly and byte comparison. It also checks that the complete writer range contains exactly one zero store and two loads of `[rsp+0x38]`, with no other reference to that return slot. It writes only the new CP465 assembly and verification receipt. The immutable PE and bounded native exports establish the static normal branch and call order; they do not establish runtime file contents, a successful Save occurrence, error injection behavior in Qt, or the `SUB+0x28` owner's liveness. No application-control session was acquired.
