# CP207 function-boundary probe redesign

## Purpose and evidence boundary

The next probe should first preserve the CP205 fault path, then ask whether the `1d510` call in that same `eaf60` invocation returned a null owner. The smallest useful layout has **two function-entry Interceptor sites**: `eaf60` to identify `O` and the invocation, and `1d510` with `onLeave` to capture its returned `P`. A third, separately gated entry at `a74f0` can record the `P` actually consumed by the selected loop. This is a plan, not approval to run or edit the observer. No executable, fixture, source, REA database, or process was changed for this report.

The pinned original `DEF_GUI_MO_64.exe` belongs to the v11.0.2 installation; SHA-256 is `fd8ae1f8dd50d068267b3b7e49efdf11eaa178889131e59ec4b6f8de64725acc`. Its PE version resource was reported null in CP202, so the installation version is not a version-resource reading. CP205's qualified, no-Interceptor run on `C:\PROBLEM\p202a\Gear_blank.moproj` captured a QtCore `QListData::size` read AV at `0x58`, `RCX=0x58`, with app returns `a7510 -> eb1ec -> eaa7a` in the same stack. The copied-code chain means `P=0` at that selected `a74f0` call. CP206's four mid-instruction hooks instead registered before resume and saw zero visits before a first AV executing unmapped `0x7ff632e30008`; the child naturally exited `0xC0000005`. This is path divergence, not evidence that the producer returned zero or that a particular Frida hook caused the fault. CP202 earlier installed six hooks and observed dock/visibility/slot events before a QtCore `0x32c0` fault, but its cleanup and coverage were incomplete. That occurrence shows Interceptor callbacks can arrive in this original; it does not validate these proposed sites or establish instrumentation neutrality.

## Proposed sites and observations

All coordinates are EXE RVAs added to the **current loaded module base** after exact path, image-size, file hash, and unpatched prefix checks. Never reuse a prior run's ASLR base. The following entry instructions were checked in the SHA-matched copied PE using bounded DUMPBIN 14.44.35228.0 views; they are static, not live interceptability tests.

| Stage | Function entry and first instructions | Record and caller restriction |
|---|---|---|
| 1 | `eaf60`: `48 89 4c 24 08` (`mov [rsp+8],rcx`), `53` (`push rbx`), `48 81 ec 60 01 00 00` (`sub rsp,160h`) | `onEnter`: save raw `RCX=O`, TID, incoming return address, entry RSP, invocation ID, sequence. Keep a per-thread invocation stack; `onLeave` only retires it if it actually returns. Prefer the selected caller return EXE+`eaa7a` (`eaa75` calls `eaf60`). Do not treat a stale stack entry after an AV as a completed invocation. |
| 2 | `1d510`: `48 89 4c 24 08`, `48 83 ec 28`, `48 8b 4c 24 30` | On entry, require incoming return address EXE+`eb000` (`eaffb` calls `1d510`) and one unambiguous active `eaf60` invocation on the same TID. Save that invocation ID, `O`, and input `RCX` for the paired `onLeave`. On normal `onLeave`, record raw `retval` as `P_producer`, plus guarded contemporaneous `[O+30h]=H` and `[H+38h]` with explicit read status. The field read is **pre-store context**, not proof that `eb00f` committed. No return record exists if the callee faults or does not return. |
| Optional 3 | `a74f0`: `89 54 24 10`, `48 89 4c 24 08`, `48 83 ec 38` | `onEnter` only when incoming return address is EXE+`eb1ec` (`eb1e7` calls `a74f0`) and an unambiguous `eaf60` invocation is active on that TID. Record raw `RCX=P_consumed`, `EDX` loop index, invocation ID, `O`, guarded current `H=[O+30h]`, and guarded `[H+38h]`. `RCX` is the call operand; the field reread is diagnostic and may race. This site is a later escalation if the two-hook run preserves the CP205 path. |

The two entry callbacks correlate by process creation FILETIME text, PID, TID, nested invocation ID, sequence, and the exact `eb000` caller return. An entry RSP is useful for disambiguation but is not the post-prologue `S` of CP206; do not compare those two stack values directly. The optional third callback uses the exact `eb1ec` caller return and the same active invocation, so other callers of `a74f0` cannot be silently merged. Keep raw pointers and failed-read states; never substitute an unreadable pointer with zero. Emit bounded scalar records and overflow counters, with no target-side API calls, stack walks on every hook, memory dumps, register writes, or exception suppression.

With two hooks, a qualified CP205-style AV plus a paired `1d510` return of zero supports “this producer returned zero before the selected null consumption.” A nonzero return followed by the same null consumption narrows the change to **after the return**, but without a committed-store observation it cannot prove a later field clear. With the optional `a74f0` entry, matching `O,H` and `P_consumed=0` ties the selected call operand to the producer record; differing `H`, failed reads, reuse, recursion ambiguity, missing events, or possible concurrent mutation leave the cause indeterminate. Neither layout identifies a specific writer or establishes object lifetime. A normal-return producer record alone does not prove that the subsequent store at `eb00f` executed; reaching the selected `a74f0` through the qualified same-frame path and static `eaf60` flow strengthens that inference, but no claim of exact store value should be made without a direct store witness.

## Relocation and path-risk assessment

These entry sites avoid CP206's two adjacent hooks (`eb00f`/`eb013`, four bytes apart) and the `eb1e7` relative CALL. The two-hook first stage also avoids instrumenting the consumed-call body. At `eaf60`, the first 13 bytes are ordinary MOV/PUSH/SUB; for a 14-byte overwrite the next 12-byte immediate MOV must be relocated too, reaching 25 complete bytes before the RIP-relative LEA at `eaf79`. At `1d510`, the first 14 bytes are MOV/SUB/MOV with no relative operand; the first relative CALL begins at `1d51e`. At `a74f0`, the first 13 bytes are MOV/MOV/SUB; a longer overwrite includes the nine-byte immediate MOV before the CALL at `a750b`. These windows are **risk comparisons**, not a claim about Frida's actual patch width or trampoline behavior. Even prologue hooks rewrite code, perturb timing, can interact with unwind/branch targets, and can create a different fault path. CP206's unmapped execute AV must remain unresolved unless a later trace supplies a causal mechanism.

Use a staged execution decision rather than adding all three at once: first review and harmlessly fixture-test the new callback/caller-filter semantics and code prefixes; then, only under a separately reviewed owned-original run, install the two entry hooks before the single resume. The `onLeave` belongs to `1d510`'s **function**, not to the call instruction at `eaffb`; Frida's saved return address must be qualified at `onEnter`. If the two-hook run yields a CP205-style first AV but the producer/consumer link remains ambiguous, separately review the third site before another run. A one-run hook-ready receipt cannot establish that any site executed or that its callback delivery was complete.

## Explicit stops and acceptance

Before resume, stop on any mismatch in original file/module identity, creation identity, command/cwd/fixture manifest, entry bytes, hook installation, handler readiness, or ownership. Terminate only the held suspended child through the existing exact-handle helper and retain cleanup and independent absence receipts. Do not fall back to a nearby instruction or reduce required checks after an install failure.

At the first AV, send one compact core message **before** backtrace work, containing fault RIP, module/RVA if mapped, access operation/address, `RCX`, sequence, per-site counts/overflow, and creation identity; retain the full accurate stack as separately qualified enrichment. Return `false` so the exception follows its natural path. If the core or stack is lost, or any message/callback error, cap overflow, premature detach, incomplete cleanup, or fixture change occurs, classify the run incomplete. Preserve natural exit and exact handle/Windows/Frida absence independently of causal classification.

Stop causal analysis after one first AV if it is an unmapped execute fault, differs from QtCore RVA `32c0` read at `0x58`, or lacks the app chain through `eb1ec` and `eaa7a`. Such a run is a probe-path divergence, even if producer events were logged. If the CP205-style AV recurs, pair only same-creation, same-thread, same-invocation records with qualified caller returns. Zero hook counts at a different first AV cannot be treated as a negative producer observation. Repeating CP206's four-hook arrangement or changing the converter from either incomplete probe is unsupported.
