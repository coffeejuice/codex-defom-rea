# CP202 original probe attempt 2: cleanup error diagnosis

Scope: read-only diagnosis of PID 20712's cleanup receipts and the owned-process helper. No process was launched, no GUI/app-control input was used, and the helper was not edited.

## Evidence

The retained run is `analysis/resume202-passive-oracle-run-2026-10-26T04-45-03-155Z/`. The helper created PID 20712 suspended and resumed its primary thread once. Its last successful process-state receipt says `state: "running"`, `wait_result: 258` (`WAIT_TIMEOUT`), `exit_code: 259` (`STILL_ACTIVE`). At cleanup the helper received `terminate_command`, then emitted `cleanup_error` with `PermissionError(13, 'Access is denied.', None, 5)` and `exit_verified: false`; it emitted neither a successful cleanup receipt nor a held-handle wait/close receipt. The helper exited with code 1.

The runner records `sessionDetachedReason: "process-terminated"` and `sessionCleanupSettled: true` on the `already_detached` basis. The contemporaneous same-device query at 04:45:08.719 matched PID 20712, so the runner set `fridaAbsent: false`; the saved `present: {}` is the matched Frida process object serialized with no enumerable properties. It does not expose the object's fields, but it is not a “not found” receipt. At 04:45:08.982, the Windows inspection returned a successful schema result with `present: false` and an empty process list. Thus Windows absence is established at that later time; runner-level same-device absence is not. Any later independent Windows/REA absence observation should be retained as a separate, later observation, not retroactively substituted for these runner values.

The recorded Windows Event 1000/1001 evidence supplied for this diagnosis identifies PID 20712 faulting in `QtCore4_64.dll`, offset `0x32c0`, at 04:45:05 UTC. This establishes an application crash during the run, before the helper cleanup error. The Frida detach reason and later Windows absence are consistent with the crash ending the target, but do not establish precisely when the process object became signaled relative to `TerminateProcess`.

## What the code establishes

`owned_suspended_process.py` retains the `hProcess` returned directly by `CreateProcessW`; it does not reopen PID 20712. Its `terminate()` first calls `status()`, then `TerminateProcess(hProcess, 0xE201)`. On API failure it immediately calls `status()` again and raises the Win32 exception only if that second check still reports not-exited. The helper's `finally` then attempts `child.close()`, which repeats termination and closes both retained handles in its own `finally` block. The JSONL contains no intermediate status or per-call `GetLastError` timing, so the recorded exception alone does not identify which cleanup call failed.

The source does not use a Job Object. The evidence supports an unhandled QtCore crash, not a job-induced termination. The retained `CreateProcessW` process handle is not an `OpenProcess` handle whose rights depend on a later PID lookup. A simple missing-rights explanation is therefore not supported by this code or receipts, although the receipts do not independently audit the handle's granted access mask.

## Diagnosis and limits

The strongest causal account is a crash/termination race: Windows records the target fault at 04:45:05; roughly three seconds later Frida reports process termination; then the helper's termination call receives `ERROR_ACCESS_DENIED`, and Windows reports no PID about 263 ms after the same-device query. This ordering makes target termination already underway or occurring during cleanup plausible. It does **not** prove that the target had fully exited before the failing API call. The helper's immediate post-failure `status()` apparently still found it unsignaled (otherwise the code would have accepted the race and continued), so a narrow interval in which termination was underway but the process handle was not yet signaled is consistent with the code path. A persistent handle-rights/API problem cannot be excluded because the helper did not record the individual calls and waits.

The receipts do not establish a helper crash: helper exit code 1 follows the emitted cleanup error, and the Python `finally` path explicitly returns failure on cleanup exception. Nor do they establish that the target was alive after the error: successful Windows PID absence followed within 263 ms, while exact held-handle exit was never verified. Consequently this attempt fails the held-handle cleanup gate and cannot claim verified cleanup, even though later OS absence was observed. The observed crash also makes the capture incomplete; the successful pre-resume hook readiness and runtime messages do not convert it to a completed trace.

## Smallest safe next step

Do not repeat this original run to investigate the helper. First use a disposable, harmless owned child to exercise the cleanup race under a controlled natural-exit schedule, with a test wrapper that records each `WaitForSingleObject`, `TerminateProcess` result/`GetLastError`, immediate post-failure wait, and final held-handle state. Keep this as a helper-only Windows lifecycle test; do not use an original executable or GUI. If the reproduction shows `TerminateProcess` returning error 5 while a short bounded wait subsequently reaches `WAIT_OBJECT_0`, minimally change cleanup to preserve the failed API attempt and classify the successful wait as an exit-during-termination race. If the bounded wait remains `WAIT_TIMEOUT`, retain failure and investigate the handle call path rather than converting later PID absence into held-handle proof. Separately, serialize same-device matches as explicit scalar fields such as `{pid, name}` so `{}` cannot obscure that the enumeration matched a PID.
