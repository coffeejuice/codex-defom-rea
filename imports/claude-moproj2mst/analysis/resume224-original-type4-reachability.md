## Observed retained native call/order

The controlling retained source qualification is `source/docs/re/moproj2mst/s1-01/spec.md:3`: Ghidra decompiles of the original x64 binary, static-only, with image base `0x140000000`. The imported decompiles are historical analysis snapshots, not newly returned Ghidra Evidence. 1. Original constructor `0x140089880` writes `P+0x50=0` and appends `0x1400b5470(new SUB,P,0,0)` to `P+0x58` (`dc/open4.c:590–604`). The SUB constructor writes its Type argument to `SUB+0x18` (`dc/open1.c:262` onward). Thus the fresh main record is Type 0 independently of the first XML Sub_Project's attributes.
2. `.moproj` `OpenProject 0x14008a9b0` calls `ReadProjectFile 0x14008afa0`; the latter calls `WalkProject 0x14008b410` after successful DOM parsing. CP215's retained assembly fixes the walk call at `0x14008b27e` and the Open reader call at `0x14008ae0c`.

An Operation_List calls `0x14008cb50(P,element)` during that same traversal (`dc/open0.c:476`). Only after the traversal's node-null exit does the function construct and append SUB indices 1 through n-1, then call `0x14008f200` on unloaded non-main SUBs (`dc/open0.c:387–409`). Earlier textual placement of a Type4 XML element therefore does not construct or activate its SUB before a later Operation_List.
4. `0x14008cb50` calls `0x14008ccf0` for each Operation (`dc/open1.c:43`). In its Type arm, `0x14008ccf0` replaces only ID zero with the document ordinal and calls factory `0x140046cc0` (`dc/open2.c:350` onward). ## Candidate reconciliation and limits

Candidate `walkProject` in `src/moproj/read.cpp` matches the relevant retained construction order; `initProject` in `src/model/project.cpp` sets activeSub zero and installs the main Type0 SUB. CP223 was therefore justified in refusing a parser fixture that claimed a Type4 Open-time occurrence. CP220 remains correct about the helper's conditional branch and its path. A helper-level Type4 test is valid branch coverage, with no claim that fresh top-level Open reaches it. Preserve that distinction when reporting staged decision coverage.

There are other uses of this code. `dc/sub0.c:1500` calls `0x14008cb50` from **`0x1400aa000`**, whose caller **`0x1400a9be0`** reads a **TemplateFile** (`dc/sub0.c:1212,1652`). It is not evidence that the fresh `.moproj` top-level traversal activates Type4. Lazy activation `0x1400a7250 -> 0x1400a7b90` writes the selected index and invokes `0x14008f530` for unloaded SUBs (`dc/sub0.c:263–325,660–675`); that is a distinct later phase. This bounded review does not establish every helper caller, template behavior, cross-project/reentrant state, or absence of arbitrary callback mutation. Those possibilities must not be presented as observed reachability.

The older spec §5.3's loose wording about DoeStudies subfolders is superseded for this helper by CP220's exact assembly/Type4/DieStress qualification. It does not overturn the parser ordering.

The smallest next action is to retain the parser coverage distinction in the checkpoint report: the Type4 helper branch exists, while fresh top-level Open does not obtain Type4 state from this XML traversal. A fresh native caller proof remains blocked by the exact Ghidra startup timeout above; changing REA's startup configuration or importing a qualified compatible snapshot would be a separate follow-up, not an accomplished repair. Before proposing any Type4 parser integration test, identify a retained original caller that reaches the helper after selecting a Type4 SUB within the authorized lifecycle; a synthetic helper call, post-Open mutation, or Type4 XML attribute alone does not establish that route. No implementation change is justified by this review.
