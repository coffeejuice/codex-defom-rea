# CP424 held-channel WORKER snapshot repair

CP423's `cp333_worker_wait_unavailable` was caused by CP328's required hold transition clearing its public pipe receipt before CP333's deadline handler. CP332's failure-only worker snapshot called the normal `_custody()` check, which rejected that cleared receipt before reaching its exact zero-time wait. CP424 adds a keyword-only `allow_held_channel` mode to `_custody()`. Its default remains false for all normal budget, ACK, success and cleanup paths. The sole opt-in is `diagnostic_worker_wait()`; it permits the original channel receipt or exactly `held is True` with a cleared public receipt, while retaining the frozen exports, owner identities, nonce, offer/frame, four endpoint handles and exact duplicate WORKER handle checks. A foreign receipt, a cleared receipt without hold, or changed frozen endpoint remains unavailable. No process is opened by PID.

The diagnostic still calls `WaitForSingleObject` on the retained exact WORKER handle once with timeout zero only after ACK and only for a failure snapshot. It never authorizes success, changes process state or releases ownership. An `active` result is a momentary process state; `signaled` needs timing qualification against concurrent containment. The unchanged primary deadline exception and cleanup remain authoritative.

Independent current-source review found no acceptance/custody regression. Root addressed its foreign-receipt and frozen-endpoint test gaps. The final injected suite passed 652 CP3xx tests and eight CP4xx tests from both supported roots using `-B`; raw output is `cp424-final-injected-tests.log`. `git diff --check` passed. Reviewer Git diff access was unavailable, so root inspected the exact patch.

CP425 is the successor: freeze/push this candidate, independently gate one fresh monitored inert occurrence, then correlate the WORKER wait status with the runner's existing ACK budget and exact cleanup. Do not replay CP423 or relax the original five-second deadline.
