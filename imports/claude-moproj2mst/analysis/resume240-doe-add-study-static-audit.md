# CP240 DOE Add Study static call-chain audit

## Result

The retained original code identifies a concrete Type 2 Add Study creation path that CP215 does not cover. The QAction setup connects `triggered()` to `slotActionProjectAddDoe()`. A Type 2 wrapper calls a guarded add routine, whose successful branch calls the GUI-specific subproject creator. That creator changes the project's current subproject index, appends a new SUB, and requests an initial `SfOprDoeOutput` operation. This is a source fact about the possible path, not a fresh B120 execution or proof of the subsequent sample/file effects. No production edit is justified yet: the current public converter has no Add Study action or selection argument, and the exact live branch/return and sample producer remain unobserved.

## Original call and effects

All addresses below are VAs in the retained `DEF_GUI_MO_64.exe`, SHA-256 `fd8ae1f8dd50d068267b3b7e49efdf11eaa178889131e59ec4b6f8de64725acc` (rehash in this audit). The `tools/doe_static_pe.py` offline string/reference scan supplied candidate sites; bounded DUMPBIN disassembly confirmed the instructions. A reference or Qt connection does not itself prove delivery in the B120 occurrence.

1. At `0x140005B51` and `0x140005B7D`, the action setup routine `0x140005B10` references `Add new DOE Study` and `Add DOE Study`. At `0x1400068A5–0x1400068C7`, it passes sender `[this+0x30]`, signal `2triggered()` (`0x1420F2800`), receiver `this`, and slot `1slotActionProjectAddDoe()` (`0x1420F27E0`) to the imported Qt connection call. The string offsets are `0x20F0D10`, `0x20F0D28`, and `0x20F0FE0` respectively. The exact action object construction and success of the connection are not established by this bounded slice.
2. The meta-call dispatch window `0x1400D8593–0x1400D859D` calls `0x140008920`. That wrapper loads the project pointer from `[this+0x10]`, sets `edx=2` at `0x140008929`, and calls `0x14002AB20` at `0x140008937`. The slot-to-meta-call index is strongly indicated by the connection string and adjacent dispatcher cases, but was not independently observed at runtime.
3. The add routine `0x14002AB20` first checks a global guard (`0x14002AB50–0x14002AB6D`), obtains a project (`0x14002AB72–0x14002AB92`), and tests type 2/3/4 (`0x14002ABAA–0x14002ABCC`). Another decision stores a boolean at `[rsp+0x70]`; if false it takes the message-dialog branch at `0x14002AE2B`, while true reaches `0x14002AF2E`. On that true branch, `0x14002AF43` reloads the caller's type, `0x14002AF4A` reloads the project, and `0x14002AF4F` calls `0x1400A6A00`. Therefore a click alone cannot be equated to creation. The precise predicate behind `[rsp+0x70]` and its B120 value still need a fresh witness.
4. The retained Ghidra decompile of `0x1400A6A00(P,type)` shows the first concrete creation side effects. It performs existing-project housekeeping (`0x1400A7AC0`, `0x1400A83A0`), sets `P+0x50` to the pre-append subproject count returned by `0x1400A7360`, obtains an id via `0x1400A7860`, and chooses `DOE Study <id>` only for type 2. It creates/appends a `Sub_Project` DOM element through `0x140099040` and `QDomNode::appendChild`; for type 2 it constructs a SUB with `0x1400B5680` (the GUI variant sharing the main model), marks `SUB+8=1`, appends it to the list at `P+0x58`, calls `0x1400A7B90(P,P+0x50)`, then calls `0x1400A63C0(P,SUB,"SfOprDoeOutput",1)`. The latter call requests an initial DOE Output operation; its full downstream effects and return are outside this decompile. The creator contains no direct sample-generation call in the retained body.
5. After the creator returns, `0x14002AF54` calls `0x1400A73C0` on the same project. `0x14002AF9E` later calls `0x14002A9B0` with UI selection arguments. These are concrete downstream calls, but the retained slices do not establish that either generated the 100 saved empty rows. Prior source qualification in `evidence/gui_mo/s1/s1-01/spec.md` §8.2 describes `0x1400A7250 -> 0x1400A7B90 -> 0x14008F530` activation; it does not equate `0x14002A9B0` with this specific B120 result.

The smallest new fact is thus the **type-2 success-branch call to GUI SUB creation with immediate current-index assignment and initial DOE Output request**. `P+0x50` receives the old count as the new index before the SUB append. That supports a future exact test seam for an explicit Add Study operation, once the triggering branch, id source, ordering, and live effects are bound to one occurrence. It does not authorize injecting a Type 2 record into ordinary Open or Save.

## Candidate comparison and limit

Current `src/core/convert.cpp:249` activates index 0 after Open. `src/model/subproject.cpp:290–309` constructs a SUB and DOE Study from an **existing** Type 2 record; `activateSubProject` at line 345 parses an existing selected record. `src/doe/doe_study.cpp:138–148` assigns `DoeStudy<id>` and attempts directories for that owned record. These seams do not implement the GUI-only DOM append, shared-model SUB creation, current-index mutation, or initial `SfOprDoeOutput` request identified above. CP215's reader-I/O identity check applies later to an existing Study's lazy read.

The B120 before project (27,053 bytes; SHA-256 `e5b529b6440ebd55bfbb701da26beae94a67c883f35c4c177a9a80caf530e523`) has no Study. The retained after project (34,774 bytes; SHA-256 `60addc2722e85f92a088fa07f77e8a966928ab5b934f161df87dcf6a417ed30e`) has Type 2 Id 1/Active 5 and seven DOE Control files. Those hashes are from `analysis/resume203-b120-doe-state-static.md`, not reattribution of the files to a particular call. The source path above is compatible with an added study, but static control flow does not establish B120's actual click, branch result, generated sample rows, Save ordering, or which call wrote each file.
