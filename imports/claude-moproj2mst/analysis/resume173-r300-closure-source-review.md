# CP173 R300 first-cut source review

## Verdict

**Accept the four-file patch for a source-bound compile and focused tests.** Static review finds the `opStep` raw-return route removed without changing the reached `opModel` lookup order, nullable behavior, branch results, or CP163 cache boundary. It is a narrow internal C++ access migration. It does **not** close public `GuiModel::step`, preexisting aliases, whole-model reentry, or the R300 Stopping barrier. No compile or runtime parity claim is made before root's build and tests.

I reviewed the released `engine_internal.hpp`, `loader.cpp`, `loader_l2.cpp`, and `db_load.cpp` against `analysis/resume173-r300-barrier-review.md` and the owner's `analysis/resume173-r300-closure-implementation.md`. ## Compileability and behavior review

`withOpStep` has the needed `<functional>`, `<type_traits>`, and `<utility>` includes. Its constrained callback accepts only `void` or `bool` results and invokes the callback immediately with exactly `model ? model->step.get() : nullptr`. It adds no geometry check, extra model lookup, fallback allocation, or pointer return. The current call sites use valid void/bool lambdas. This is a static compileability review; the compiler has not checked all instantiations.

`inheritSimCtrl`, `loadSimCtrl`, `loadInterObject`, both MeshSettings readers, and `loadObjProperties` acquire the step at their former first statement, keep their null-false branch, and preserve all subsequent early returns inside a bool callback. `slotMaterialsFromMesh` still tests `objHasMesh` first and dereferences the obtained pointer without a null check; that existing missing-model behavior was not silently changed. `furnaceLoadPrologue` still performs base prologue and TRANS updates before the nullable step lookup, and writes `tnow3` only for a nonnull step.

`loadMaterials` retains item-ID/key-path mutation before the writer's model lookup. The native-task writer acquires the step inside its selected branch; the scratch writer acquires it inside `captureWrite`'s immediately invoked callback, after scratch path setup as before. Neither inner lambda stores the step pointer. `syncMaterialItem` still finds the item before lookup and handles null step/material without changes. `syncFromModel` still does its initial model lookup and missing-model return, then manager access, then its second model lookup. Its material, object, equipment, tail and diagram operations remain ordered inside the callback. The nested `captureWrite` is synchronous in the inspected `loader.cpp` body; no callback is retained beyond its call. `syncFromModel` continues to hold the step across nested operations, matching its previous local pointer lifetime rather than creating a new safety guarantee.

The callback result constraint prevents returning the pointer directly, but C++ cannot prevent a lambda from writing it to an external holder. No current migrated callback does that. The broader direct `GuiModel::step` and raw `simCtl`/object return surfaces remain open. The helper itself has no operation lock or lifetime pin, so the same-thread serialization and outstanding-borrow issue identified in the barrier review remains unresolved.

## Integration gate

The source owner did not touch `simcontrol300.cpp`; the reviewed four files contain no selected-length/cache1 write. CP163's after-A `CoordinateSync` refusal therefore remains the boundary for this patch. Root should compile the changed core and run the focused `m2m.mdt.loader_l2`, `m2m.mdt.db_load`, `m2m.mdt.simcontrol300_stopping_cached`, `m2m.s.save_current`, and `m2m.g0.abi` targets, checking that the changed loader/material/DB paths are actually exercised. A passing unrelated test is not evidence for the native versus scratch writer ordering or the missing-model cases. Keep source owners on hold through the source-stable suite and freeze. If compilation or a focused regression fails, revert the four files together to restore `opStep` and its callers; do not advance cache1 to work around the failure.

No build, test, GUI/app control, original execution, live REA, mutable analysis DB, or other source file was touched in this review.
