# CP265: bounded DEF_CVT3 KEY STL static contract

The imported converter establishes a small executable wrapper contract: delete an existing readable `SCRATCH.KEY`, launch a sibling `DEF_STL.EXE` through `system`, and discard its status. It does not itself parse STL or produce KEY records. The child has a configuration-file route and an interactive route; the retained fixture's guessed answers are not an established child input contract.

## Inputs and method

All paths below are relative to `imports/claude-moproj2mst`. Analysis read only `evidence/original-binaries/DEF_CVT3.com` (36,864 bytes, SHA-256 `8dd8b87c8b24cec933e98fee31946103d95cb0c09a6cb28119131aacc04652fe`) and `DEF_STL.exe` (233,472 bytes, SHA-256 `7a4d8fe41b94709ac4b0094ce9a6ccb85cf0ae2c10fdc6785085c0b961e27a9a`). Hashes were recomputed. These are original x86 PE32 console artifacts, not reconstructed application versions. No product version was established here.

Evidence is immutable PE section/import decoding with Python `struct`, plus Microsoft DUMPBIN 14.44.35228.0 `/DISASM:NOBYTES` and `/IMPORTS`. Tool path: `C:/Program Files (x86)/Microsoft Visual Studio/2022/BuildTools/VC/Tools/MSVC/14.44.35207/bin/Hostx64/x64/dumpbin.exe`. Each address below is a preferred-image virtual address, base `0x400000`; it is independently recoverable with those commands. DEF_CVT3 has equal section RVA and raw offset, so its VA maps to file offset `VA-0x400000`. DEF_STL `.text` starts at VA `0x401000`, raw offset `0x400`; its `.rdata` starts at VA `0x42e000`, raw offset `0x2c800`.

REA skill was read. Its status reported no open target and an available Ghidra provider. The supported `open_binary` schema did not expose a caller-selected database directory; the parent required database/artifact confinement to this subtree. Therefore no REA target or database was opened or changed. Neither original was executed. No GUI control was acquired. Only this report was written.

## Wrapper: proved code relationships

1. CRT startup calls the thunk `0x40105a -> 0x402af0` at `0x402ff2`. The main-like function copies `argv[0]` into a 1024-byte local buffer (`0x402af0–0x402b27`). It calls `0x402aa0`, which replaces every `/` with `\\`, then `strrchr(buffer,'\\')` (`0x402b2d–0x402b4d`). If found, it writes NUL immediately after the last separator; otherwise it sets the prefix empty. This is a textual prefix from `argv[0]`, not a `GetModuleFileName` result and not a current-directory change. Relative and bare executable names retain that ambiguity.
2. The argument loop starts at index zero and uses imported `_strcmpi` (IAT `0x407180`) for `-help`, `-h`, `/?`, `KEY`, `BPT`, `NWM` (`0x402b52–0x402be8`). Thus this parser is case-insensitive and scans arguments rather than requiring `KEY` at a fixed position. At `KEY`, the following argv pointer is fetched; if null it prints the format request and exits zero. Otherwise `0x402d60(prefix,nextArgument)` is called (`0x402bf7–0x402c32`). Extra arguments are not passed to the STL child on this branch.
3. `0x402d60` rejects null prefix/option pointers with `-1`. With nonnull pointers, it first calls thunk `0x40100a -> 0x401170` with `SCRATCH.KEY` at `0x406700`. That helper performs `fopen(path,"r")`, closes a successful stream, and returns one on successful open or zero on failed open (`0x401170–0x401197`; mode at `0x406410`). If readable, thunk `0x401069 -> 0x401250` calls imported `_unlink` (`0x402d81–0x402d9c`). Its result is ignored. This is a readability test, not an unconditional existence/deletion guarantee; an unreadable stale file is not removed by this gate. Deletion precedes checking whether the option is STL/PDA/STB, so even an unsupported option can remove readable stale output.
4. `_strcmpi(option,"STL") == 0` reaches `0x402db4–0x402dbc`: push `1`, push suffix at `0x4066ec` (`DEF_STL.EXE"`), push prefix, call thunk `0x40103c -> 0x401c00`. The next instructions force zero return. Main then calls imported `exit(0)` regardless of that result. Child failure is not translated into a wrapper failure status.
5. `0x401c00–0x401d11` first concatenates prefix and suffix into a local command buffer, then overwrites its first word with the quote and NUL at `0x4064d4` (`0x401c24–0x401c30`), appends that quote again, then prefix, suffix, and another quote. The suffix itself ends with a quote. Consequently the exact constructed command is `""` + prefix + `DEF_STL.EXE""`: it has **two leading and two trailing quote bytes**. This slightly unusual literal construction must not be silently normalized in a claimed exact reconstruction. The function flushes stdout, calls imported `system` (IAT `0x407144`), then flushes stdout again; the route does not call `_spawnv`. The pushed third argument `1` is not read in this helper body. No `chdir`, input redirection, filename argument, or KEY output argument occurs in this path.

The prefix selects a command target, while `SCRATCH.KEY` is a relative filename. Static code supports inherited process working directory as the intended relative-file context. Actual Windows command-shell resolution and handling of the doubled outer quotes remain runtime questions. Neither installed sibling resolution nor stdin inheritance was observed by this investigation.

## Child: bounded prompt and output facts

CRT startup calls `0x404900` at `0x419413`. That function initializes object number one and a float tolerance of approximately `0.0010000000474974513` (stored float at `0x42f758`). Before asking interactive questions it tests `DEF_STL.INI` with `0x404770`, then attempts an `"rt"` open at `0x40493c–0x40494b`. The config route reads a filename using `%s`, object with `%d`, and tolerance with `%f` at `0x404958–0x4049ab`. Invalid/nonpositive object numbers are reset to one. Negative tolerance is diagnosed and reset; zero tolerance is reset to the stored default. Read-conversion return values are not tested in these shown call sites.

When the initial INI test fails, `0x404a29–0x404b1f` follows this order:

| Prompt | Input conversion | Following branch |
| --- | --- | --- |
| `Enter STL File Name or 0 to quit` (`0x42f69c`) | `%s`, call at `0x404a46` | First filename byte `0` exits zero (`0x404a4e–0x404a57`), not a whole-string equality test. |
| `Enter Object #` (`0x42f688`) | `%d`, call at `0x404a79` | Nonpositive object resets to one. |
| `Enter Error Limit # (0 for default tolerance of %.3e)` (`0x42f640`) | `%f`, call at `0x404acf` | Negative/zero handling as above. |

These conversions call the same statically linked input wrapper `0x418a88`, which forwards format/varargs to `0x418a02` with stream selector zero. This is strong static evidence for scanf-style token input: blank lines are not established as default answers, and `%s` does not admit a space-containing path as one token. The deepest CRT scanner was not fully reconstructed, so locale, encoding, EOF, malformed numeric tokens, buffer bounds, and unusual path behavior remain outside this contract. A failed INI open after its initial test prints an error and joins conversion; it does not use the ordinary prompt branch (`0x404a09–0x404a24`). Do not replace that race/error prefix with an invented fallback.

Both routes join a call to processing function `0x403b00` at `0x404b48`. Within its output path the call at `0x404172` reaches writer `0x4038c0`. That writer opens literal `SCRATCH.KEY` with literal `"wt"` (`0x4038cc–0x4038db`, mode `0x42ed94`, path `0x42edd4`). It tests the stream pointer and prints `Error opening file SCRATCH.KEY` on null (`0x4038e0–0x4038fa`). This proves a text write/truncation request when that writer is reached, not success or atomic output. The complete processing/geometry branches, ASCII versus binary admission, merge ordering, KEY record grammar, and writer-failure propagation have not been recovered. The child's main-like function returns zero after processing (`0x404b48–0x404b67`).

The wrapper itself neither creates KEY records nor verifies new output after `system`. If deletion fails, stale output can remain. If child creation fails after successful deletion, output can be absent. If a writer fails partway, partial output is possible; the inspected wrapper does not distinguish it. These are control-flow implications, not observed runtime cases.

## Selected next leaf and exact missing witness

The smallest defensible leaf is the **external KEY/STL wrapper boundary**, not an STL parser. Its static specification is now sufficient to propose a narrow launch/cleanup implementation, but it is not yet an accepted end-to-end source change. The actual source caller is `source/port/def_pre/src/menu_shell.cpp:464–471`: File Input option `5` calls `launch_dir0("DEF_CVT3 KEY STL")`, then reads `SCRATCH.KEY` if readable and waits for return. The existing `source/tests/commands/FILE_INPUT/fi_stl_def_cvt3.json` labels its extra answers as guesses. It is not an actual-caller acceptance for this new contract.

Include one controlled missing-child case with a preexisting readable marker KEY so deletion-before-launch and ignored failure can be distinguished from successful conversion. This task does not authorize that execution.

For the source implementation's actual-caller test, drive the existing File Input option `5`, route its launch boundary through a controlled converter/child seam, and assert event order: stale readable marker tested/deleted, exact child command requested in the same cwd without filename argv, ignored child failure, then caller read only if KEY is readable. A marker left by failed deletion must remain eligible for the caller's readability gate; do not strengthen it to “new output only.” Separately assert the three token prompts or INI selection once original runtime evidence is authorized. Until that witness exists, retain the fixture as guessed and do not claim full STL conversion, character/numeric compatibility, or original-process validation.
