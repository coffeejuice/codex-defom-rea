# Checkpoint 50: reachable non-ASCII path guard in Extra3D sidecars

## Target

The current Extra3D sidecar adapter has a public unsupported guard for a non-ASCII directory path. This is a concrete RFORMAT target even though no candidate/original byte diff is available: `makeNativeExtra3DIo(directory, 1252, ...)` calls `ordinaryNarrowPath` on the directory before any operation and throws `M2M_E_UNSUPPORTED` for any UTF-16 code unit >= 128 (`source/apps/moproj2mst/src/engine/simcontrol300_native_io.cpp:22, 99–107`). The focused test `native_extra3d_directory_and_delete_path_profiles_are_explicit` constructs a directory ending in U+4E2D (`中`) under a temp path and asserts that it is unsupported (`source/apps/moproj2mst/tests/mdt/test_simcontrol300_native_io.cpp:170–186`).

The Extra3D fill is a reachable SimControl branch, not merely an unused helper: `simcontrol300_lifecycle.cpp` dispatches the `Page::Extra3D` case to `fillExtra3D(io, context.numericLocale)`. With a non-ASCII project/operation directory, the constructor guard refuses before it attempts a sidecar read. Public full lifecycle integration remains separately qualified; this report only identifies the existing typed-I/O branch and its caller.

## Original behavior supported by retained source

The original scalar sidecar readers at `0x1410da510` (double array) and `0x1410da690` (integer array) construct `QFile` from a `QString` path, call `QFile::exists`, and open ReadOnly before attaching a `QTextStream` (`analysis/wave2-doe-sim300-extra3d-sidecars-decompile.json`; qualification contract `analysis/wave2-save-diffs-300-native-reader-contract.json`). The original writer at `0x1410da9e0` constructs `QFile` from a `QString` and opens WriteOnly; the surrounding `0x1410db030` assembles QString content using `QString::number(..., 'g', 6)` and calls it with fixed ASCII names including `SPRING.INI` / `SPRING2.INI`. These are Unicode Qt file paths. The retained call sequences do not establish an original rejection for non-ASCII path code units.

Thus the current ordinary-ASCII directory guard is narrower than the original's apparent QFile path type and may refuse an original-reachable Unicode path. This is a source-level discrepancy candidate, not a confirmed behavioral mismatch: no retained original runtime fixture demonstrates opening an Extra3D sidecar under a non-ASCII directory.

## Separate path and content codecs

- **Project input path:** the CLI wide API receives the project path as UTF-16. It is not itself converted through ACP before the Extra3D adapter receives its directory.
- **Original sidecar path:** QFile receives a QString path for read/write, rather than a narrow path generated by `QString::toLocal8Bit`. The PE evidence for this branch therefore does not require assuming ACP for path lookup.
- **Current sidecar path:** `openRead` resolves a QString name and forwards it to `StudyIo`; `openWrite` passes the resolved QString to `mst::FileDevice`, which opens a wide path. However, construction first calls `ordinaryNarrowPath` and refuses non-ASCII, so those wide operations are unreachable for this case. `removeIfReadable` really does call `ordinaryNarrowPath`, then narrow `fopen("rt")`/`remove`; its path behavior is a separate lower-level branch and must not be generalized from the QFile readers/writer.
- **Sidecar content:** original `QTextStream` parses scalar values and its locale/codec path is independent from the QString filename. The current adapter currently bounds content to ASCII/KnownC; its contract explicitly leaves BOM/Unicode decoder and non-C locale branches unresolved (`wave2-save-diffs-300-native-reader-contract.json`). This report does not assert the content is UTF-8 or ACP encoded.

## Concrete next validation

The minimum useful original-first fixture is a disposable copy of a known 3D project that reaches `Page::Extra3D`, placed under a short directory containing one non-ASCII component such as `C:\PROBLEM\Café\`. Keep the fixed sidecar basename ASCII and seed one existing scalar file (`NBC.DAT` or `STRAIN_DST.DAT`) with the known ASCII numeric grammar. Capture the original `QFile::exists`/open outcome or Save-side resulting files, then run candidate only after confirming the same page/sidecar branch is reached. Record both raw path and content bytes. Expected evidence question: does original QFile open this Unicode directory and does candidate guard before that open? Keep parser locale/content questions separate from filesystem path behavior.

Until such a fixture is qualified, the concrete current status is: candidate public guard refuses non-ASCII Extra3D directories; original source passes QString paths to QFile and has no source-evidenced ASCII-only guard; runtime parity is unestablished. No source, fixture, build, application, or mutable REA state was changed for this audit.
