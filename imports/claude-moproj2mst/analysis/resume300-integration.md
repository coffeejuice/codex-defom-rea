# CP300 fake-only cloned-image handoff scaffold

CP300 added an optional callback to CP289's `_acquire` after collective manifest, command and retained-handle identity validation and before its `finally` closes source, destination, directory and parent handles. The default CP289 path has no callback and keeps its previous behavior. The new private coordinator uses a disposable synthetic manifest with a `fixture.exe` entry, selects the **copied clone** image, and requires its copied SHA-256 and retained destination final-path identity before passing that path to an injected fake owned-process factory. It then checks fake PID, primary TID, creation FILETIME, image/hash/cwd/argv and suspended status; cleanup must report exact exit and wait. It never calls resume.

Independent review caught a first design that launched an external fixture with only the clone as cwd. That did not prove clone-image provenance. The implementation was corrected to require `cloneRoot\\fixture.exe`, its copied entry and retained destination identity. The review also found that an arbitrary matching `fixture.exe` name and caller-supplied hash cannot prove a harmless binary, and that CP214's current `OwnedProcess.close()` can discard the retained handle after failed termination/wait; constructor-side cleanup failure can leave identity uncertain. The code now labels such cleanup `uncertain_child_may_remain_live`, requires explicit fake API/factory in the private seam, rejects the real `OwnedProcess`, and hard-disables the fixed B98 real entry point. This is a **fake scaffold**, not a completed creation-bound real-child handoff. The fixed B98 manifest has no synthetic fixture entry and cannot take this path. No real synthetic child, original app, GUI or Frida was launched.

Nine fake-only focused tests passed, covering retained callback timing, copied-image/identity checks, suspended state, prior clone refusal, manifest refusal and uncertain cleanup. CP289's 26 tests passed 25 with one logged OS symlink-privilege skip; they exercised disposable native file behavior and did not create a real B98 clone. Raw logs and the separate compatibility receipt are retained; the historical CP289 receipt was restored unchanged. Machine receipt: `analysis/cp300-fake-validation.json`. This checkpoint does not change converter outputs or m2m C ABI. CP301's final full converter regression remains the latest compiled candidate.

The reference-harness README and observation template now distinguish a GUI-control release receipt from a fully owned non-GUI CLI/debugger child, and request creation FILETIME, primary TID, loaded modules, clone receipt and accepted-Close evidence. The current supported computer-use API still has no release/status operation, so no new GUI-control session was acquired.

CP302 is selected: establish a fixed reviewed harmless fixture identity and repair/prove CP214 cleanup ownership on failed termination/wait and constructor failures. Only after those gates pass can a real **synthetic** cloned-image handoff be considered. CP215 observer/live patch gates and original execution remain separate HOLD items. The recovery queue's other public editor300, DOE, Boolean, Save failure and Close paths remain guarded.
