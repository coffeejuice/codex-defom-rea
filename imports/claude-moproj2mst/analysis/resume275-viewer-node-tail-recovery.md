# CP275 viewer node-display tail: helper-local contract recovered; caller leaf HOLD

## Decision

`FUN_1411fc900` has a small finite synchronous contract: after the nonnull-object bind's color call and optional Slice call return normally, it takes the size of the View's `+0x2e8` node-display vector once and writes byte `1` through the indexed accessor for each index from zero to that size minus one. An empty vector produces no indexed access or write. The loop has no object, owner, settings, or geometry gate of its own. This is a qualified **helper-local** recovery, not yet a PASS-ready converter change. The actual caller must reach the node tail, the vector is absent from the converter, and the retained record does not close the indexed accessor's copy-on-write/failure behavior or provide an observable actual-caller test. Status: **HOLD for implementation**.

## Evidence and scope

The retained original is **DEF_GUI_MO_64.exe v11.0.2**, SHA-256 `fd8ae1f8dd50d068267b3b7e49efdf11eaa178889131e59ec4b6f8de64725acc`, as independently qualified in `analysis/resume257-scene-next-leaf.md` and `analysis/resume262-scene-radius-next-leaf-review.md`. This pass read retained decompilation and current source only; it did not rehash or execute the PE, run REA, open an analysis database, acquire GUI control, build, or test. `evidence/gui_mo/s1/mdt/V/spec_V.md` is a useful prior interpretation, but its “UI-only and droppable” judgment is not an original behavior oracle. The direct body below is stronger evidence for this specific loop. No reconstructed DEF_PRE instance is discussed.

* `V/v0.c:436-476`, `FUN_1411f17f0`: null object stores null, fully unbinds, does display cleanup, and returns **before** node display. A nonnull object partially unbinds, stores the object, chooses 3D or 2D representation binding, resolves color mode, calls `FUN_1411f28f0`, conditionally calls `FUN_1411fdd30` when View `+0x338` is nonnull, then calls `FUN_1411fc900`. Neither color nor Slice has an outer-binder skip around the node call. Their exceptional/nonreturning paths would still prevent it; this review does not claim those paths are absent. The Slice early-return cases in CP272/274 return from the Slice helper, then continue here.
* `V/v1.c:400-417`, `FUN_1411fc900`: `func_0x00014127ee00(view+0x2e8)` supplies one initial signed size. For an unsigned 32-bit loop index starting at zero, each iteration calls `FUN_1411659d0(view+0x2e8, index)` and writes one byte `1` to the returned pointer. The loop neither resizes the vector nor calls a graphics backend directly. Its writes are ordered by increasing index. A failure during indexed access could leave a prefix set; the body contains no rollback or error translation. The retained listings do not contain the bodies of the size or indexed-access helpers, so allocation, detachment, and exception behavior cannot be stated exactly.
* `V/v1.c:1-85`, `FUN_1411f2050`: the 3D bind path reaches `FUN_141201e90(view+0x2e8, *(int *)(obj+0x880))` only after `*(int *)(obj+0x87c) != 0` and `FUN_1408340f0(obj)` is true. This resize precedes mesh-rep creation and `FUN_14122d9e0(rep, view+0x2e8)`. `V/v3.c:308-350` shows that rep attachment reads the vector size and, when nonempty, takes element zero's pointer; the resize helper calls `FUN_141165bc0` after its growth decision. These calls support the vector's node-display role, but do not establish all resize/COW side effects. `V/v1.c:126-244` shows the 2D binder has no corresponding `+0x2e8` resize in its displayed body; a 2D node-tail result therefore depends on preexisting vector state, including prior binds, and is not safely inferred as always empty.

## Actual converter route and candidate test

`source/apps/moproj2mst/src/engine/viewer.cpp:1659-1683` implements `bind`. Its nonnull path partially unbinds, stores the object, binds a 3D or 2D representation, then returns on pending geometry; it qualifies the Slice short circuit and ends without native color or node effects. `viewerSync` calls this bind at lines 1857-1874, and `viewerRebuild` calls it at lines 1876-1891. Thus `viewerSync` with a nonnull, live, ordinary 3D object is the smallest existing production caller to target. `test_viewer_box.cpp` already uses that entry point (for example the test beginning near line 476), but its objects have no 3D mesh-node display vector to inspect. `test_geometry_node_width_mismatch.cpp` builds a 3D mesh object, yet its constructor calls `viewerSync` before attaching the mesh and then proceeds into a separate reader path; it is not evidence that the node tail writes a positive-length vector.

A meaningful future test would set up a 3D object with `+0x87c != 0`, valid coordinates accepted by `FUN_1408340f0`, and positive `+0x880`; call `viewerSync` through the current production entry point; inspect the View's node-display vector after binding; then rebind after deliberately clearing one flag and verify the tail restores it to `1`. Include an empty-vector case. The test needs a narrow internal observation seam or later consumer of this vector. A test of a standalone fill helper, or of `viewerSync` without an observable node state, would merely mirror the implementation. The result also requires accounting for the color call that precedes the native node tail and for the optional Slice side effects; this report does not assume either away.

## Boundary to clear

Before implementing, source-qualify `FUN_1411659d0`, `func_0x00014127ee00`, and `FUN_141165bc0` (or immutable code bytes for their bounded behavior), including shared-vector detachment, failed access/allocation, and partial-write ordering. Establish the fresh View vector state and what partial unbind preserves. Bind an ordinary positive-node caller fixture to that state, with a testable effect after the color/Slice prefix. Then the finite leaf can be stated as vector resize/attachment plus post-bind fill for the admitted fixture, without claiming full color, graphics, or historical-session parity. Until then, the direct loop is known but converter parity is not PASS-ready.
