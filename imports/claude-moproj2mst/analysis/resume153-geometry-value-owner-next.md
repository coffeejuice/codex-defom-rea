## Why existing calls do not close this next boundary

Unrestricted `StateVarBase::resize_values(false)` already contains host malloc1, then CowVector.resize, slot publication and temporary free. Its broad successful order matches the native leaf, but the API exposes neither temporary allocation occurrence nor an owner-qualified failure stop before its unconditional host bad_alloc behavior. A caller catch cannot reliably certify which allocation failed or retain an actual T ownership receipt. Calling the whole virtual leaf would also repeat CP152's setters and overwrite their previous values. These are concrete reasons to keep the existing guard rather than invoke the method and inspect its final state afterward.

There are two ownership domains to reconcile explicitly in an integrated implementation: (a) the existing typed candidate StateVar/CowVector allocator mapping and its deallocation lifecycle, (b) strict native source-role CRT heap/handler/free observations. A successful host malloc return may be valid translated candidate storage under its paired owner, but it must not be labeled an original heap-slot/handler witness. Conversely, actual source-role HeapAlloc storage cannot be installed in a std::free-owned body. Neither ownership claim should be invented from a Boolean success or static address.

The next **integrated engineering boundary** is an occurrence-aware allocation continuation attached to this actual frame/receiver/value body, with a compatible allocator/deallocator mapping used by temporary allocation and the actual value body lifecycle. It must preserve request0->normalized1, request8, fill/body/slot stores, partial failure, and normal free/error order. It would require coordinated existing StateVar/CowVector allocation-path integration (including clear/destruction/clone ownership), not a standalone helper or Viewer-only heap-owner flag. Keep the current0x38 StateVar ABI and current body owner intact until that binding is concrete. No source-ready publication through the current APIs was established in this read-only lane.
