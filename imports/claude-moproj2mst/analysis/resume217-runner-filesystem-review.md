I independently compared the current fixture’s content manifest to `resume202-passive-oracle-run-2026-10-26T04-45-03-155Z/source-before.json`: both contain 33 entries and all path/type/size/content hashes match. `Gear_blank.moproj` is 10,932 bytes with SHA-256 `e769faf514b335d56ffbb22f2c76490d029f2714ada9b26a75496fbd62ade7fd`.

XML is parsed after cloning; the runner requires the ordered operation names, IDs, and types for both control and negative cases. This is a useful structural witness, although it does not independently compare the cloned negative project bytes to the expected variant bytes.
- The `encodeQChar` loop serializes JavaScript UTF-16 code units as four hex digits each and round-trips the string. `helperArgs` sends that ASCII encoding to the owned-process helper; the `created` identity receipt is checked against the same exact encoded path and expected `-m open -f` argument positions. The self-test only exercises an ASCII path; no non-ASCII or surrogate-pair fixture is covered.
- Clone paths are lexically constrained below `C:\PROBLEM\` and the project path is required to be under 100 characters. The two configured paths are short.

## Blocking findings

1. **The live runner stops before cloning because `writeJsonExclusive` is undefined.** It is first called for `preflight.json` (line 137), before either case is cloned or any child is spawned. Later calls also depend on it. Define it using exclusive creation (`open`/`writeFile` with `wx`, and close in `finally`), or the opt-in run cannot produce its first receipt. The current literal-false guard prevents this defect from being reached by a normal invocation.
2. **The fixture is not pinned by this runner.** `preflight()` builds `sourceManifest` from whatever is present at invocation time; it does not compare against the known 33-entry qualified source manifest or a fixed manifest digest. The current tree matches the prior CP202 manifest on this inspection, but that does not make future runner executions reject a changed fixture. Pin and validate the expected manifest/content digest before creating clones.
3. **The `C:\PROBLEM` containment check is lexical and misses reparse ancestors.** `path.resolve()` does not resolve Windows junctions. The fixture-root walk also checks entries but not the root itself or its ancestors. A junction at `C:\PROBLEM` or at the fixture root could redirect cloning or source reads outside the intended tree. Reject reparse points on each existing ancestor (at minimum `C:\`, `C:\PROBLEM`, the fixture root and its path components), and verify canonical final paths remain under the intended physical root before copying. Recheck the destination immediately before creation to narrow the preflight/copy race.
4. **Source immutability is recorded but not enforced.** Each result stores `sourceAfter: inventory(pf.source)`, but never compares it to `pf.sourceManifest` or fails on a change. A mutation during or after copying can therefore be reported as a successful case. Compare source-after to the preflight manifest and mark the run incomplete on any difference; ideally revalidate source identity immediately after each clone as well.
5. **Negative-copy identity is not proven byte-for-byte.** `cloneCase()` writes with `flag: 'w'` and only requires the negative manifest to differ from the source in one path. It does not assert that `Gear_blank.moproj` equals `pf.variant.bytes` or has `sha(pf.variant.bytes)`. Verify exact bytes/hash after writing and use a safe, race-aware overwrite of the freshly cloned file; the current `w` flag can truncate a replaced file if the destination is raced.
6. **The effect delta is evidence, not an acceptance check.** The runner records arbitrary added/removed/changed clone entries and reduces comparison output to path lists. It does not validate that each case has a usable delta or that both inventories completed under the expected case identity. If CP217 requires a pass/fail comparison, add explicit schema and result predicates after the expected output contract is known; otherwise label the output as observational evidence.

## Error-path notes

Missing executable/helper, hash mismatch, parser failure, unexpected XML, and existing destination paths throw before launch or before case execution. However, `fs.existsSync()` can miss dangling links, and no check validates the physical destination root. `spawn()` has no explicit `error` listener; startup failure becomes a delayed missing-event path rather than a direct spawn diagnostic. If the parent’s 30-second close wait expires, it records a timeout but does not terminate the helper launcher, so that outcome must remain incomplete/uncertain and needs bounded owned cleanup before a future run is considered safe.

- Assert source immutability and exact negative-variant bytes/hash.
- Add non-ASCII QChar transport coverage, direct spawn-error handling, and cleanup for the launcher-close timeout.
- Keep the original-launch guard false until these changes are reviewed and the external GUI-control release prerequisite is satisfied.
