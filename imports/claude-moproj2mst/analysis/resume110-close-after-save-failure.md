# CP110: FileCloseAll after a failed or cancelled Save

The native Save answer, native main-window Save Boolean, and converter error are three different contracts. Project/MST writer false does not itself reject native Close. A later FileCloseAll evaluates the current application/main state and can invoke Save again before any accepted cleanup. No accepted-Close leaf can currently be added to the public converter by treating a returned adapter error as that native call boundary.

Only this report was written. Investigation used retained native contracts/source and bounded offline PE/DUMPBIN reads; no code, build, test, GUI, original execution, REA retry or mutable REA database. ## Actual converter seam and exact blocker

Current `src/core/convert.cpp` constructs a ConversionSession, registers its real Mo child before Project initialization, commits moProject after initialization, selects after Open, and executes split native Save effects. It retains project/MST failure through the remesh tail, then maps them to M2M_E_WRITE (MST before project); an unrecovered remesh boundary maps M2M_E_UNSUPPORTED. Its catch returns an adapter error. There is no normal-Close callsite. `ConversionSession::~ConversionSession` expressly performs adapter storage/receiver/dispatcher cleanup, not native Close. `releaseProjectAfterCloseEffects` is storage-only after diagram-null admission, not a Close decision or Save.

No existing closed leaf supplies a valid shortcut: writer false does not null moProject; the actual manager is not empty after registration; Report-null is nested behind Project/diagram/SubProject predecessors; and the real notifier prefix requires the accepted true-busy caller first. Calling any of these from catch/finally would invent phase reachability. Calling normal Close after the default native terminal remesh branch would additionally invent a return/unwind that never occurs in that qualified path.

The first producer dependency remains CP106/107's actual startup chain: CRT initializer141ca0bb0 constructs singleton143d766b8; main1410 runs pre-application7fc450, constructs SfApplication21c0/QApplication, then the actual primary SfMoMainWindow10490. Its basec99530 publishes the same this atc9957b before main+50 setup; the derived table and later+480/+270 producers are separate later phases. Current GuiStartupUnitScope, Session, primary-address projection and run mutex do not execute that producer. An invocation-local AppState with constructor constants cannot establish the post-Open/Save current main or busy state.

Therefore **no new public Close source increment is qualified here without that same-owner producer/cursor**, followed by live busy/current-main, modal due-event/nested-Save, display, notifier and destructor dependencies. The useful implementation work is the actual startup/base/derived/main-manager integration slice, guarded at its first unresolved Qt predecessor; it is not another detached Close helper. No source patch is proposed in this lane.

Focused future validation must drive the actual one-project owner through Open, explicit Save failure, subsequent FileCloseAll and nested Save, recording same singleton/main/manager identities and fresh busy reads. Separate fixtures must distinguish project-false, MST-false, their combination, warning cancellation, no-nonnull-subproject, and terminal remesh. Assert prior file residue and exact answer independently of adapter error; require no accepted mutation on exact Cancel and no manager current reset before child teardown. A declared helper fixture cannot certify native modal schedules or startup. No tests were executed here.
