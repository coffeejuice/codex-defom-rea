# CP388 exact-child exit and stage integration

CP382's fourth inert occurrence stopped after `FixedParentEntry.from_client_argv` and before either return or caught exception from `run()`. Its outer 80-byte claim read failed Win32 109. The preserved receipt did not contain the child's exit status before cleanup, so a crash and cleanup-induced termination remained indistinguishable.

CP349 now performs `WaitForSingleObject(process, 0)` on its retained exact CP347 process handle only after a failed claim read and before cleanup. It queries `GetExitCodeProcess` only after `WAIT_OBJECT_0`; timeout is recorded as active, and unrecognized/query errors remain unknown. The original read error stays primary. CP350 writes this observation into a separate failure report field.

CP349's fixed bootstrap passes its bounded stage writer to CP347. CP347 emits markers at entry, before/after native export loading, before/after CP334 inherited-client adoption, and before/after CP333 acknowledge and complete. The trace parser accepts the full ordered marker set while retaining its bounded size, exclusive occurrence path and termination-before-read rule. The stage writer does not select success or alter the public converter.

Independent CP388 review found a fail-closed hole: a later callback could clear an earlier diagnostic callback error before the claim. Root made that error sticky, protected the callback and client argv fields from mutation, and added a regression. Injected tests also cover exact exit observation ordering, CP350 serialization, and the complete marker sequence. `analysis/cp388-final-tests.log` records 627 passing CP3xx tests from each of the two import roots. An earlier sandboxed test attempt could not write its temporary directory; the normal authorized run passed and that infrastructure failure is not a product result.

No native child, WORKER, original DEFORM application or GUI control ran for this integration. CP301 remains the compiled C++ converter candidate, with historical 93/98 full-Save matches and unresolved guarded paths. The next executable action is a clean source/bytecode freeze and independent gate for at most one new monitored inert CP350 occurrence. A result must be interpreted from the exact exit observation and the first missing stage; an absent stage is not proof of a specific native failure without corroborating evidence. Do not rerun the CP382 occurrence.
