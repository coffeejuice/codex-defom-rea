## Corrections required before reusing the pattern for original capture

1. **Bind cleanup to process identity, not only a PID (lines 21–24, 37–44).** Record the owned child's executable path, full command line and creation time immediately after spawn; retain an OS process handle/creation identity where available. Check that identity before every destructive cleanup action, including `device.kill`, and record mismatch as an unresolved cleanup condition. The current primary kill has no identity check. Its fallback checks only path plus a `time.sleep(60)` substring, which can match another Python process after PID reuse. A creation-time check improves detection; a retained handle avoids the check/kill race. Never generalize the substring rule to an original app.

2. **Make cleanup single-flight and actually bounded (lines 35–55, 65, 85–87).** The watchdog can enter cleanup concurrently with normal `finally`. Normal `finally` clears the watchdog before awaiting cleanup, and `device.kill`, `unload`, `detach` and enumeration have no individual deadlines. Ten iterations do not bound those awaits; ten CIM failures alone can consume roughly 100 seconds. Use one cleanup promise/state, per-operation deadlines and an independent supervisor tied to the owned process identity. Retain timeout and uncertain outcomes. Cover the interval before the PID is returned as well: the current watchdog starts only after `spawn` resolves.

3. **Require fresh successful verification observations (lines 28, 50–54).** Each verification attempt should produce a timestamped success/error record for both observers. Do not retain an earlier `null` as the current result when a later query throws. Require both final absence checks to succeed, matching readiness PID/cwd, and no unresolved watchdog, script or cleanup error before emitting PASS. Currently the PASS expression ignores `failures`, `localVerificationError`, `fridaVerificationError` and unexpected script messages. The supplied clean run has none of these errors, so this weakness does not invalidate that particular reported result.

4. **Retain a reproducible execution identity.** Bind the report to the runner hash, injected script bytes/hash, Python executable hash, Frida package manifest/hash, loaded native binding identity/hash and Node runtime version/path. A package version string and import URL alone do not authenticate the installed code. For an original run, additionally freeze the original executable and relevant loaded-module hashes, module bases/sizes and architecture; identify hooks as module-relative addresses plus recovered signatures/source qualifications. Preserve raw messages/errors and per-run immutable report names instead of overwriting the sole report path.

5. **Validate actual hook readiness before original behavior claims.** A future instrument must report every intended hook installed at a validated address before resume; fail on installation errors or unexpected module identity. Preserve hook coverage, invocation records, dropped/error counts, target PID/run identity and the fixture/output hashes needed by the comparator. This Python API-call probe establishes none of those properties.

6. **Keep authorization and lifecycle gates separate.** This source can inform the spawn/attach/readiness structure of a future owned original capture after the corrections above and the applicable original-capture contract are satisfied. It provides no GUI release operation or verifiable release receipt. Any capture needing GUI control remains subject to the existing release-lifecycle gate. Process kill, Frida detach and JavaScript completion must not be described as GUI-control release.

No source modification or repeat probe is required to accept the supplied narrow smoke-test observation. Original capture remains BLOCK under this review until its separate identity, hook, cleanup and evidence requirements are met.
