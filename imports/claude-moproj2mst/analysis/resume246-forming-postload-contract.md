# CP246: Forming post-load equipment coordinator contract

## Decision

A finite synchronous coordinator is a valid ownership boundary for the **successful, recorded-effects** route, but the current `createEquipment` helper cannot simply be moved behind it. The retained original has a different order: it assigns the `ObjEntry` and `Operation` equipment IDs **before** the second equipment KEY write. The converter's `createEquipment` records that write before it returns, so `formingPostLoad` assigns the IDs afterward. That difference matters if the second serialization or write fails. The current `FileEffects`/`addEquipment` representation also cannot reproduce native copy failure: with non-null bytes, `addEquipment` unconditionally records a mkdir and write, appends a row, and returns a positive ID. A faithful failure-path migration is therefore **not implementation-ready** until the native add/copy failure prefix and its converter effect mode are resolved. A refactor that only hides native aliases would certify a known wrong prefix.

## Exact source and original sequence

The live `loader_l3.cpp:126-143` path resolves `opModel(p, op)`, returns if absent, calls guarded nullable `m->simCtl()` and returns if null, reads `pdie1`, reads `op.equipmentId`, then calls `m->object(pdie)` and `objEntryN(op,pdie)` in that order. `objEntryN` is not a pure lookup: for an in-range slot it appends missing `ObjEntry` records up to that slot (`model/objects.cpp:93-107`); out-of-range returns null. The equipment-manager lookup follows those reads in the original. Creation is gated by existing manager, `equipmentId < 1`, engine object and slot. The converter assumes a Project equipment manager always exists.

The retained GUI v11.0.2 static decompile, `evidence/gui_mo/s1/mdt/L3/d0.c:84-161` for `0x140c06130` and `:254-327` for the 2D twin `0x140c04950`, establishes this ordered successful branch:

1. Build `Equipment (<manager row count + 1>)` and a temp KEY path; remove a pre-existing temp file, serialize the object movement to that temp file, call equipment-manager add (`0x1400bf510`), then remove the temp file. The add wrapper calls manager vt+0x160 and returns its ID (`d2.c:40-43`).
2. Copy the name into native movement bytes at `obj+0x2160` with `strncpy(..., 0x50)`; ask the manager for the new item's file path.
3. Write the returned ID to slot `+0x28` (`0x14004deb0`) and operation `+0x4c` (`0x14004ca30`), in that order (`d0.c:145-146`; `d2.c:286-303`). These calls occur even if add returns `-1`.
4. Reacquire the model step. If non-null, ask for the manager path again and invoke the KEY writer with the renamed movement. The decompile does not show a successful-add guard or an empty-path guard before this second call (`d0.c:147-155`).

The current `postload_views.cpp:165-174` helper instead computes first bytes, calls `addEquipment`, names the movement, obtains the path, **conditionally records the second KEY only when `managerFile` is nonempty**, then returns the ID. `loader_l3.cpp:139-141` assigns both IDs after that return. `addEquipment` at `postload_views.cpp:91-104` records `mkdirs`, then the first `writes` entry, then appends the Project equipment row. `equipmentBytes` performs a disposable native temp serialization even in recorded-effects mode (`postload_views.cpp:108-119`). `FileEffects` keeps separate mkdir/write/delete vectors (`engine.hpp:42-68`), and `core/convert.cpp:110-130` later replays all mkdirs before all writes. Consequently vector order can prove two equipment writes relative to each other, but cannot by itself prove physical mkdir/copy/row/ID/write chronology or an original copy failure. The existing atomic write replay is another already-known Save fidelity limit; this contract does not broaden that redesign.

The older L3 spec §2, §6-7 and ledger name the same original functions but still say this creation is refused. That refusal statement is stale relative to current source and `test_engine_l3.cpp:360-379`. The source/decompile establishes the intended ordering; neither it nor the historical Oracle-B 96 final-file comparison (`tests/s/test_postload_views.cpp:9-11,141-151`) is fresh original execution of each branch or failure.

## Finite API and placement after the failure prefix is settled

Use a named `GuiModel` member, proposed `void completeFormingPostLoadEquipment(Project&, Operation&, FileEffects&)`, declared next to other owner commands in `include/m2m/engine.hpp` and implemented in `src/engine/postload_views.cpp` beside equipment creation. `loader_l3.cpp::formingPostLoad` keeps the existing `opModel` lookup and invokes that member only when non-null. The member owns one synchronous `simCtl()` borrow, `pdie1`, object lookup and native step/serializer access, while receiving the exact `Project`, `Operation` and `FileEffects` owners by reference. It retains no pointer or reference, returns no native alias, publishes no callback, and changes no C ABI. This cross-owner method is a finite command, not a claim that `GuiModel::step` or all other loader aliases have been closed. Do not add a new admission after a side effect or precompute a value before the existing guarded `simCtl()` call.

The coordinator must keep the original read order, including `objEntryN`'s possible lazy append on a no-creation branch. It then executes the creation phases in the order above. Do not call today's whole `createEquipment` from the coordinator, because it performs the second write too early. A forming-specific phase implementation may share the pure naming/serialization utilities and `addEquipment` only after its failure behavior is qualified; keep `equipmentSync`'s existing use of `createEquipment` untouched unless a separate reviewed contract covers it. Do not use a generic callback between add and final serialization as an owner escape hatch. In particular, the ID stores must occur after name/path operations and before the second KEY attempt, and a null reacquired step must skip only that final KEY attempt. Preserve `-1` propagation on add failure; do not silently return, roll back a row/file, or substitute zero.

`simCtl()` and `object()` currently apply the geometry barrier (`gui_model.cpp:210-219,401-405`), whereas `objectCount()` does not. The command must preserve the first barrier check at `simCtl()`, and must not introduce a later extra guard between IDs and the final writer. The original's second step lookup is nullable; a modern implementation must decide how to express that lookup without turning it into a new throwing admission. That decision belongs to the same failure-prefix review.

## Branches and tests that establish the migration

The existing `test_engine_l3.cpp::forming_without_equipment_creates_one` uses copied corpus 56 op 1 and reaches the caller through `loadOp`, but checks only `op.equipmentId > 0`. Extend a focused copied-corpus fixture, under the configured test scratch, to check the selected PDIE slot's ID, one new Project equipment row and its ID/name/path, the first and final `FileEffects::writes` entries and their distinct bytes (the final movement name), and no unrelated effects. This is a reconstructed successful-path test; compare final bytes with historical Oracle-B 96 only with that provenance stated.

Use separate fresh fixtures or reset model/operation state for each branch, and call the actual L3 hook or `loadOp` path:

* **Existing operation equipment (`>=1`)**: retain the ID, row set, movement bytes and effect vectors. Still run the preceding object/slot lookups; if a valid slot had no materialized record, the `objEntryN` lazy append is an expected prefix, not a failed no-op.
* **Missing engine object**: choose a PDIE number that is an in-range operation slot but absent from the loaded model; verify `m->object(pdie)==nullptr` before invocation. This isolates object absence from missing-slot behavior. Assert no equipment row, KEY effect, name mutation or ID change, while allowing/expecting the slot materialization caused by `objEntryN`.
* **Missing operation slot**: keep a real engine PDIE object but make `pdie > objSlots(op)` in a copied operation fixture. Verify no new equipment row, KEY effect, movement rename or ID change, and no `ObjEntry` append. Do not use PDIE zero for this case: it usually makes both object and slot absent.
* **Null model/control and parked geometry**: preserve early return for null model/control; for a parked model the existing `simCtl()` refusal must occur before an object lookup, slot append or equipment effect. These are guard regressions, not native-failure evidence.

For the success path, final-state assertions alone cannot prove the ID stores precede the second serialization. Review the actual coordinator source order and add a narrow instrumented failure test only where a real existing writer/effect seam can interrupt the final attempt after the ID stores. Do not add a production observer solely for the test or inject an exception at an invented native stage. An add/copy-failure test must use a qualified failure mechanism, assert `-1` in both IDs and the observed Project/FileEffects/temp/name prefix, and must not claim parity from a synthetic exception that bypasses the real add path.

## Smallest remaining investigation

Before source migration, inspect the retained manager vt+0x160 / copy helper decompile and the current `nativeSave` path at `core/convert.cpp:265-349`: determine whether a failed mkdir/remove/copy leaves a directory, destination file or manager row; whether `0x1400bf510` still emits notification; the returned `-1` behavior; and how the temp KEY writer's failure is handled. Bind one disposable, scratch-only reconstructed test to the discovered failure seam. If source evidence cannot resolve the native filesystem prefix, obtain a fresh owned-original capture under the established original/GUI-control gates; do not infer it from Oracle-B 96 final files. Until then, only the success-path boundary is specified; the full faithful coordinator remains blocked by this specific effect/failure contract, not by an inability to pass the finite owner types.
