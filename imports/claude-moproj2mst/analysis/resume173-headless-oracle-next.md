# CP173: bounded Qt dock visibility signal route

## Result

The retained Qt implementation **can** emit `QDockWidget::visibilityChanged(true)` without a mouse or keyboard action: `QDockWidget::event` routes a delivered Show event through a true-signal branch when its two dock-position checks are nonnegative. The original `-m open -f` startup calls programmatic `showMaximized(main)` after postOpen, so an input-free Show event is a concrete candidate producer. For the selected fresh B98 project, static evidence does **not** establish that the dock `main+0x420` actually receives that Show event with both checks nonnegative, that its earlier `setVisible` request is true, or that the main is unbusy at signal delivery. A fresh original auto-save and a full Open → Save → Close oracle remain unproved. Stop this bounded branch at those runtime/Qt state gates.

Read-only evidence only: original `DEF_GUI_MO_64.exe` v11.0.2 SHA-256 `fd8ae1f8dd50d068267b3b7e49efdf11eaa178889131e59ec4b6f8de64725acc`; retained `QtGui4_64.dll` SHA-256 `c360c971d292a3c84fc59b8e38733a85a111243f1dbc44737d87b6d744725887`; DUMPBIN 14.44 and bounded PE byte/table reads. Only this report was written. No original execution, GUI control, installed file, live/mutable REA or shared source/test/plan/fixture was touched.

## Why the selected CLI Open remains conditional

The retained `98_B_DS3F_before/Gear_blank.moproj` selects active SUB type 0. CP172 traces `0x1400151a0`'s dock request: type 0 initializes visibility true for application type 5, but model/DB owner `0x140cdd330`, Project+0x57, and mutable globals read by `0x1412e85a0` can force it false. The first refresh occurs at `0x14002aabc` **inside** `0x14002aa8a` busy=true / `0x14002aacb` busy=false; postOpen may refresh again at `0x14002a98f` if main+0x3c0 stays zero. `showMaximized(main)` follows only after Open returns. Qt `QWidget::setVisible(true)` at `0x65070410` has branches for already-visible/parent/private widget state, and the examined prefix does not establish that a hidden child's requested visibility becomes a delivered type-17 Show at either refresh. The later main show can make child Show delivery possible, but actual dock membership, visibility, two position values, connection success and synchronous callback order remain unfrozen. `2ca920` also tests singleton+9 and actual main virtual+0x300 busy state, not just the bracket byte (`analysis/resume101-close-live-owner-chain.md`). Consequently the static chain supports **capability**, not this project's auto-save occurrence or a successful file write.

The accepted Close routes remain QAction metadata method 20 → `0x140031f10` → `0x1400299a0` and the window close-event decision `SfMainWindowBase::...` → main virtual+0x2d8 `0x140010b10` → `0x1400299a0` (CP172). No input-free Close producer follows from dock visibility. Program termination and main destructor are a different cleanup path (`analysis/resume149-close-next.md`).
