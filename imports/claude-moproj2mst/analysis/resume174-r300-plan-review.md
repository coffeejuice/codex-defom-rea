# CP174 R300 plan review

## Scope and decision

Read-only review of `analysis/resume174-r300-next-cut.md` against the active CP173 frozen source under `optimization/test-speed/source/apps/moproj2mst`. No source, build, GUI, live REA, or shared runtime state was touched. The plan's bounded four-file migration is compileable in principle, but the plan is not ready to release as written: its required focused cases cannot be implemented in the named test files alone for all stated null-owner/model/step branches, and a proposed `readerSimCtl` explicit-sc fast path must preserve the current no-lookup behavior exactly.

## Source findings

- The frozen source has exactly seven `propsStep(` call sites counting helper-internal acquisition: `props_sync.cpp`'s `readerSimCtl`, the accessor definition, `propsSetHeatingTime`; L2's `furnaceEnvTemp`, `furnacePropsLoad`, `furnaceToEngine`; and L3's `formingPropsLoad`, `fePropsLoad`. Thus seven *callers* is accurate if the plan excludes the accessor definition but counts the two L2 helper callers and two L3 probes plus the two props-sync callers. The source has two props-sync `propsStep` call expressions (`readerSimCtl`, `propsSetHeatingTime`), three L2, two L3 = seven.
- `readerSimCtl` currently immediately returns an explicitly supplied `sc` without touching `Project` or `Props`; only a null `sc` invokes `propsStep`. The plan correctly identifies that returning `&s->sim_ctrl` beyond the new callback lifetime is invalid. Its suggested explicit-sc route can remain a direct `if (sc) ...` branch in each reader or a value/result callback, but it must not call `withPropsStep` first and then override the supplied pointer: that would add a model lookup absent today.
- Null behavior differs by site and must remain distinct. `propsSetHeatingTime` throws before `B(pr)` allocation on absent step. The L2 furnace writer (`furnaceToEngine`) returns before name conversion, length validation, curve update, and diagram signal when step is absent. The L2 furnace property load returns when no step before `furnaceEnvTemp`, `furnaceSetModel`, and `furnaceDataFromSimCtl`. `furnaceEnvTemp` itself returns before curve/diagram effects. The two L3 callbacks perform four property fills first, then return on missing step before `propsModel` and movement/property effects. A bool callback must report actual non-null presence; callback return type alone is not presence unless helper semantics explicitly encode it.
- `furnaceSetModel` copies furnace data into property-owned storage and assigns a name; it retains no engine step pointer. The plan's assertion is supported by its implementation.
- The L2 furnace order is `propsStep` -> `furnaceEnvTemp` (curve update then diagram signal) -> property copy -> sim-control property fill. Preserve this sequence inside the scoped callback or an equivalent nested scoped helper. `furnaceToEngine`'s name validation must remain after successful step acquisition.
- Current tests `tests/mdt/test_loader_l2.cpp` cover a positive corpus furnace path (`heat1_as_furnace`) and ordinary heat-transfer path. They do not cover null owner, owner with no model/step, caller-supplied sc with no model lookup, furnace writer missing-step no-effects, or ordered nested furnace lookup. `tests/mdt/test_engine_l3.cpp` covers positive Express/Forming loads but not either L3 null-step early return or pre-effect property state. A `Props` with `owner == nullptr` is easy to fixture in an engine-level focused test, but a valid owner lacking a model and an explicit caller-supplied sc are harder to exercise through the current corpus loader tests without exposing/injecting internal props-sync functions or adding a narrow test seam. The plan says “add focused cases” but does not identify a viable seam/test owner for these branches.

## Required plan amendments before first compileable cut

1. State the exact seven *callsites* unambiguously: one `readerSimCtl`, one `propsSetHeatingTime`, three L2, and two L3. Do not describe these as seven callsites in addition to the helper/definition ambiguously.
2. Specify helper semantics for bool callbacks: invoke once with null on `pr.owner == nullptr`; otherwise one `opModel` lookup and invoke once with `model ? model->step.get() : nullptr`; return callback's void/bool result, with presence checks explicitly returning `step != nullptr`. This preserves the owner short circuit and allows L3's bool probe.
3. Pin `readerSimCtl` migration to no model lookup for non-null `sc`. Clarify whether the callback itself supplies the scoped sim control or the four property readers split explicit and fallback paths. Any fallback must consume `sim_ctrl` only within the callback and cannot return/store its address.
4. Add a named test-seam owner or revise acceptance to use a feasible existing public loader path for each required condition. Tests must establish null path effects, and the explicit-sc/no-lookup assertion needs an observable lookup counter/test seam; corpus positive tests cannot prove it.
5. Clarify that “all seven callers” includes the nested call in `furnaceEnvTemp`, which may be removed by merging it into `furnacePropsLoad`'s scoped callback. If retained, avoid a second independent lookup relative to today's `furnacePropsLoad` flow; currently it intentionally performs one lookup for the outer step and another in `furnaceEnvTemp`, so the callback rewrite should preserve or consciously qualify that lookup count/order rather than silently collapse it.

## Review conclusion

The raw-pointer lifetime concern and four-file ownership split are valid. No source evidence shows `furnaceSetModel` escapes the pointer, and the two L3 probes have a clear same-position bool-callback mapping. The principal compile/correctness blocker is the underspecified test seam and lookup-count semantics: the named acceptance cases cannot be demonstrated by existing L2/L3 positive corpus tests, while the proposed architecture could accidentally introduce a lookup for explicit `sc` or remove the current nested furnace lookup. Resolve those specifications before calling the cut compileable/reviewable.
