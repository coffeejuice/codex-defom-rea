# CP281 smallest original-capable color entry observer design

## Decision and witness boundary

A fixed DR0 execution comparator on the owned primary thread can establish one positive 3D color-helper entry with existing Win32 primitives. This is source-ready as a bounded implementation design, not a released runner. Original execution remains HOLD until the implementation, harmless tests, loaded-image/fixture gates and independent neutrality/policy review pass. There was no original launch, debugger session, GUI input, Frida, REA access, clone preparation or build in this lane.

Select only `FUN_1411f26e0`, entered from the direct call at `0x1411f2482`. The claim is: in one fixed-command owned child, its primary thread reached the helper entry before its first instruction, with the selected caller return and the recorded entry registers/frame/readable View state. No global order, uniqueness, overlap exclusion or other-thread absence is needed for that positive event. CP277 continues to block the full CP214/Open contract; its five-address schedule is not part of this contract. A miss, timeout or exit is **no qualified witness**, never evidence that the helper is unreachable. B98's effective color mode and reachability remain unknown.

The immutable target is original installation v11.0.2 `DEF_GUI_MO_64.exe`, retained file `evidence/original-binaries/DEF_GUI_MO_64.exe`, SHA-256 `fd8ae1f8dd50d068267b3b7e49efdf11eaa178889131e59ec4b6f8de64725acc`, 67,611,136 bytes, PE embedded version resource previously qualified null. Any mixed/unknown cause is not an owned hit. Capture raw context and reject unreadable/short reads explicitly.

For the proposed nonnull-object witness require that pointer nonzero; unreadable or changed samples are unqualified rather than filled with zero. These fields support a sampled View/object ABI interpretation qualified by the retained static call body, not a recovered object type or constructor provenance. Raw RSP and caller instruction support a frame-bound entry observation; the return word alone cannot prove the complete dynamic ancestry or exclude forged stack state. No fixed historical pointer or synthetic CP278 `RCX==VIEW` constant is admitted.

## Smallest state machine

Use a new disabled, fixed-target runner, leaving CP278 unchanged. No arbitrary PID, executable, address, CLI command or attach mode is accepted. Its sole future command is `[fixed installed EXE, '-m', 'open', '-f', canonical_code_unit_hex]`, cwd a separately reserved fresh B98 clone below `C:\PROBLEM`, full project paths under 100 characters. Do not reuse already-run `p214a`; retain its exact CP214 bytes only as historical reference. Bind the new clone's exact root, project, hex argument, manifests and reservation receipt into a frozen launch contract. CP280 clone validation does not itself establish freshness.

Use CreateProcessW with an explicit application path, correctly quoted mutable command line, `DEBUG_ONLY_THIS_PROCESS | CREATE_SUSPENDED`, noninherited handles, and the fixed cwd. Save returned handles immediately, duplicate a retained process handle, record PID/TID and creation FILETIME as a decimal **string**, and establish the independent watchdog before the one ResumeThread. The required host-supported sequence is: pre-resume process/handle/creation-identity checks and supervisor acknowledgement -> sole ResumeThread returning previous count 1 -> WaitForDebugEvent delivers CREATE_PROCESS_DEBUG_EVENT -> validate image/base/mapped bytes and save primary context -> DR0 write/readback while that event stops the process -> ContinueDebugEvent. Do not wait for CREATE_PROCESS before the sole resume, and do not claim DR0 was armed before resume. The creation event provides the supported stop before initial target user-mode execution; the observer arms there before continuing that event. The pre-resume checks use available creation handles and file identities, while event-derived image/base/thread and mapped-byte checks remain explicitly post-resume/pre-continuation. Do not substitute arbitrary sleep for startup readiness. All WaitForDebugEvent/ContinueDebugEvent calls occur on the creating debugger thread.

State progression is `created -> initial-event-validated -> armed-entry -> witnessed | no-witness | observer-error -> cleanup -> exited`. Save complete original DR0..DR3/DR6/DR7 and relevant flags. Refuse an occupied slot or unexplained debugger state rather than clearing another owner. Change only DR0, its L0/G0/RW0/LEN0 fields and owned DR6 status, preserving reserved and unrelated DR7 bits; require L0=1, G0=0, RW0=00 and LEN0=00 on each armed readback. Refuse preexisting L0 or G0 ownership instead of overwriting it. Validate all preserved bits as well as the owned fields. Never modify RIP, stack, View/object, executable bytes or arguments.

Keep DR0 at this entry until one selected hit or an endpoint. For an unselected caller, retain a bounded rejection count/sample, clear owned B0, set RF for one-instruction resumption, read back the permitted changes, and continue the owned exception as handled. The same comparator stays armed; no return handoff is needed. RF suppresses the immediately retriggering execution breakpoint; its suppression interval is explicitly recorded and cannot support absence claims. If a selected event fails required state reads, preserve the failed raw record and stop qualification. No second event overwrites the first selected record.

The first selected entry ends the scientific observation. Request intentional termination of that owned child while its event is held, continue that pending event with its correct disposition, and drain to EXIT_PROCESS. This entry-only design deliberately does not execute the helper after the witness, so it has no result or helper-side-effect claim. If termination fails, retain the held state and cleanup failure; never claim success just because entry was seen. Record `entryQualified` separately from `cleanupComplete` and overall capture success.

Only the primary thread is armed. CREATE_THREAD events are recorded and continued, with their handles tracked; they are not errors and do not receive DR0. Exceptions from them must use their own event thread context if context is needed. There is no coverage before the initial successful readback, during any explicitly disarmed interval, on other threads, or after the endpoint. Additional threads cannot invalidate an already qualified primary positive entry merely by existing. No late overlap poisoning, uniqueness counter, acceptance/current/activation observer, creator predicate or full CP214 schedule is imported.

## Exception and event disposition

CP278's synthetic policy of aborting every non-owned exception and rejecting post-marker threads is unsuitable for the original. Every delivered event has one ledger row before processing and exactly one successful continuation or a retained explicit continuation failure. A failed ContinueDebugEvent is not silently counted or retried indefinitely.

Handle nonexception events with DBG_CONTINUE after resource handling. The expected single startup loader breakpoint needs independent qualification: retain its first-chance address/module/bytes and startup phase; do not classify the first arbitrary INT3 as the loader breakpoint. Implementation may pin the OS ntdll breakpoint signature/address using the fixed harmless startup tests and same-host module identity. If that qualification cannot be established, record unknown, decline the witness and perform bounded owned cleanup. Only that qualified loader event and owned DR0 exceptions use DBG_CONTINUE. For other first-chance exceptions, including C++/Qt exceptions, unknown breakpoint and foreign single-step, record bounded raw exception metadata and forward DBG_EXCEPTION_NOT_HANDLED so target handlers run. Never swallow them as successful instrumentation. Unowned second-chance exceptions are also forwarded, mark the run incomplete, and permit normal OS termination/drain. A deliberate safety endpoint such as AV records the first-chance event and its forwarded disposition before owned termination; it is not a fabricated natural application failure. Do not read primary-thread registers and label them as another thread's exception context.

A 12-second monotonic observation deadline begins immediately before the sole ResumeThread; an independent nonresettable owner/watchdog deadline of at most 30 seconds covers setup and cleanup. Poll debug events with bounded waits (e.g. 100 ms), bound total events and receipt bytes separately, and never drop overflow silently. A bound firing yields no complete observation, preserving any earlier positive entry separately. Original DLL/thread volume needs a harmless high-event fixture; CP278's arbitrary 256-event cap is not evidence that this suffices for original startup.

## Ownership and cleanup receipts

Use retained process handles for termination and signaled-state checks, not process-name matching or a fresh PID-only kill. Bind creation FILETIME, image and command/cwd at creation; numerical JSON float equality is forbidden. The independent supervisor starts its nonresettable overall deadline **before launching the debugger worker or beginning setup**, and retains its own process handle and creation identity for that worker. The fixed worker first creates the suspended debug child with CreateProcessW(DEBUG_ONLY_THIS_PROCESS | CREATE_SUSPENDED), then calls and checks DebugSetProcessKillOnExit(TRUE) on that same, now-connected debugger thread before the sole ResumeThread. This API cannot establish the policy before a debug connection exists. Failure leaves resume disabled and enters owned cleanup; the child already exists and must remain in the ownership ledger. The creation-to-explicit-call interval relies on the documented default TRUE debugger-exit behavior, which must be explicitly retained and tested rather than described as an explicit-call guarantee. Include a harmless worker-crash/hang injection immediately after CreateProcess and before this call, with the supervisor deadline and worker handle already established; verify child exit independently or retain the outcome as unknown. Before child resume, the supervisor must also hold a duplicated owned-child process handle, acknowledge it over a bounded channel, and bind its creation identity. A missing child-handle handshake keeps resume disabled. On timeout, the supervisor first requests bounded cooperative cleanup and, when it holds the child handle, requests termination of that exact child. If a pending debug event prevents child exit or the worker does not respond, the supervisor uses its retained **debugger-worker handle** to terminate only that worker within a second bounded cleanup interval, allowing the configured debugger-exit kill behavior to resolve a held child. This fallback is required also for a hang before child-handle acknowledgement: worker ownership and deadline already exist even though child ownership transfer is incomplete. Wait for worker exit and verify child exit using the supervisor child handle when available; otherwise retain the child identity/absence evidence obtainable from creation receipts and explicitly mark unknown if it cannot be independently established. No PID-only kill, broad process targeting or general-purpose arbitrary-PID service is admitted. The child-handle handshake, worker termination fallback and kill-on-exit behavior need harmless native validation; none is inferred from the design.

Ledger handle generations as well as values: PROCESS_INFORMATION handles, retained/watchdog duplicates, create-event process/thread handles, later thread handles, image and DLL hFile values. Manually close each nonnull image/DLL hFile on its event. ContinueDebugEvent has documented closure behavior for debugger event thread/process handles on exit; record that successful continuation before marking those rows closed, and do not blindly double-close them. Distinguish duplicate/aliased values by actual ownership and test the observed Windows behavior. Manually close owned PROCESS_INFORMATION and duplicate handles once each. Tests must cover numeric handle reuse and prove no unrelated handle can be closed.

On normal endpoint or a responsive error path, retain pending-event metadata/disposition, terminate only the retained owned child if needed, continue/drain pending events through EXIT_PROCESS, wait for the retained process to signal, record actual exit code, then close manual handles. If the supervisor must terminate a stuck worker, any event lacking a successful ContinueDebugEvent receipt is recorded as **abandoned by debugger-worker termination**, never as continued; the lost continuation and worker-local cleanup remain incomplete even if OS teardown and independent child exit succeed. The supervisor's handle closures and OS teardown are separate from worker ledger closure. Preserve the last delivered event, attempted disposition, continuation outcome and worker-termination receipt. Deadline or cleanup timeout cannot be converted into absence. Require an independent image/creation-aware Windows process query or successful PID absence query; access denied/query failure/reused PID is not absence. Do not kill a reused PID. `DEBUG_ONLY_THIS_PROCESS` makes no descendant coverage claim. Report child exit separately from debugger worker exit and supervisor exit. Preserve source-before/after and clone-before/after full manifests, and all unknown/partial actions. Termination is not application Close. Logical ledger closure is not OS invalid-handle proof; CP278 explicitly leaves that stronger test false.

No GUI-control API is used. Debugger cleanup, process exit and JS reset cannot serve as GUI-control release. The separate root GUI release gate remains unchanged.

## Optional separately reviewed continuation pair

Defer this from the first implementation. A one-slot handoff after a selected entry could preserve immutable `(PID, creation string, TID, S, V, dynamic return PC)` and arm DR0 at B+`0x11f2487`. A hit must match the same TID and RSP=S+8; RCX/RDX/RAX at continuation are volatile and must not be compared with the entry View or treated as success. Mismatched return hits must not overwrite the selected entry. Thread exit, timeout, unwind or unreadable context makes the pair incomplete. Record the entry-disarmed interval explicitly: nested/repeated helper entries and other-thread activity can be missed. It cannot prove overlap absence.

Even the matching continuation/frame pair should be named a **paired caller-continuation witness**, not proof that a RET transferred normally from the helper. To claim that transfer, separately qualify the actual ret site and stack frame, or an equivalent branch-trace/single-step mechanism with its own tests and neutrality review. An execution comparator at the continuation alone does not distinguish RET from another transfer to the same PC. Do not enlarge the first entry observer to obtain that stronger claim incidentally.

## Neutrality assessment and prerequisites

Hardware DR execution observation avoids executable-byte patches, injected libraries, relocated prologues, code-page permission changes and target data writes. That supports a smaller perturbation surface than an injected callback; it does **not** prove neutrality. Debug creation sets debugger-visible state, the loader breakpoint is handled, all process threads stop on debug events, DR/RF context changes are observable, and timing/exception behavior can change. Entry-plus-termination supplies only an instrumented occurrence, never an uninstrumented completion result. No claim about palette values, graphics effects, binder continuation or complete Open follows from the hit or the historical Lubricants delta.

Before original review, implement and freeze these harmless tests with the same event loop/ABI/ledger code intended for the original:

1. A fixed native synthetic CALL with matching prefix/RCX object sample; verify primary-thread entry RIP/S/return and no target-code write, plus exact DR readback and the one startup resume. Wrong caller, wrong bytes/base, short read and changed pointer sample must fail qualification without inventing values.
2. Benign **handled** first-chance exception before the call; forward NOT_HANDLED and verify the target handler reaches the entry. Also exercise an unhandled second-chance path and a target-generated INT3 distinct from startup; receipt proves each disposition. CP278's unhandled RaiseException cleanup case is insufficient.
3. Additional startup/late threads and an entry executed only on a worker; primary-only scope yields no witness for worker-only, retains threads/handles, and cleans up. Repeated primary calls with an initially wrong caller verify RF permits progress without a retrigger loop. A nested call test makes no overlap-absence claim.
4. A high-volume bounded DLL/debug-string/thread-event run, event cap/receipt cap, entry-readback failure, continuation failure, watchdog timeout, debugger crash/hang, supervisor handshake failure, natural pre-entry exit and intentional endpoint. Inject hangs separately before child-handle acknowledgement, while holding the selected entry exception, and while holding EXIT_PROCESS_DEBUG_EVENT. For each, prove the supervisor deadline predates setup, its worker handle remains owned, the bounded worker-termination fallback exits, and any uncontinued event is labeled abandoned rather than continued; verify child exit independently where possible and retain unknowns otherwise. Check exact pending-event disposition, signaled owned exit, creation-bound independent absence, handle generation ledger and worker/supervisor exits for each.
5. Startup loader breakpoint qualification on this host and exact child creation/ResumeThread/ContinueDebugEvent sequence. Check seeded occupied DR state refuses at the delivered creation event before its target continuation; it cannot be described as a pre-ResumeThread refusal. OS-invalid-handle confirmation is separately bounded and never conflated with ledger completion.
6. Independent static receipt review: fresh reservation/manifest/command gate, pinned PE plus entry-prefix/mapped-byte gates, current dependency identities, source/observer hashes, actual bounded launch artifact with guards disabled, and policy/neutrality review. No repeated original control run is prescribed to mask missing implementation evidence.
