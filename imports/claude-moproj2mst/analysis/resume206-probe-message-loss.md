## Failure modes, ranked

In the [CP206 injected source](resume206-original-null-owner-2026-10-26T09-46-02-454Z/null-owner-observers.js), the handler sets `first=false`, computes an accurate backtrace, and **then sends counters and the full AV as separate messages** (lines 70–82). Because the counters arrived, the backtrace call and mapping had already returned on this callback. The most plausible gap is between the two sends: Frida documents `send()` as asynchronous, and the callback returns `false`, allowing the original exception to terminate the process. The agent or transport may disappear before the second queued message reaches Node. This is a plausible timing explanation, not proof that the second `send()` was called.

The second payload also evaluates `describe()` three times, collects registers and memory metadata, and serializes a larger object. An exception during construction or serialization is possible. The source catches JavaScript errors and attempts an `exception-handler-error` send, but that message would face the same asynchronous delivery/teardown window; its absence does not rule out a local callback error. A Frida internal fault or other abrupt callback termination is likewise unobserved. Host-side filtering is less likely: the callback stores every received message before its kind-specific branches, its 96-message cap was not reached, and there was no script error. Neither summary nor runner logs provide a send completion or delivery acknowledgment, so the exact mechanism is unresolved. [Frida's JavaScript API](https://frida.re/docs/javascript-api/) describes asynchronous `send()` and says returning anything other than `true` forwards an exception to the application or OS.

## Smallest safe capture change for a future separately authorized run

In `admin/original_null_owner_probe.mjs`'s generated exception handler (currently lines 157–177), make the **first** send in the first-AV branch one compact `first-av-core` message. Construct it before backtrace, symbol lookup, or the full register walk. Include `pid`, process creation identity, exception type, `details.address`, `context.rip || context.pc`, `context.rcx`, `details.memory` operation/address, a guarded RIP module identity (`name`, `path`, `base`, `offset` when lookup succeeds), and **snapshots** of `sequence`, `counts`, and `overflow` in that same payload. Copy the count maps (`{ ...counts }`, `{ ...overflow }`) when constructing it. Keep the existing full AV message as optional enrichment after the core send; keep `return false` and all hooks passive. Do not block for a host acknowledgment, sleep, alter context, or change application data to improve delivery.

One message makes the essential RIP/RCX/module/counters one transport unit and removes the present two-message split. A guarded module lookup must degrade to `module:null` plus an error string if it throws, so it cannot suppress the raw RIP/RCX receipt. If the compact message is delivered, the host should retain it immediately as a separate `firstAvCore` record. Update qualification so the core receipt answers only the minimal first-AV question; `CAPTURE_COMPLETE` still requires the existing full record, qualified hook evidence, natural cleanup, process absence, and unchanged fixture. This change reduces the loss window but cannot guarantee delivery when the target exits; an acknowledgment would require a separate timing/behavior review.
