# CP201: passive owned-process trace feasibility

## Finding

A bounded passive trace of the original process is **technically supported without CUA or app-control acquisition**, using the REA Frida spawn/instrumentation lane already represented by prior receipts. It is not a supported way to complete Open → Save → Close: the currently established hypothesis reaches only a conditional auto-save, while no non-GUI accepted-Close producer has been identified. This audit did not launch, attach to, or instrument a process.

The GUI-control gate remains `unsupported_release_api` in `analysis/gui-control-lifecycle-assessment.json`; `python tools/gui_validation_status.py` reports the existing external-validation work queue/blocker. That gate blocks GUI sessions. The prior Frida receipts explicitly distinguish their owned-process observations from GUI control (`gui_control_acquired: false`), so a passive REA spawn trace is a separate lane, not a way to bypass the requirement for GUI interaction. The only CLI available in this shell inventory is Python; no local `windbg`, `cdb`, `procdump`, or `frida` executable was found. The REA tools do expose `start_frida_session`, `resume_frida_session`, `instrument_with_frida`, `close_frida_session`, and process discovery/absence tools.

## Evidence and qualifications

- `resume173-headless-oracle-next.md` identifies the exact unresolved Save edge: observe original `0x1400154a4`'s requested visibility bool, Qt `0x6539ffa0` event type, Qt `0x653a0084` emitted bool, original `0x14003a990` entry, `0x14003aa81` busy result, and `0x14003aaa2` auto-save call. This would establish occurrence on the chosen disposable project, not successful Save by itself and not Close.
- `resume172-headless-oracle-next.md` qualifies the native CLI project as process type 5, making the direct caller at `0x1400155ec` unreachable for B98. The signal route remains conditional on actual Show delivery, connection, dock position and unbusy state. The accepted Close routes require QAction method 20 or a delivered window close event; neither has an input-free startup producer established.
- The original is identified in those reports as `DEF_GUI_MO_64.exe` v11.0.2, SHA-256 `fd8ae1f8dd50d068267b3b7e49efdf11eaa178889131e59ec4b6f8de64725acc`; retained QtGui hash is `c360c971d292a3c84fc59b8e38733a85a111243f1dbc44737d87b6d744725887`. These qualify the reviewed evidence, not a claim about a currently installed image.
- Prior owned-process receipts show the mechanics exist: `wave3-original-editor-probe-004-receipt.json` records an original CLI Open prefix, exact owned PID, module hashes, paused observation endpoint, exact-PID termination, and independently verified absence. It also explicitly says no GUI input, Qt calls, event pump, or target-memory assignment occurred; it did not reach Save/Close. `wave3-original-grid-probe-receipt.json` similarly records root-owned PID termination, process absence, Frida session closure, and `gui_control_acquired: false`. These are precedents, not authorization or proof that the proposed trace has been run.
- The existing `oracle_b/launch.py` starts the installed executable with caller-selected cwd and arguments, detached/new process-group flags, and prints a PID. `oracle_b/run.py` instead performs interactive menu actions and must not be used for this passive trace. The old launch helper does not itself provide safe ownership or cleanup receipts.

## Bounded method if separately scheduled

1. Prepare one disposable copy of the selected B98 project under a short, owned working directory; preserve the source fixture. Record before-state file names, sizes, timestamps, and hashes. Do not target the installed project or user settings.
2. Use REA `start_frida_session` in **spawn** mode for the verified original executable with argv `-m open -f <disposable-project>` and that copy's directory as cwd. Record the returned exact PID, session identity, executable path/hash, and loaded module paths/hashes. Do not enumerate/attach to an unrelated running DEFORM process.
3. While the spawned target is paused, load a narrowly scoped Frida script with entry/return hooks at the six addresses listed above. Since the application and Qt modules have different bases, resolve each address against the receipt-confirmed module base; do not assume a fixed ASLR base. The script should only record arguments, return values, thread/order, and timestamps, then allow execution. It must not synthesize input, call Qt APIs, alter target state, or modify control-flow/data. Resume once and stop at a finite endpoint after the relevant startup interval. If any address/module mismatch, hook error, unexpected dialog, or timeout occurs, preserve the partial/error receipt and do not broaden the probe.
4. Capture the target's bounded observations and the disposable directory's after-state hashes. Report requested visibility, event delivery, emitted bool, slot entry, busy result and save call independently. A call at `0x14003aaa2` proves only that the save path was entered; compare actual outputs to establish writes. Missing events or a failed launch remain inconclusive.
5. Cleanup belongs only to the spawned exact PID and its Frida session: stop instrumentation, terminate that owned PID through the supported REA lifecycle, independently verify that PID is absent, close the session, and retain the cleanup/absence receipts. Do not kill by image name, close windows, or use process exit as accepted Close evidence. Do not report app control released based on JS reset, debugger detach, target exit, or session close.

## Decision

**Feasible as a passive owned-process Save-path discriminator, subject to using the supported REA Frida session lifecycle and explicit exact-PID cleanup receipts. Not sufficient for the full oracle.** The static Close audit remains an independent blocker: process termination or `QApplication::exec` return cannot stand in for accepted FileCloseAll/Close. This file records feasibility only; no process or probe was started and no source, build, fixture, installed file, or REA session was changed.
