## Two historical conclusions that must not remain blockers/contracts

**The normal Geometry manager vtable is already source-qualified.** CP107's receiver/vtable notes say no concrete manager/callee/destructor can be named from the immediate reader callsite. That is true of an arbitrary unknown caller, but it omits already-retained CP91/93 qualification for this selected normal Study branch: constructor0x1400d1180 installs SfMoDoeManager vtable0x1421671b8; +0x178=0x1400d7f00 and +0x1a0=0x14091b950. Destructor0x140919cb0 ->0x14091db70 ->0x1408169d0 and geometry cleanup0x140817d10 were independently captured. The current HeaderVariableRecord concrete owner models that recovered branch. Do not repeat generic vtable discovery as its earliest dependency, or use this qualification to admit arbitrary dynamic manager types.

CP105/106/107 captures of Geometry record append/correspondence can be reconciled against those owners once the earlier actual filename/QString/QFileInfo boundary closes. The current lack of a path/private/file-engine occurrence remains real; CP105 value context is not native owner parity. No geometry import is released by correcting the historical vtable omission.

**Refresh-time manager equality is not a native continuation precondition.** `resume101-doe-refresh-runtime-witness.md` asks a receipt to verify equality between refreshed table manager and Save's original cached manager. CP105 and CP108 correctly state that these are independently selected values and can differ. Native continuation reuses the cached Save manager; it does not branch on equality with the refreshed current manager. A future adapter must preserve both identities and the cached manager's liveness, without reselecting the active SUB or inventing an equality guard. Owner-loss refusal remains a separately stated reconstruction boundary, not evidence of safe native behavior after arbitrary deletion.

These corrections are recorded here without rewriting historical reports or frozen receipts.
