# CP282 conditional 3D color backend method

The immutable original `DEF_GUI_MO_64.exe` v11.0.2 SHA-256 `fd8ae1f8dd50d068267b3b7e49efdf11eaa178889131e59ec4b6f8de64725acc` has distinct 3D callback slots. `0x14122fb50` reaches `0x141237d00`, whose backend virtual slot is +0x78; paired `0x141237c70` uses +0x98. The +0x78 wrapper asks `0x141233dc0(this,0)` for an existing backend pointer at subobject+0x2f0. Null returns without that virtual call; the zero argument does not create the backend.

A separate creation path `0x141233dc0(...,1)` allocates 0x240 bytes and calls constructor `0x141254bb0`, which writes vptr `0x142d19028`. Bounded vtable bytes and retained `vtables.tsv` bind +0x78 conditionally to `0x1412a7340`. Bounded disassembly of that method converts three integer channels to floats, divides by constant `0x1421ebb18`, writes floats at backend+0x10/+0x14/+0x18, sets byte backend+8 to 1, then invokes another virtual slot +0xf8. The latter target/effect was not bound at CP282; CP283 subsequently mapped this vtable's +0xf8 slot to a stack-home spill and RET in analysis/resume283-color-3d-f8-leaf.md.

This is a conditional concrete receiver contract, not proof the ordinary 3D View has that backend at the callback. CP286 corrected the earlier `rep+0x458+0x2f0` wording: `0x14122fb50` adds +0x458 only for a color-member setter, then reloads the original rep before calling `0x141237d00`; the backend field is **rep+0x2f0**. That callback first returns when rep+0xf9 is nonzero. The constructor initializes rep+0xf9=1 and rep+0x2f0=null; only the zero-flag build arm can lazily allocate the backend. This correction leaves the backend stores conditional and the public color path on HOLD. See `analysis/resume286-color-ownership-and-3d-receiver.md` for the new bounded trace. Evidence: retained V/v8.c, V/v1.c, view_d3.c, view_d4.c, vtables.tsv and bounded DUMPBIN of `0x1411f3430`, `0x14122fb50`, `0x141237d00`, `0x1412a7340` and vtable data.
