# CP400 early CP333 primary-error trace

CP399's trace reached `cp333_before_offer_ack` and then `run-exception`, but the later exclusive child diagnostic was absent. CP333's existing exception handler retained its primary error in an in-memory receipt, then initiated containment cleanup. The parent could not read that child receipt after the failed outer claim.

CP333 now emits one failure-only marker before its receipt update and cleanup: `cp333_error:<exception type>:<sanitized message>`. The message is printable ASCII capped at 120 characters, and a marker-callback failure is swallowed so it cannot replace the primary error. CP349 accepts only a bounded type/name and printable message schema; the same 2048-byte and 40-record limits apply. Trace data remains diagnostic and cannot authorize acceptance. Injected tests verify marker emission before cleanup, the original chained exception, valid parsing and malformed rejection. `analysis/cp400-early-error-tests.log` records 634 passing CP3xx tests from both import roots.

Independent CP400 review found the marker occurs before containment cleanup, adds no process/handle operation, and cannot replace the original exception or select acceptance. It qualified that a missing marker remains inconclusive if the child stops or trace writing fails before completion. The previous CP399 occurrence is not repeatable. CP401 will first freeze source/bytecode and obtain a one-occurrence gate, then use at most one new monitored inert diagnostic to identify the primary OFFER/ACK failure. No native child, WORKER, original application or GUI ran during this integration. The public C++ converter candidate remains CP301.
