# CP287 node byte-vector copy-on-write and failure ordering

Read-only bounded DUMPBIN 14.44, PE import/export and exception-metadata inspection used immutable original `DEF_GUI_MO_64.exe` v11.0.2, SHA-256 `fd8ae1f8dd50d068267b3b7e49efdf11eaa178889131e59ec4b6f8de64725acc`, and copied `QtCore4_64.dll`, SHA-256 `bcf0074c7e9fba3bcafdaa38742931f309889cbdbacffbca32af83db237fc160`. No original process, GUI, Frida or mutable REA database was used.

The node vector's mutable accessor `0x141165ae0` compares its refcount to 1 and enters `0x141165b20` → `0x141165bc0` only when shared. The latter's reachable byte-vector path differs from generic template-looking code: constant-zero branches skip element destructor/construction/copy loops. Shared storage allocates `requestedCapacity+16` bytes at alignment 8; a direct copy moves `min(requestedCapacity,oldCapacity)+16` bytes, including the header and capacity bytes. Unique storage invokes Qt `QVectorData::reallocate`; success publishes its returned pointer at `0x141165e78`. The common path sets refcount/capacity/flags, zero-fills a new logical tail through Qt `qMemSet` and stores size. Shared publication comes after old deref/free at `0x14116610e`. The resolved EXE IAT entries identify Qt atomic compare/assignment/deref, QVector allocate/reallocate/free, qBadAlloc and qMemSet; the copied Qt wrappers ultimately use MSVCR90 allocation functions.

Failure ordering matters. Shared null allocation calls `qBadAlloc` before changing old storage/refcount/publication; it throws `std::bad_alloc`. EXE FuncInfo `0x142c44b40` protects unique reallocation `[0x141165dca,0x141165e9b)` with a typed bad_alloc catch. Catch funclet `0x141b3e900` rethrows on requested growth but suppresses a failed shrink and resumes using the old buffer. A separate catch-all for generic copy code is on a constant-zero unreachable branch here. It does not prove rollback for reachable zero-fill or publication. Assuming a valid vector and no concurrent mutation, shared allocation failure during node fill occurs on the first accessor before its byte-1 write; successful detach makes later accesses unique. It cannot by itself explain an arbitrary newly written prefix. External invalid-size, CRT-internal and OS-fault behavior remains unqualified because no immutable MSVCR90.dll copy was retained.

This closes much of the vector helper contract but does **not** establish fresh View node-vector initialization/partial-unbind state or an ordinary positive-node caller that passes preceding color/Slice effects.
