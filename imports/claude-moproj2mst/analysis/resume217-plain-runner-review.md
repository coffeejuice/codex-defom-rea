## Required fixes

1. **Undefined receipt writer stops every enabled run before cloning** (lines 137, 142, 159, 166, 172). `writeJsonExclusive` is neither declared nor imported. Once the guard is enabled and preflight passes, the runner creates its output directory and throws `ReferenceError` at the first receipt write. Implement an exclusive JSON writer, then exercise the complete enabled orchestration against injected harmless dependencies. Syntax checking and the existing self-test cannot detect this defect.

2. **Process error and close handling can lose the cleanup evidence** (lines 143–156). There is no child `error` listener or stdin `error` listener. Python launch failure can therefore raise an unhandled process error, and a resume/terminate write racing a closed pipe can raise an unhandled `EPIPE`; the local `try/catch` does not catch asynchronous emitter errors. The `close` listener is registered only after the protocol waits. A helper that exits before `created` or `resumed` is accepted can close during those waits; the later listener misses that close and returns a false 30-second timeout. Register a single close/error completion promise immediately after spawn, retain its outcome, stop waits when it settles, capture stream errors, and put stdin EOF plus bounded helper completion/receipt persistence in a `finally` path. Keep unknown cleanup outcomes as failures and do not start the next case.

3. **The negative clone manifest check can accept missing trailing entries** (lines 100–102). It compares only `actual` entries by array index. If a trailing baseline file/directory is absent, that entry is never examined; the expected `Gear_blank.moproj` change can still be the sole reported difference. Require equal entry counts and identical keyed path/kind sets, then allow exactly the project file's expected size/hash change. Explicitly compare the clone's project bytes or digest with `pf.variant.bytes`, and the control with `pf.sourceBytes`, before launch.

4. **Recorded immutability evidence does not control progression** (lines 77–79, 162–168). The helper hash is checked once before both cases; source, executable, and helper snapshots after each case are written but never compared with baseline. A changed helper can therefore be used for the second case, and a changed source can invalidate comparability without a dedicated failure. Recheck the helper and executable immediately before each launch, compare the source manifest and executable/helper hashes after each case, and fail with preserved receipts before the next case on any mismatch. The helper's own executable hash check is useful, but does not pin the helper script itself.

5. **Clone containment is lexical and covers only the root length** (lines 71–85). `path.resolve` plus a `c:\\problem\\` prefix does not reject a junction/reparse ancestor of the destination, and inventory checks children rather than the root and its ancestors. The root-length check also does not check generated descendant paths. Validate the physical destination ancestry before copying, reserve fresh clone roots exclusively, reject reparse roots/ancestors, and check all copied/generated project paths remain below 100 characters. The fixed short root names reduce length risk but do not establish these conditions.
