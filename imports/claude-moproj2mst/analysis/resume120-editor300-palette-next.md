## Control enablement is a later owner dependency

The complete static conditional branch remains CP114's `setEnabled(false)` with actual disabled bit1. It first processes raw attribute32; raw32 false becomes true in private+1c8 bit0, then the already-disabled helper returns without child/focus/platform/event work. Raw32 true takes the equality path. Changing disabled-bit0, enabling true, or unknown current fields requires later effects.

`SetupControlState::requestedEnabled` is a requested setter argument. Its optional enabled is only resolved for the explicit stopping parent-tree profile. Neither is a WidgetState/private/QWidgetData owner or an observation of physical raw32 and disabled bits. The UI+offset/name tables, internal toggled routes, and CP119 Spring page's pageChecked/recordFlagChecked also do not create actual QWidget receivers. In the actual Session, setup UI allocation and first grid/control construction have not been reached. Therefore there is no sound place to invoke the conditional enable branch merely because OPI is now guarded.

The minimal enable admission would require one actual setup-created same-runtime receiver, UI slot generation and native widget/private/data relation, plus the exact bool occurrence, disabled bit and raw32 bit at that occurrence. A receiver with already-disabled/raw32-clear state could then commit the raw32 store and return. Unknown state must retain a guard; a projected requested false must not be used as the disabled bit. This is after the selected palette/font/thread/counter/setup predecessors, not a parallel shortcut around them.
