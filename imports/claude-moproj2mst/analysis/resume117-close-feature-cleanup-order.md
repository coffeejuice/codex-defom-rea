## Context global owner and deallocation follow Project ordering

After all accepted feature release, native Project destructor performs diagram-null binding, SubProject clear, then context destruction at08a412. That is later than the per-feature node erase/provider-delete phase. The context's optional C+1450 operation uses **process-global owner0x1446efe90**, not Session's notification state, main/global-main owner, ModelManager or remesh state. Missing global/provider/field provenance guards before that operation; constructor-null must not be reused after intervening registration/callbacks without a write history.

Normal context destruction orders: optional global12f51b0(low32(field))→free full field→null store; tree node clearing without key/provider deletion; sentinel free; only then map head/size zero; proxy free with no proxy-slot null store. Only afterward do later Project members/base finish and deleting destructor free Project. Mo+19c0 nulling follows that return; five model-slot deletion and eventual manager current clear are later still. No C+1498, PST byte, process remesh, pending Session event, global-main or whole-application reset is implied.

EH must preserve its separate cursor: provider-construction failure has its raw-allocation cleanup; later registration tail has no such local action; Project member unwind can invoke C destruction even before the normal08a412 call; optional C+1450 phase unwind invokes full map destruction; map destruction's active state uses proxy-only cleanup. A single “cleanup complete” Boolean, resetting all fields in a catch, or calling full map clear again would lose these distinctions. Do not implement these callbacks in the existing noexcept adapter destructors or claim that an adapter error entered native accepted Close. Default terminal remesh has no return/unwind to this path at all.
