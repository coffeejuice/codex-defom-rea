# CP187 R300 `saveBcc` plan review

**Decision: pass, with one fixture acceptance condition.** The proposed change is a narrow lexical-lifetime closure and is consistent with the frozen source and retained native evidence. The focused fixture must reach `saveBcc` directly (or otherwise isolate its effects); the public save oracle alone does not prove this helper's filters or detached-step behavior.

## Review findings

- **Borrow scope and ordering:** Current `saveBcc` in `source/apps/moproj2mst/src/engine/save_current.cpp` does the stated order: slot entry/`defineBCC`/type-5 filter, model lookup and step-null check, engine object and mesh checks, then `step = m->step.get()` and the two writes. Acquiring the step only after the existing model/object/mesh checks, then putting both synchronous `captureKey` calls inside a small callback, preserves that order and confines the borrowed alias to the callback. `captureKey` invokes its writer synchronously, so neither writer callback outlives that scope. Do not move the model lookup or object checks into a different ordering relative to acquisition.
- **BCC effects:** The source emits `RzElmCon` then `BccDef`, passes `s + 1` to each writer and uses `slotKey(..., s)` for the corresponding numbered paths. It ignores both writer return values and proceeds slot-by-slot. Keeping two independent `captureKey` calls preserves that behavior; `captureKey` records a file if the writer created one and removes its scratch file, while this helper adds no deletes. The plan correctly avoids introducing aggregate Save guards or new geometry/Stopping behavior.
- **Native annotations:** `spec.md` §§1–2 and the ledger qualify the entry filter, output names/order, writer twins, and writer-body accessors. The writer rows specify banner-first serialization and the `obj kind != 7 && has mesh` condition; the BCC writer returns its body status, while the RzElmCon body returns 0 on the admitted path. The note also records native open-failure behavior and the native return-3 handle leak, with the port closing the file after equivalent bytes. Since `saveBcc` prechecks mesh presence and the writers repeat the kind/mesh guard, no extra failure branch or output is implied for admitted calls. This supports the plan's limited claims, not native byte equivalence for this fixture or complete error-path parity.
- **Fixture and ownership:** `tests/s/test_save_current.cpp` already has copied-corpus open/activate/load setup and detached-step RAII examples that restore the original `unique_ptr`. Reuse that pattern in an isolated discarded project; preserve and assert model and step identity after restoration, and invoke no unrelated helper while detached. A corpus case is suitable only if it actually has a type-5 `defineBCC` slot and a loaded meshed engine object at that slot. Otherwise the plan's minimal valid synthetic slot/object/mesh construction is necessary. Assert ordered target paths, nonempty bytes, and zero deletes; exercise a filter-rejected case and null-step case only with the stated restoration guard. Keep scratch/missing-file probes under `M2M_TEST_SCRATCH` per the subtree instructions.

## Acceptance condition

Before implementation, identify the exact corpus case and slot satisfying all four admitted predicates, or document the minimal valid synthetic setup and its constructors. The focused test should call the helper directly (adding a test-only forward declaration if needed); using only `saveProject`/`syncOperationFiles` can mix unrelated Save effects and does not establish the helper-local negative cases. Then root can run the focused target when authorized and retain the integrated source-stable regression/freeze chronology.

No source, tests, build outputs, GUI/app-control session, or REA database were changed for this review. Only this report was added.
