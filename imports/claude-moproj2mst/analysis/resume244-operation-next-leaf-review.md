# CP244 operation next leaf review — PASS

The proposed HeatTreat STEPDEF command preserves the existing property/native effect order in valid synchronous states. No blocking defects found. This is design review only; no implementation or runtime result is certified.

The current `withOwnerSimCtl` checks owner/project, resolves `engine::opModel` exactly once, then calls `simCtl()` when a model exists. Both STEPDEF callbacks write only when control is nonnull. The proposed reference-taking helper preserves the lookup before reading the selected block's integer: opModel may install slots, call classModel, set current and lazily create the model. Passing a copied selection before lookup would lose that order; the proposed helper does not do so.

The command's use of simCtl() preserves its geometry guard before nullable step/control resolution. Missing step remains a guarded no-op, rather than the unchecked precondition of the dimension setter. The mapping `selection == 0 ? 1 : 3` preserves zero and all nonzero inputs, including negative/arbitrary values. It touches no other native word, default, identity or viewer state and requires no new return status or noexcept promise.

The proposed helper reads the ordinary block integer after model lookup but immediately before the command's guard, whereas the old callback read it after that guard and only for nonnull control. The report identifies this distinction explicitly. Current requireGeometrySyncAvailable() only tests the private barrier and throws; it has no callback or block mutation. The moved scalar read has no observable side effect in the supported valid synchronous state. Guard failure still leaves the setter's earlier block assignment retained, native storage untouched, and getter output unassigned. Future guard callbacks/block mutation would require re-audit, as the design states.

Both dispatches are covered: applyValue retains pv::toInt/store before synchronization; getValue retains its intentionally effectful property-to-native write before pv::vInt/output assignment. No read-only getter replacement or native-to-property direction change is proposed. Missing owner/project or null provider preserves the same output/property effects without native mutation. The Mode callback machinery and its separate defaults/refresh behavior remain unchanged.

The existing L6 test actually exercises STEPDEF setter zero/nonzero mapping, getter native effect and returned Variant, plus null-step behavior with a saved native sentinel and restoration on normal and exceptional paths. Its copied-corpus/internal fixture scope is correctly qualified. A negative getter extension is meaningful but optional. The proposed one-line direct command refusal in the established viewer barrier fixture verifies admission/no native mutation; the report correctly avoids claiming that this proves the property setter's pre-guard store dynamically. The focused L6/viewer group and normal property/full regression are proportionate. Existing Testkit entry points, macros and includes suffice; no external file probe or GUI is required.

The quoted original setter/getter addresses match source annotations and props_rest_ledger.tsv. The separate `source/docs/re/moproj2mst/owners.tsv` contains both entries; the source header identifies retained hta.c/htla.c/tpla.c decompile provenance. These records support historical static/ported-source attribution, not a fresh original execution or independent rederivation of complete bodies. The report preserves this limitation and identifies the new owner method as a reconstruction boundary.
