# CP390 CP334 adoption-stage integration

The CP389 trace ends after CP347's `before_cp334_from_bootstrap_argv` marker. CP334 parses four fixed argv fields, constructs a `NativeRunnerClientPipe`, retains exactly two inherited handles, and queries a clock, handle flags and pipe information for each before returning. The trace did not distinguish these calls.

CP334 now accepts an optional diagnostic stage callback. Its actual CP347 caller supplies CP347's sticky `_mark` callback, which forwards to the bounded CP349 child trace. CP334 emits ordered markers after argv parse and owner construction; before and after `GetTickCount64`, `GetHandleInformation` and `GetNamedPipeInfo` for each handle; and around the final clock check. Ordinals identify handles without writing raw handle values to the trace. CP334 retains both handles before any adoption mark/native query; its original `_hold()` and `.owner` exception custody remain in place. The CP349 parser accepts only those new names and still bounds raw bytes to 2048 and records to 40. It reports recorded order but does not certify a valid whole-run sequence.

Injected tests verify full marker order, a first-handle `GetNamedPipeInfo` failure retaining both handles for cleanup, and parser acceptance of the complete known success sequence. `analysis/cp390-adoption-stage-tests.log` records 628 passing CP3xx tests from each import root. Independent CP390 read-only review found no concrete ownership or fail-closed defect; it cautioned that durable per-marker `fsync` calls can consume the five-second adoption deadline. A disposable local 21-write/flush/fsync sample took 8.192 ms. That one sample is not an upper bound and does not prove that a future missing post-marker means the native call itself blocked.

No native child, WORKER, original application or GUI was run during CP390 integration. The next executable action is a clean source/bytecode freeze and independent gate for at most one new monitored inert diagnostic. The fifth CP389 occurrence must not be repeated. Public C++ converter candidate CP301 and its guards remain unchanged.
