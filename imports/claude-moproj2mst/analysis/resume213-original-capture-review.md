## Why the completion flags are false

The runner records `helperStdinError={name:"Error",message:"write after end"}`. At its outer-return endpoint (`admin/original_encoded_open_frida_probe.mjs:615-616`), it writes terminate and calls `helper.stdin.end()`. In `finally` (`:621-624`), the guard checks only `!helper.stdin.destroyed`; an ended stream can remain not destroyed, so it writes terminate and ends again. The `sendCommand` helper (`:469`) makes the same insufficient destroyed-only check. The retained raw helper stream has one terminate endpoint, not a second accepted command. The exact asynchronous error therefore fits the second write-after-end path. This is a source-supported causal inference, not a claim of an observed JS stack trace.

`cleanupComplete()` (`:431-432`, also host include `:59-60`) requires `helperStdinError == null` in addition to the successful exit/absence/retention checks. `completionPrerequisites()` then requires `cleanupComplete()`, so `completionPrerequisitesMet`, `cleanupComplete`, and `captureComplete` all become false. `outcome=INCOMPLETE` and `causalClassification=incomplete` follow mechanically (`:677-684`), overwriting the tentative indeterminate causal label. The false flags are faithful to this strict transport predicate, but they should **not** be read as failed held-handle cleanup or a failed Open observation. Conversely, the observed process cleanup should not be used to relabel the immutable capture receipt as complete. `releaseBlocked` and `technicalStatus=HOLD_PENDING_INDEPENDENT_REVIEW` are hard-coded in finalization (`:670,:680`), so they do not establish an actual failed runtime gate; the prior independent technical release review was conditional and this is the required independent capture review.
