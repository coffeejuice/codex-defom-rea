# CP116 two-row Spring acceptance review

## Required no-edit Open→Save contract

Retained `FUN_1410dab40` evidence in `analysis/resume116-spring-multirow-parser.md` establishes a count-driven loop over `n` complete 0x40-byte rows, with flags in a parallel `n`-element array. For a bounded two-row profile, both complete records must be read in order and `SPRING2.INI` must be absent, which supplies flag zero for each. The page path must retain both item-owned rows; Open selects row zero after inserting all rows. Save first writes the currently selected row's visible controls back to that row, then snapshots every row in list order. Therefore unchanged Save should normalize only row zero through the Qt `g,6` display/parse roundtrip and preserve row one's values, IDs, and zero flag exactly.

The CP116 writer receipt `analysis/resume116-spring-count-two-writer.md` provides an exact candidate literal for a two-row all-zero-flag serialization. Its count is `2`, each row has the original per-row field ordering, separators are LF, every non-LF list element adds TAB, and the stream ends CRLF. The writer attempts `SPRING.INI` first and calls the existing readable-delete helper for `SPRING2.INI` afterward when all flags are zero, including if the primary write returned failure. A strict acceptance fixture should retain seed bytes, expected bytes, actual bytes, and their hashes independently; assert count/order, exact full output bytes, absent companion, and stable second Open→Save bytes. Do not count a helper-only reader success as page or lifecycle acceptance.

## Current boundaries and a fixture consistency issue

At the reviewed source snapshot, the page adapter still admits exactly one row: `fillExtra3DImpl` checks `springs.size() != 1` and `exactOneSpring`, while Apply checks `items.size() != 1`, that same exact one-row predicate, and hardcodes count `1` in its SPRING writer. Those are clear required implementation changes for a two-row page profile. Tests should keep the public/session qualification explicit and should exercise the real deferred combo-ID callback if they claim lifecycle integration.

There are two different second-row values in the retained CP116 artifacts: `resume116-spring-multirow-parser.md`'s seed fixture uses `(30, 2.5, 3.5, 40, [1,0,1])`, while `resume116-spring-count-two-writer.md`'s exact output example uses `(30, -2.25, 4, 40, [1,0,-1])`. Both are structurally complete all-zero-flag rows, but the current candidate native parser admits only the former exact seed spelling; it will not read the latter writer example or either row's tabbed writer spelling. Before asserting a roundtrip, choose one evidence-backed pair and make the reader's admitted seed and writer-normalized literals describe that same pair. The original reader is value-generic at the retained decompile level; the exact-byte whitelist is candidate admission narrowing, not an original value restriction.

The two-row fixture also needs the actual deferred combo lists to contain IDs 10/20 and 30/40. The page-only test overload may use explicitly fixture-qualified spans, but a lifecycle test must provide a model whose non-kind-7 objects actually yield those `+8` item-data IDs. No combo fallback or missing-ID behavior should be invented. Keep nonzero companion flags, present `SPRING2.INI`, partial rows, trailing fields, extra rows, allocator failure, and user row switching outside the profile.

## Discriminating tests

1. Native reader: exact count-two seed with two complete rows and absent companion returns two ordered records, each flag zero; count-one behavior stays intact. Guard count >2, present companion and malformed/partial/trailing variants without changing the file.
2. Page Fill: a supplied/deferred combo ID set containing both rows' object IDs admits the full ordered vector, checks page enabled, selects row zero, and initializes the visible fields/selected combo IDs from row zero. A missing ID in either combo refuses before any Save write.
3. Apply/writer: no edits; row zero receives the visible `g,6` roundtrip, row one remains byte/value-equivalent as an item payload, the primary bytes match an independent two-row literal, and flag-zero companion deletion follows the source order. Reopen/reapply must reproduce the same bytes.
4. If claiming Session integration: invoke the actual Open owner with a real model-backed ID list and verify the Extra3D page reaches its recorded completion boundary. This still does not make the public selected palette/Save complete; the public guard remains separate.

After the worker release and grouped build receipt, the one/two-row code matches the retained no-edit Save contract for the admitted values. Fill admits either exact row0 alone or exact ordered row0+row1, checks both IDs of every row in both combo item-data spans, and initializes current-row/visible controls from row0 (`simcontrol300_io.cpp:31-45,152-174`). Apply preflights current row zero and the exact unchanged ordered vector, copies all payloads, parses visible row0 fields back into that first copy only, and serializes the whole vector with dynamic count and per-row native list order (`simcontrol300_io.cpp:213-265`). The follow-up readable-delete of SPRING2 remains after the primary attempt (`:265-266`). Native reader admits exact seed and corrected normalized writer bytes for the same two records and absent companion, then parses both records in order with zero flags (`simcontrol300_native_io.cpp`, `readSprings`). The row1 mismatch identified in the pre-integration report is resolved: both accepted two-row spellings now use row1 `(30, 2.5, 3.5, 40, [1,0,1], 0)`.

The focused page test's positive case asserts initial row order, row0 selection/text, exact literal output, unchanged source item payloads, absent companion and second-cycle byte stability (`test_spring_page_io_roundtrip.cpp:231-254`). Additional cases cover primary-open denial followed by companion removal and exact event order (`:256-274`), plus missing ID, changed row selection/order/payload/text, partial rows and count-three refusal (`:276-299`). These are helper/page tests using explicitly supplied test ID arrays; the test header itself excludes C ABI/full Session/native GUI. Thus this implementation is not a public Save or native combo widget acceptance claim.

One source comment was stale at review time: `include/m2m/engine/simcontrol300_io.hpp:48` said “Bounded one-item QListWidget payload,” although `items` now admits the exact one-or-two-row profile. Root was notified to update it before final freeze. Root also identified the test comment that says only the byte spelling differs even though the second row's direction differs; that is a documentation correction, not a failed assertion or behavior issue. The CP116 build receipt reports source stable during grouped build and full suite 306/306; this review did not run a build or test.
