# CP180 connector batching review: five QtCore private zero stores

## Decision and scope

**A five-instruction batch is source-ready for one future checkpoint, conditional on CP179 passing its parent-owned focused, full-suite and freeze gates.** Start from its accepted `BeforePrivateZero10` frame at QtCore RVA `0x13120f`; model the five stores through RVA `0x131220`, end exclusive. Retain a distinct sparse state and cursor after each instruction, and run the established source-stable validation and freeze once for the batch. This is a static recommendation, not implementation or acceptance. As of this review, `analysis/takeover-state.json` still names CP178 as the latest build/check receipt, and no `resume179-dual-build.json` or `resume179-dual-tests.json` exists.

This choice avoids the first changed-memory read at `0x131224`. It also stops before the sixth zero store at `0x131220`, so the proposed batch is exactly five instructions. An implementation should not silently advance the public task/private backlink, QObject completion, TaskInfo, reference counts, task/cache maps or thread/counter work.

## Source identity and exact native sequence

The retained shipped `evidence/original-binaries/QtCore4_64.dll` has SHA-256 `bcf0074c7e9fba3bcafdaa38742931f309889cbdbacffbca32af83db237fc160` and preferred base `0x67000000`. Its `.text` RVA `0x1000` maps to raw `0x400`, so raw offset is RVA minus `0xc00` here. I checked the five bytestrings directly against the PE and against `analysis/resume163-connector-qobject-67131160.asm` (SHA-256 `006a86bf080b956ccfa0885cb2a20313a0c69a198648dd770ea93caf82527aad`). The full proposed byte interval `[0x13120f,0x131220)` is `48897b10897b2448897b38897b64897b60`, SHA-256 `a7de8449ab5859fce3867f62e28f3d4060546d70b30701092ad0f631e10a9144`.

The next instructions are `mov [rbx+28h],rdi` at `0x131220..0x131224`, then `mov eax,[rbx+20h]` at `0x131224..0x131227`, `and eax,0xfffffcf0` at `0x131227..0x13122c`, `or eax,0x60` at `0x13122c..0x13122f`, and `mov [rbx+20h],eax` at `0x13122f..0x131232`. The latter read/modify/write has an unknown input value and merits a separate contract. The initializer returns at `0x13123f`; only then does public QObject code reach its distinct task `+0x08` private-pointer publication at `0x131425` and private backlink at `0x131431` (retained `analysis/resume163-connector-qobject-671313d0.asm`).

There is **no branch, call, explicit throw or register write** between the proposed entry and `0x131220`. Earlier `0x131178` puts the private pointer in `RBX`, and `xor edi,edi` at `0x1311b5` clears `RDI`; CP178's qualified `EDX=0x40804` equal branch at `0x1311f7` skips the mismatch call at `0x131206`. CP179's accepted predecessor observes private `+0x08=0` and stops at `0x13120f`. On this selected non-null, equal-version path, `RBX` and `RDI` remain unchanged through the proposed batch. All five destinations lie inside the `0x88` allocation and do not overlap each other or the already observed `+0x08` store. Native access faults remain theoretically possible for invalid memory, but the retained model admits only the owned, valid private allocation; the dump does not establish any recoverable per-store exception behavior. No runtime occurrence is claimed. The disassembly covers a bounded unwind region, not all logical QObject constructor paths.

## Ownership, partial state and failure order

Current source `source/apps/moproj2mst/include/m2m/doe_task_runtime.hpp` keeps the private allocation as a unique sparse pointee, with optional zero observations and a `QObjectPrefix::Phase`. `source/apps/moproj2mst/src/doe/task_factory.cpp` uses `qualifyRetainedZeroPrefix` before CP179's write, then refuses at a deliberate `M2M_E_UNSUPPORTED` stop. That stop is a reconstruction boundary, not a native throw between adjacent stores. Collapsing five stores into one final state without intermediate representable states would lose the present partial-state diagnostic contract.

Keep the current Report ordinal and allocation-time private pointee identity, `0xc0` task / `0x88` private sizes, written address points, exact factory/root control-block and pointee association, first and second same-root QList binding with both commit markers, QString and QVector binding/markers, six prior private zeros plus `private08=0`, and module-qualified `{QtCore SHA-256, EDX 0x40804, load RVA 0x13140f, call RVA 0x131417}`. Preserve the three symbolic root reference deltas and optional baselines. Require QObject/base incomplete and both backlinks unavailable. Reject all malformed entry conditions **before the first new store**; do not repair a bad frame, infer absolute shared-null counts or execute the excluded mismatch fallthrough.

Represent new fields as `optional<uint64_t>` at `+0x10` and `+0x38`, and `optional<uint32_t>` at `+0x24`, `+0x64` and `+0x60`, all initially unknown. The phase/cursor must distinguish `0x131213`, `0x131216`, `0x13121a`, `0x13121d` and `0x131220`. Advance one store and one cursor together, in native order. For each prefix, only its listed fields are observed; later fields stay disengaged. A resumed prefix must validate its earlier zeros, later unknowns and unchanged ownership/provenance before its next write. An already observed next field, including zero, must refuse without mutation. A rejected later prefix retains prior zeros and its exact cursor. Terminal same-key and different-key reentry at `0x131220` must refuse without replay.

One ordinary native-profile continuation may run all five transitions and return the established unsupported stop at `0x131220`. For tests and retained diagnostic replay, provide a narrowly scoped internal store-budget/stop hook (or equivalent direct transition access) to stop after 1, 2, 3 or 4 stores; its default is five. The hook must not alter the public C ABI or introduce a native behavior claim. If the implementation cannot preserve those intermediate states and later-prefix refusal semantics, use a smaller batch or retain single-store checkpoints. Do not use a transaction that rolls back earlier accepted stores after a later refusal: that would erase the very partial state being preserved. Conversely, prevalidate the entire current prefix before each next write so host-side validation exceptions never leave a cursor ahead of its observed field.

## Measured gate cost available to avoid

The closest comparable completed receipts are CP176–178 dual-lane runs. Their build workflow command sums are 47.595, 48.124 and 48.251 seconds (mean **47.990 s**), including configure, focused preflight/tests and full build. The corresponding full-suite launcher receipts are 33.141, 33.109 and 33.469 seconds (mean **33.240 s**); raw CTest inside them is 16.296, 16.344 and 16.578 seconds. Their full build commands alone are 29.719, 29.828 and 29.812 seconds (mean **29.786 s**). These values come from `analysis/resume176/177/178-dual-build.json`, `resume176/177/178-dual-tests.json` and each tests receipt's `timing_receipt` JSON. All three reported 354 clean passes, six logged-gap suites, one diagnostic-difference suite, zero failed/skipped/incomplete/fixture changes; this is qualified regression, not fresh original parity.

Five single-instruction future checkpoints versus one five-instruction checkpoint would eliminate **four repeated gate sets**, provided those checkpoints would otherwise each require the same gate. At the measured CP176–178 mean, that is about **324.9 seconds of recorded build-workflow plus full-suite launcher command time** (`4 × (47.990 + 33.240)`). A narrower directly attributable lower bound for repeated full-build and full-suite stages is about **252.1 seconds** (`4 × (29.786 + 33.240)`); the balance includes configure and focused checks whose composition may change. These are projected avoided command durations, not measured future savings, elapsed end-to-end time, dual-lane critical path, reviewer time or token savings. The receipts do not measure new batch implementation/review cost, overlap with other lanes, or a serial baseline; measure those at the actual checkpoint before claiming a realized speedup.

## Qualification

This review read retained PE bytes, disassembly, current source, plan and timing receipts only. It made no source/build/test, shared recovery state, GUI-control, original-process or live mutable REA change. CP179 acceptance and any future batch acceptance remain with the owner. No GUI-control session was acquired.
