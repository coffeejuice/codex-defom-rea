## Proposed ownership boundary

Use a future 64-bit native runner calling documented `CreateProcessW` with the explicit original application path, `DEBUG_ONLY_THIS_PROCESS | CREATE_SUSPENDED`, CP264's encoded positive-ID B98 argv, and its exclusively reserved disposable fixture cwd. This establishes debugging at creation rather than attaching to a discovered PID. Do not call `DebugActiveProcess`, enable SeDebugPrivilege, enumerate candidates for attachment, inject an agent, use Frida, or control a window. Debugger operations stay within the newly created child. `DEBUG_ONLY_THIS_PROCESS` does not claim ownership or automatic tracing of descendants; an unexpected external helper must leave the run incomplete rather than trigger opportunistic attachment.

Before permitting child execution, retain `PROCESS_INFORMATION` process/thread handles, PID/TID, exact creation FILETIME as a decimal string, image path/hash, argv/cwd, bitness, token/session identity and loaded image base. Cross-check these against `CREATE_PROCESS_DEBUG_EVENT`. Duplicate a process handle for waiting after the debug-event handles are closed by Windows. Hash the executable through its opened image-file identity where possible, and compare memory prefixes and module layout against the frozen original. Any mismatch fails closed. Never use a PID alone as cleanup authority.

The creating debugger thread must own the event loop. A pending creation event and the explicit initial suspend count are different states: the runner must prove the single `ResumeThread` decrement and matching `ContinueDebugEvent` sequence on a benign surrogate, rather than assume either operation alone starts the child. Preserve the CP264 12-second observation deadline and 30-second total helper bound with finite event waits; record wall-clock pause overhead. No dialog response, synthetic application call, Save or Close action is permitted.

## Bounded observation design

Prefer hardware execution breakpoints and register/memory reads for the first prototype, avoiding executable-byte replacement. Four x64 debug-address registers impose a real scheduling limit. A narrow nested schedule can place outer entry, acceptance entry, creator entry and helper entry in four slots, replacing each entry with its observed return address while that span is active. This is a design hypothesis requiring proof against the retained call chronology. It does **not yet** accommodate every CP214 duplicate/factory/cast/Project/postOpen hook simultaneously. A reviewed staged schedule must retain all CP264 required predicates before a full CP264 success claim is possible; do not silently weaken the acceptance contract to make four slots fit. Software INT3 patching is a separate fallback requiring explicit patch/restore/race qualification, not an automatic escalation.

For the selected occurrence, use loaded-module base plus RVA, not absolute preferred VAs:

- Outer `0x1ca30` with expected caller return `0x1c94`; acceptance `0x8a9b0`; keep CP264 duplicate/factory/cast/Project checks in the eventual reviewed schedule.
- Creator `0x8c630`: entry RCX=P, entry RSP, caller return `0x511d0`, primary TID, occurrence serial and enclosing accepted-Open identity. Match its normal return and preserve raw return registers without calling RAX a success boolean.
- Helper `0x81afb0`: select only entry return address `0x8c77a` in the active creator, RCX=QString pointer and DL=1. Read a bounded QString using a separately verified layout and validate length, readable ranges, UTF-16 decoding and exact `C:\PROBLEM\p264a\Lubricants` path. Retain entry pointer/raw bytes as well as decoded text. Match normal helper return to the same TID, span and stack identity.

The retained disassembly directly confirms creator call at `0x1400511cb`, fifth helper call at `0x14008c775`, helper first instruction `88 54 24 10`, and creator first instruction `48 89 4c 24 08`. These establish static call/ABI facts, not runtime occurrence or instrumentation safety. Consult the entire retained source qualification before implementation.

Store registers RIP/RSP/RCX/RDX/R8/R9/RAX and debug-register state at each selected event. Keep the entry stack return slot and at most 16 validated unwind frames, using matching module unwind data rather than guessing an RBP chain. Unwind failure remains explicit and cannot satisfy an obligatory frame predicate. No arbitrary stack or heap dump is needed. Event caps should be fixed before execution (proposal: 4 active hardware slots, 128 selected records, 4,096 total debug events, 512 UTF-16 path units). Overflow, unexpected thread participation, nesting, multiple eligible occurrences, exceptions, modal stalls or deadlines produce an incomplete receipt. Use thread-created events only to maintain ownership and detect unsupported execution; a primary-thread-only hardware schedule cannot establish absence on other threads.

The handler needs independent proof of hardware breakpoint resume semantics, debug-register preservation, per-thread application, expected initial breakpoint handling and exception pass-through. Never swallow an unexpected application exception as a debugger event. No function returns, arguments, application data or branch decisions may be replaced. Only the documented debugger control state necessary to continue execution may change.

## Cleanup, provenance and neutrality

Keep debugger kill-on-exit enabled and verify the setting/API result in the runner; qualify abrupt debugger death on a harmless surrogate. Do not assume it covers the pre-debug creation race or descendants. A separately owned watchdog with duplicated exact-child handle is a possible additional safeguard, also requiring surrogate qualification. A Job Object kill-on-close design must be independently reviewed for child/job behavior and timing effects before adoption.

At the matched normal endpoint or any failure, stop further observation and terminate only the held owned child if it has not exited naturally, retaining CP264 cleanup code `0xe201`. Record natural-exit races, API results, exit code, EXIT_PROCESS event and its continuation, then bounded wait on the separately retained process handle. Close image/DLL file handles, owned process/thread/watchdog handles and output streams with explicit ownership accounting; Windows debug-event handles and duplicated handles have different closure rules. Verify exact PID+creation absence independently through Windows, with retained-handle signaled status as primary evidence against PID reuse. Frida absence is unnecessary for this distinct no-Frida route, but the receipt must explicitly record that no Frida device/session was created. Do not claim debugger detach or process termination releases GUI control. Unknown cleanup fails the cleanup predicate and never authorizes a broader process kill.

Freeze runner source/binary/runtime hashes, API architecture/layout checks, breakpoint schedule, prefix records, raw timestamped event JSONL, stderr/late errors and full argv. Preserve CP264's complete 27-file source fixture, before/source-after/output manifests and project digest `e769faf514b335d56ffbb22f2c76490d029f2714ada9b26a75496fbd62ade7fd`; reserve a fresh child clone under C:\PROBLEM and reject links/escapes and paths >=100 characters. CP264's `p264a` is only proposed, not verified available. New path selection requires regenerated encoded argv and independent round-trip proof. Hash retained receipts and capture the exact invocation separately. No prepared training-harness lifecycle receipt can be substituted.

Hardware breakpoints avoid code patches, but debugging is observable and pauses all target threads at events. Scheduling, timing, exception delivery, debugger detection, file sharing, worker behavior and modal paths may differ. A passing run establishes a same-occurrence trace under that instrumentation only. Neither a target hash match nor a surrogate cleanup pass proves neutrality. CP219's uninstrumented filesystem contrast supplies no comparable completed Open; it cannot certify neutrality for this run. Qualify neutrality only against a future comparable uninstrumented baseline with equivalent progress/output. Even a complete trace establishes the selected helper attempt; actual mkdir causation needs an OS or QDir return witness in that span. Save, accepted Close, negative-ID causation and full application parity stay unproven.

## ETW alternative and decision

The installed WPR FileIO profile supplies a plausible filesystem corroboration route. It cannot, by itself, bind arbitrary private-function entry arguments and normal returns. Stack-enabled file events could identify call ancestry for an OS operation if that event/provider supports it, but cannot replace the QString and matching-return evidence. Provider schema, privilege, session ownership, loss counters, stack coverage and existing-session coexistence remain unqualified. Do not start/cancel a global WPR session as discovery, or stop someone else's recording. ETW is therefore no-go as the sole CP264 witness and optional only after its own bounded owned-session review.

**Smallest next action:** prepare an offline specification of the four-slot schedule and native API/handle state machine, reviewed against CP264 and CP214 retained events; then implement and qualify it solely on a purpose-built harmless surrogate under a separately authorized change. Verify launch-at-creation, nested arguments/returns, Unicode path decode, exception/timeout/overflow paths, normal exit and abrupt-owner-death cleanup before proposing any original run. If four slots cannot retain the full required predicates, return a concrete schedule conflict rather than launch a reduced witness. No debugger installation is currently necessary to decide that question. Original execution remains no-go until source/native/lifecycle/policy review establishes a supported route.
