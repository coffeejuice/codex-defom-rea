## 2D curve owner and branch order

The mode-1 post-bind chain is native `0x1411f17f0` → `0x1411f1d80` → `0x1411f28f0` → `0x1411f2430` → `0x1411f24a0` → lazy per-curve getter `0x1411f3560` → `0x1412675d0(curve,color)` → `0x14126f300(curve+0x130,color)` → `0x14126a620(curve)`. View+0x28 owns 0x1c0-byte curve items, allocated by `0x1412671d0`. Its secondary color subobject is curve+0x130; the `QColor` receiver curve+0x168 is that subobject+0x38. Setter `0x14126f300` assigns this color and writes secondary+0x4c (curve+0x17c) to 1 before `0x1412675d0` calls the callback. Thus this post-bind callback selects the nonzero QColor branch if the setter returns; branch selection for this specific occurrence is no longer unknown. The constructor initializes that flag to zero.

The earlier initial-bind geometry path is different. The curve secondary vtable points to `0x14126a190`; its render-row builder calls `0x14126a620` before the post-bind setter. That initial occurrence can take the zero-flag palette-slot-12 branch. `0x1411f24a0` chooses two colors before iterating curves: when View+0x20==1 it constructs `(176,0,0,255)` for both; otherwise the first comes from `0x1402d4f90` for object-kind 5 or `0x1402d4df0`, and the second from `0x1402d4e30`. The live selected mode, palette slot 12, chosen QColor values and render-buffer state remain unobserved. The converter's curve item model retains vertices, but the native curve also owns a separate render/color vector at +0x1a8. Do not integrate the isolated post-bind callback as complete public color fidelity.

## Corrected 3D receiver

At `0x14122fb50`, +0x458 applies only to the color-member setter call at `0x14122fb6f`. At `0x14122fb79`, the original rep is reloaded before `0x141237d00(rep,color)` at `0x14122fb7e`. Its flag query reads **rep+0xf9** and returns immediately when nonzero. Otherwise `0x141233dc0(rep,0)` reads the backend at **rep+0x2f0**; null returns. The previous description `rep+0x458+0x2f0` was an offset-composition error and is explicitly corrected in `analysis/resume282-color-3d-backend-method.md`.

Both ordinary geometry and mesh representation constructors call the base initializer `0x141233720`, setting rep+0xf9=1 and rep+0x2f0=null. The binder later writes rep+0xf9 from `0x1411f6210(view)`, which returns 1 unless the View owner exists and owner+0x258 is nonzero. The build dispatcher takes the backend-creating arm only when that flag is zero; `0x141233dc0(rep,1)` then lazily allocates a 0x240-byte backend and `0x141254bb0` installs vptr `0x142d19028`. Allocation failure leaves null; an existing pointer is returned without vptr proof. Only an actual nonnull backend reaches virtual +0x78 and CP282's normalized RGB stores. CP283's +0xf8 no-op applies only to that vptr.

The converter's canonical 3D/null-database test still has a model owner; null database does not prove the native owner-absence predicate. Its current `patchModeOf(m)` returns true based on separate editor-only owner evidence. Bind omits the color path, and adding a guarded no-op callback would change no represented state. Enabling public success from that alone would skip unresolved color-member setter, palette and finalizer effects. Public 3D color remains HOLD.
