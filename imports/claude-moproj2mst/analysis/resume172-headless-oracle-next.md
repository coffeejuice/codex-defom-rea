## Close producer audit

The concrete main vtable `0x1420fb108+0x2d8` points to `0x140010b10` (`evidence/gui_mo/s1/vtables.tsv`). Its direct body calls main virtual+0x778, copies a returned byte+0x210 to global `0x143d77553` if nonnull, calls main virtual+0x2d0, then calls accepted Close root `0x1400299a0` at `010b63`; it normalizes the returned Boolean. This is not an argv command and its precursors cannot be skipped.

An offline exact-byte search for `FF 90 D8 02 00 00` across the original file-backed `.text` returned four pattern sites: `0x140001fdd8`, `0x14007dd55`, `0x14007e299`, `0x140c9ec45`. DUMPBIN shows `1fdd8` is mid-instruction/operand in main's `exec` return bookkeeping, so it is **not a call site**. The `07dd55` and `07e299` sites call a virtual+0x2d8 on a receiver loaded from another object's `+0x18`; they are generic virtual dispatches, not evidence that the fresh primary main receives that call. At `c9ec45`, the receiver is the current `SfMainWindowBase`/derived main. Its containing `0x140c9ec00` is base vtable+0xe8 and takes an event pointer, calls busy `2ca920(show=true)`, then virtual+0x2d8 if unbusy; false invokes imported `QEvent::ignore` (`IAT 0x141e050d8`), true invokes `QEvent::accept` (`IAT 0x141e05638`). This identifies a window close-event decision path, conditional on a delivered QCloseEvent. A GUI close event is outside the current app-control release gate and was not observed. This pattern scan is bounded and does not exhaust all register-materialized/indirect virtual calls.

The other accepted Close entry is main Qt metadata method 20 `slotActionFileCloseAll()` → `0x1400db5ff` → `0x140031f10` → `0x1400299a0`.
