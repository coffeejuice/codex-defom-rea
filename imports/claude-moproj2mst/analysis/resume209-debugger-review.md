# CP209 independent debugger review

**PASS for the two disposable-child fixture paths, with the evidence qualification below. HOLD for adapting this implementation directly to an owned original process.** The source supports the narrow feasibility claim: native x64 register capture, one primary-thread hardware execution breakpoint, and unhandled AV delivery without swallowing either chance. It does not establish observation neutrality or original-process readiness.

This review did not run the fixture, launch an original, acquire GUI control, modify implementation source, or modify external projects. ## ABI and breakpoint assessment

The x64 CONTEXT prefix matches the documented native field order through RIP: homes, flags/MXCSR, segments/EFlags, debug registers, then integer registers. RIP is at byte 248 and the buffer is 1232 bytes. `context()` rounds the backing allocation to 16-byte alignment and retains the allocation while the view is used. Flags `0x100013` request AMD64 control, integer, and debug-register state. Only those sections are requested; the opaque tail is adequate for this use and is not evidence of floating-point or extended-state capture. EVENT has the necessary x64 union alignment and the startup gate checks its 176-byte size, CONTEXT size, and RIP offset. The declared Win32 API pointer/handle types avoid the usual ctypes pointer truncation.

The fixture writes `mov rax, sentinel; ret` to its own allocated page, makes it executable/readable, and flushes the instruction cache. The authenticated debug marker identifies the page; DR0 is set to offset 10, the `ret`, with local execution enable in DR7. No original code is patched. A hit requires single-step exception code, matching RIP, and DR6.B0; the receipt records RAX `0x1122334455667788`, DR6 `0xffff0ff1`, DR7 `0x401`, and one hit in each case. Disabling the breakpoint before continuing avoids re-triggering that execution breakpoint. Kernel-normalized/reserved DR7 bits explain why the receipt need not equal the requested value 1 exactly.

This is primary-thread coverage only. The handler does not explicitly require the matching hit TID or first-chance status, although only that thread is armed in this fixture. It overwrites DR0/DR6/DR7 instead of preserving preexisting debugger state; this is acceptable only for the new disposable self-fixture boundary. A future runner needs explicit ownership and restoration, including a policy for other debug slots and any resume-flag changes.

## Event disposition and natural termination

The event loop and continuations execute synchronously on the creating thread. Non-owned exceptions default to `DBG_EXCEPTION_NOT_HANDLED`, preserving first-chance handler search and second-chance termination. Both AV chances are recorded before that disposition; neither is marked handled. The transcribed AV receipt has matching read address/RCX `0x58`, matching RIP/registers, first then last chance, natural exit `0xc0000005`, and no forced cleanup. The separate native AV thread avoids ctypes' native-call SEH wrapper. Normal exit is 0. Event/continuation counts are equal at 42 and 45 respectively.

The first breakpoint exception is unconditionally treated as the loader breakpoint. It is not qualified by first chance, thread, ntdll module, expected address, or lifecycle state. This is a known restriction of the fixed fixture and a blocker for an original runner. Unknown exceptions are retained in `otherExceptions` and passed through, but do not prevent the fixture pass flag. The AV gate checks chance order and read operands but not equality of RIP, thread, or complete snapshots. The reported records satisfy those stronger properties; the executable pass predicate alone does not prove them. An original parity gate must make the required module/RVA, thread/frame correlation, operands, stack, chance sequence and natural exit explicit.

The main loop has a 15-second/256-event budget. This bounds ordinary event processing, not every possible kernel/API stall or debugger-process failure. No detach or existing-process resume path is present.

## Ownership and cleanup

The sole launch uses the current interpreter and this resolved script, `-I -S`, a fresh token and `DEBUG_ONLY_THIS_PROCESS`. There is no target-path, PID, attach, arbitrary command, or working-directory interface. The internal child mode only runs the fixed fixture. The returned exact process handle is duplicated and checked for image path and creation time; termination uses that handle or its exact CreateProcess predecessor. PID probing is read-only and is never used to select a termination target. This is an effective restriction for accidental target expansion, not a security boundary against a modified interpreter/script or another actor editing files.

Natural-path ownership is coherent: image/DLL file handles are closed, event thread handles are tracked, exit events are continued, and a retained independent process handle is waited to a signaled state. Caller handles are closed separately when distinct from event handles. All known handle values are checked for ERROR_INVALID_HANDLE after cleanup. The transcribed receipt records successful closure and invalid-handle checks in both passing cases. Microsoft documents automatic closure of event process/thread handles on continued exit events; the source does not double-close those known event handles. A signaled exact process handle proves termination of that created instance. A subsequent signaled OpenProcess result does not prove PID disappearance or defeat PID reuse; the report correctly avoids that claim.

Failure cleanup is weaker than the natural paths. TerminateProcess and drain continuations are unchecked; cleanupExitObserved is set even if its continuation failed. Newly delivered CREATE_PROCESS/CREATE_THREAD handles and the create-process image file are not recorded/closed by the drain. A failure before a create event is processed therefore has a less complete ownership receipt. The finally block can also raise on closing the independent PID probe, preventing a structured return. The known-handle set is a set of numeric values across time, without handle generations; reuse can make its interpretation ambiguous. These do not invalidate the two reported natural runs, whose pass gate excludes forced cleanup, but they block a blanket cleanup guarantee or direct original adaptation. Inject failures before/after the create event, marker/context operations, and exit continuation; retain API outcomes and exact owned-process state in a raw receipt.

## Readiness boundary

Before a separately reviewed owned-original runner, require exact binary/hash and version identity, copied disposable fixture identity and environment, module-load/ASLR mapping with byte/instruction validation, qualified loader-breakpoint handling, per-thread breakpoint ownership, bounded reads, invocation/return correlation, and strict exception/stack parity against CP205. Preserve original bytes, both exception chances, and natural fault exit. Establish cleanup for failure paths using exact handles and checked continuations. Persist complete raw receipts with source and input hashes before claiming independently verified runtime behavior.

Hardware breakpoints alter debug state and timing. Successful self-fixtures do not show that the original follows the same path with instrumentation; CP207 remains separately qualified and no converter acceptance or behavioral conclusion follows from CP209 alone. No GUI-control lifecycle was acquired or released by this review. This work produces no deployed executable.

Primary API references checked during review: [native x64 CONTEXT](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-context) for register layout and [ContinueDebugEvent](https://learn.microsoft.com/en-us/windows/win32/api/debugapi/nf-debugapi-continuedebugevent) for exception disposition, creating-thread requirement, and event-handle closure. These API contracts support implementation assessment; they are not original behavioral evidence.
