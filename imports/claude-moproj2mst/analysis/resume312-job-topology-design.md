# WORKER and CHILD job topology: native gate

CP307's WORKER job uses `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` without a breakaway limit. CP303 creates the child with `PROC_THREAD_ATTRIBUTE_JOB_LIST(CHILD)` and no `CREATE_BREAKAWAY_FROM_JOB`. [Microsoft Nested Jobs](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs) says a child normally inherits its parent's job chain and that compatible additional jobs can nest. This leads to an **expected**, not yet measured, topology of WORKER outer and CHILD inner, with the child in both jobs. CP308's fake model currently rejects child membership in WORKER, so it cannot be promoted unchanged to the native path.

The documentation does not explicitly settle the combination of inherited WORKER membership and creation-time CHILD `JOB_LIST` for this exact host. A bounded native test must create an inert suspended child from an owned worker, record `CreateProcessW`/last error and independently query `IsProcessInJob` for both exact job handles before any resume. The test must then terminate jobs, wait on exact worker/child handles and query active counts. No such process was run for this design.

A peer-job topology would use WORKER breakaway permission and `CREATE_BREAKAWAY_FROM_JOB`; that creates an additional escape path and is not selected on static evidence. [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) describes kill-on-close behavior for nested jobs; it does not prove every interruption outcome inside `CreateProcessW`. Keep CP303–311 live entries held until the native topology and independent cleanup are observed. No original or GUI control is required for this disposable experiment.
