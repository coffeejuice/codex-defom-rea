# CP404 failure-only outer-job PID census

CP403 reported WORKER=1 and CP331 inner outer=3 before ACK. The third associated process is not identified by the count, and CP349's distinct top job must not be conflated with CP331's inner outer job. CP332's strict count remains 2; this increment adds only a read-only diagnostic on the failed outer count branch.

The diagnostic uses the retained exact outer-job handle with Win32 `QueryInformationJobObject(JobObjectBasicProcessIdList=3)` and a fixed eight-PID Win64 buffer. It accepts a complete list only when the API succeeds, the returned length is bounded, assigned/listed counts agree with the observed accounting count, and PIDs are nonzero, distinct DWORD values. API faults, races, oversized lists or incomplete results become `ids=unavailable` or `ids=invalid`; they never replace the primary Hold or authorize ACK. The Hold includes the retained runner PID and offered WORKER PID so a later occurrence can compare the list without opening any PID-derived handle. [Microsoft documents the structure and nested-list semantics](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_process_id_list).

`analysis/cp404-outer-census-tests.log` and the final `analysis/cp404-outer-census-final-tests.log` each record 636 passing CP3xx tests from both supported roots. Fake tests cover a complete three-PID list, oversized/incomplete or short-returned lists, API failure, duplicate/zero PIDs, failed strict accounting and no ACK. Independent current-file review found no acceptance weakening and confirmed the Win64 layout; its returned-length qualification led to the final stricter check. Its Git view was unavailable, so root checked the actual diff separately. CP405 next freezes source and requests a one-occurrence gate; only a new occurrence can identify the actual third PID. A missing or incomplete marker remains inconclusive. No native child, original application or GUI ran during CP404 integration. Public C++ converter candidate CP301 is unchanged.
