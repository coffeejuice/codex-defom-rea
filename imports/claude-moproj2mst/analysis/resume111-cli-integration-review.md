# CP111 opt-in isolated Save static integration review

## Review outcome

Process ownership, worker role validation, and the terminal receipt ordering are coherent in the reviewed source. The only concrete integration blocker found is late rejection of a receipt path located inside the selected project tree. `runIsolatedSave` checks receipt equality/equivalence with the selected project and output at `src/cli/isolated_save_supervisor.cpp:131-140`, but does not reject descendants of the project directory there. The only containment check is `src/cli/isolated_save_job.cpp:251-253`, reached from `runIsolatedSave` at `isolated_save_supervisor.cpp:168-172` after the worker has stopped naturally at the terminal boundary. Therefore an invalid nested receipt request can perform Open/Save writes and terminally stop its worker, then fail receipt commit and return CLI code65 without the durable receipt or parent relay. Add the project-tree containment check to prelaunch validation and cover a nested receipt path proving no child and no project changes. The current project-alias test checks only exact alias, not a descendant path (`tests/g0/test_cli_isolated_save.cpp:494-526`).

This is a request-validation ordering defect, not evidence of arbitrary-path deletion or a C ABI change. The commit helper correctly refuses to create the receipt inside the project tree if reached.

This establishes a completed flushed/closed file before relay, not a general power-loss/volume-metadata durability guarantee; the receipt tests are synthetic serialization tests, not hardware-fault evidence.
- The raw acceptance test prepares fresh copies and retains manifests/raw changed-file bytes; terminal case holds the remesh primary lock through the external CLI run and checks status, receipt qualification, unchanged primary/fallback and prefix outputs (`tests/g0/test_cli_isolated_save.cpp:445-492`). The normal case expects no receipt, as the worker receipt states; only terminal outcomes are committed in this first cut.
