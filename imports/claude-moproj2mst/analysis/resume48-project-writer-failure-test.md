# Resume 48 native project writer failure test

Added `save_project_locked_direct_write_uses_qfile_error_after_close_and_continues` to `source/apps/moproj2mst/tests/s/test_save_io.cpp`.

The test obtains a successful disposable control serialization and requires its output to exceed 16 KiB, establishing that the project serialization takes the stream's direct large-write path. It then byte-locks offset zero of a separate valid project using a second handle opened with read/write sharing, and calls full Save. This does not deny native project-file open: open can proceed, and the lock forces the subsequent overlapping `WriteFile` to fail. The test requires the public conversion to return M2M_OK, Boolean BWZ/INI effects and MST to complete, then checks the project target is either its complete prior bytes or empty. The two allowed target states reflect `FileDevice`'s source-qualified behavior: native open's `SetEndOfFile` result is ignored, so the lock may prevent truncation; if truncation succeeds, the later locked write can leave the target empty. It rejects an accidental partial prefix or other content. The successful control confirms the payload is large enough for the injected failure.

The expected success mapping is intentionally subtle: the direct device write records a QFile write error and sticky stream failure, but there is no pending QFile buffer. Close's initial buffer flush succeeds; successful native close clears QFile.error, and `saveProjectFileNative()` queries QFile.error after close rather than QTextStream status. This is qualified by `analysis/wave3-project-close-status-contract.json` and the `FileDevice` receipts/tests. The test also asserts top-level continuation after this project writer result.

No original app/runtime is used. The byte-range lock is a deterministic candidate OS fault for the direct write on Windows; the test has not been built/run by this worker. Root owns integration/build. Only the assigned Save I/O test source and this receipt were changed.
