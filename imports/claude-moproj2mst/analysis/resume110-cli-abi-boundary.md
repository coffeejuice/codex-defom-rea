# CP110 CLI and C ABI boundary for remesh terminal handling

## Existing public contract

The public header `include/moproj2mst.h` declares API version 1 and six C exports: `m2m_api_version`, `m2m_convert_utf8`, `m2m_convert_w`, `m2m_set_codepage`, `m2m_set_deform_dir_w`, and `m2m_set_gui_unit`. The CP107 final ABI audit records those six exports with stable names, ordinals, hints and RVAs versus CP106; it also records all three public ABI tests passing. CP108/CP109 worker receipts explicitly say the product CLI, public C ABI and ordinary conversion route were not changed. No CP110 binary was run or inspected here, so the CP107 table is historical evidence, not a fresh CP110 export measurement.

The existing CLI is a thin `wmain` wrapper over that C ABI. It accepts project and optional output paths plus `--strict`, `--codepage`, `--write-mdt`, `--write-save`, `--deform-dir`, and `--version`; unknown options return `M2M_E_ARG`. It prints the returned message to stderr and returns the integer result code as its process exit. `m2m_convert_w` and UTF-8 equivalent return the `m2m::Result.code`, catching known `m2m::Error` and mapping unknown exceptions to `M2M_E_INPUT`. Existing result values are 0 through 7: OK, ARG, OPEN, PARSE, INPUT, NO_OPERATIONS, WRITE, UNSUPPORTED. The ABI has no structured result for a process-terminal boundary, protocol transcript, or live `SaveCallState`.

The private C++ `ConversionDetails` surface may expose a value `saveCall` snapshot and `returnedCode` after conversion returns; it is not one of the C exports. Its documentation says it must be inspected after return. It therefore cannot deliver a return-side observation from a call that terminates the process before return.

## Worker evidence and representability

CP108/109 implement the remesh terminal route only inside an explicitly opted-in, owned test child role. The supervisor requires its dedicated `RemeshConversion` role, RemeshV2 protocol, own-image identity, nonce, bounded lifetime and worker-case selection. It does not add a product argument or C ABI entry point. The child records a live `SaveCallState`, emits Started then Boundary, and for the terminal candidate endpoint calls `TerminateProcess` on itself with `0xC0000417`. Parent-side supervisor evidence distinguishes this from an ordinary Returned record. CP109 also exercises the candidate’s declared publication-failure and endpoint-return fail-closed paths, but those are worker-only controls, not new public statuses.

The raw four-case CP108 receipts show the key split: normal is Returned/OS0/adapter0; Unknown and Custom are Returned/OS0/adapter7; the denied case is Started+Boundary with no Returned record and OS status `0xC0000417`. The returned_code field in its receipt is merely a default because no adapter return exists. CP108 qualification remains constructed remesh overlay plus retained B133 raw prefix, candidate fixed endpoint, native default-handler prelude unimplemented, no native Close claim. The worker demonstrates candidate-only process-terminal transport and does not establish a fresh original enabled-remesh occurrence.

An ordinary C ABI `int` can represent only a normal returned status. For the denied terminal case, returning any `M2M_E_*` would falsely imply that `m2m_convert_*` returned; killing the caller’s host process to preserve a terminal effect would also violate the library’s ordinary in-process API boundary. A CLI process has an OS exit status, but the existing CLI only returns the adapter result and does not inspect protocol frames. Directly returning `0xC0000417` as a `main` result is not a sufficient implementation contract: the CLI would have no evidence that it was a validated Boundary rather than an arbitrary crash/status, and it could not retain the worker transcript or source-bound snapshot.

## Safe opt-in shapes and compatibility limits

Without changing the existing ABI/default behavior, the narrowest CLI extension is a new explicit option (or equivalent opt-in configuration) that routes only the opted-in run through a dedicated owned child and a parent supervisor. The parent would need to validate the v2 transcript, worker identity/nonce and exact Boundary, then retain/emit a diagnostic receipt. Its CLI can then choose a documented distinct exit mapping for “validated candidate terminal boundary”; it must not call that mapping an ordinary converter return or native-handler reproduction. Existing invocations without the opt-in would continue through the existing C ABI path and preserve current codes/flags.

For a C API consumer needing observability, the additive route should be a separately named/versioned API with an explicit outcome structure or callback that distinguishes `Returned(code)` from `TerminalBoundary(snapshot, status, error, ordinal, proof)` and from worker/supervisor failures. It would have to document that it returns a *supervised candidate observation*, not that the original application returned from a terminal handler. Adding a field or meaning to the existing `int` return, changing API_VERSION 1 semantics, or silently making `m2m_convert_*` spawn/terminate would break the existing contract. Existing six exports and ABI tests must remain unchanged for compatibility; an additive entry point would require a separately reviewed export-table/API-version plan and tests.

Some outcomes cannot be faithfully represented as a normal return at all: actual native invalid-parameter default handling that terminates the process; the candidate worker endpoint’s process termination; and any native Close/destructor effect that occurs only during normal unwinding. The test supervisor can represent these as parent-observed process/protocol outcomes, but that is not an ordinary conversion result. If publication fails before a trustworthy Boundary reaches the parent, the supervisor can report a backend/protocol failure, not claim terminal behavior. An endpoint that returns unexpectedly is likewise a harness failure, not a remesh terminal success.

## Evidence inspected and limits

Inspected `include/moproj2mst.h`, `src/cli/main.cpp`, `src/dll/abi.cpp`, `include/m2m/convert.hpp`, `include/m2m/convert_details.hpp`, CP107 final ABI report, CP108 worker implementation/correction receipts, CP109 worker failure report, and retained CP108 per-case receipts. No source, build, test, original executable, GUI or REA action was performed. Recommendation is an interface-design boundary only; no public route for terminal remesh behavior currently exists.
