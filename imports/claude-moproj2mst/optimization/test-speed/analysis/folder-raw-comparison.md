# Raw serial/pipeline receipt comparison

`admin/compare_folder_raw_receipts.py` compares two completed schema-1 raw folder captures without running the converter or touching fixtures. It follows the schema in the isolated `test_save_folder.cpp` and the qualifications in `folder-pipeline-design.md` and `folder-raw-code-review.md`.

Supply the directories containing `complete.json` and the numbered per-case JSON files:

```powershell
python admin/compare_folder_raw_receipts.py $serialReceiptDirectory $pipelineReceiptDirectory `
  > optimization/test-speed/analysis/folder-raw-equivalence.json
$LASTEXITCODE
```

Exit 0 requires equivalent recorded case semantics and identical generated-file relative names, sizes and SHA-256 values, except the narrowly bound optional capture98 byte qualification below. Exit 1 reports differences. Exit 2 rejects missing, malformed, incomplete or internally inconsistent evidence. Timing alone cannot satisfy this comparison.

Each capture must contain exactly `complete.json` and its ordered, contiguous numbered case receipts. The verifier rejects unfinished/extra/nonregular files, missing or duplicate case names/ordinals, duplicate JSON object keys, unrecognized schemas or fields, invalid hashes and truncated JSON. It verifies every manifest-listed case SHA-256 against its exact file bytes, then cross-checks ordinal, case, mode, expected/work paths and terminal completeness. It computes and reports each completion manifest's own SHA-256. That digest is a receipt identity, not an externally authenticated signature.

Cases must have valid converter-called/status/code relationships and writer identities. Serial cases are coordinator-written; pipeline successful comparisons use one distinct `pipeline-post` writer; copy failures/refusals use `pipeline-coordinator`. Work paths must belong to the manifest coordinator's `m2m_folder_sweep_<PID>/<ordinal>` root. Generated regular-file inventories require sorted unique safe relative paths, nonnegative sizes and lowercase SHA-256. Compared cases' decisions must cover every generated comparator-visible key, using the source's precise PNG/oracleA/view-state exclusions and ASCII lowercasing. Decision stages are restricted to the seven emitted stages, without duplicate keys. Full differ/missing/extra vectors, the pre-older-window differ vector, banner counts and `.moproj`/older-window flags must reconcile; inconsistent or truncated vectors are rejected.

Across runs, ordered case membership, expected roots, full converter codes/messages, states, all complete vectors and decision stages, generated-file inventory and hashes are compared. Executable SHA-256 and filename must agree. Executable location, mode, validated writer roles/PIDs and verified coordinator-owned work roots are explicitly reported as execution provenance. No source, expected-root, relative-file or numeric-result changes are silently normalized.

Only an exact per-case work-root prefix from that case's validated identity, at a path boundary, can be substituted in its full converter message. Both raw message strings and their UTF-8 SHA-256 values remain in `raw_differences`, with `qualified_case_work_prefix_only` stating whether this narrow explanation is complete. Every changed JSON receipt retains both paths and SHA-256 values. Generated-file differences report the full baseline/candidate relative/size/hash entries and remain blockers unless the optional same-run retained-byte qualification proves the sole approved exception. Receipts alone cannot demonstrate that changed bytes reflect only embedded paths or PIDs. There is no numeric masking, banner masking or view normalization in this raw comparator.

The optional paired flags `--baseline-capture98` and `--candidate-capture98` authorize one retained-byte check for `B:98_B_DS3F/Gear_blank.MST`. Each directory must have exactly the producer's generated MST, expected MST and `capture.tsv`. The TSV schema, case, ordinal, coordinator PID/role, expected/work paths and generated relative name must bind to the corresponding raw run. Directory PID identity must agree too. The actual generated bytes' size/SHA must match that same run's generated inventory; an old capture from a different run is rejected. Expected captured bytes and input paths must agree between captures. Only the exact UTF-8 work-root byte prefix at a path boundary is replaced by `<WORK>`; an existing ambiguous token is rejected. Both sides must contain the same positive replacement count, and every remaining byte must agree. No other case/file is eligible. Full raw sizes/SHA values, TSV hashes, capture metadata and normalized SHA values remain in the report.

This report is evidence equivalence within those bounds and cannot establish fresh original-application parity or scientific completion.

## Prefetch normal-case evidence

The comparator recognizes the producer's optional schema-1 `prefetch` Boolean in the completion manifest and every case. If present in the manifest, every case must contain the same exact Boolean; missing, non-Boolean and mismatched values reject the evidence. Legacy schema-1 captures without the field remain readable. A validated flag difference is disclosed as execution provenance. All membership, converter status/message, full vector, decision-stage and generated-file checks still apply.

Those failure paths were not exercised or proven equivalent. The report explicitly records `physical_resource_failure_behavior_established:false`; full-fidelity failure behavior remains unproven and is not accepted by this comparison. Neither a passing producer CTest nor matching normal-case receipts resolves that question.

Read-only Python validation rejected five malformed/missing/mismatched case-flag mutations and retained blockers for changed converter status, file SHA, decision stage and absent byte qualification.
