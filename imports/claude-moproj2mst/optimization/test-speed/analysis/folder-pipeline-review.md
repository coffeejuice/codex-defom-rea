# Serial-conversion folder pipeline review

The proposed pipeline preserves the most important established constraint: every converter call remains on the coordinator's main thread, in the same process and predecessor sequence. It is a reasonable experimental direction, with copy-prefetch-only as the smallest first increment. It is not yet an accepted equivalent replacement. Source review identifies additional lifecycle and output gates beyond matching adjusted diagnostic rows.

This is a read-only review of `analysis/folder-pipeline-design.md`, the isolated `source/apps/moproj2mst/tests/s/test_save_folder.cpp`, relevant converter locking in `src/core/convert.cpp`, and scratch helpers in `tests/support/test_paths.hpp`. No source, fixture, build or test execution was performed. Historical measurements and the B:107 observation in the design are coordinator-supplied evidence; this review did not reproduce them.

## Process and state boundary

`convert.cpp` has a process-local engine mutex at lines 156–157. It serializes entry within one process, not semantic initialization across separate processes. The existing `runShards` assigns each child a subset of conversions, changing predecessor history; retaining the coordinator's full call sequence is therefore necessary. A lock alone cannot repair the rejected sharding experiment.

The proposed process helpers avoid simultaneous comparator allocations in the converter's heap. This is a sensible first implementation boundary, but moving work out of the coordinator removes allocations that previously occurred between calls. Full discovery ahead of conversion also moves path/string/vector allocations and preflight observations before the first call. Keeping call order does not establish unchanged allocator history or eliminate sensitivity to uninitialized data. The design acknowledges this; acceptance must compare generated bytes, not infer safety from serialization.

Do not transplant `folderWorker` as a pipeline helper: its current operation invokes the entire `runCase`, including conversion. A comparison-only helper must have no conversion dispatch route, no engine initialization/reset and no side effects on coordinator locale, CWD, environment or descriptors. Preserve the coordinator's converter environment and exact empty-output/flags/codepage arguments. Helper temp isolation applies only to helpers.

Preflight must preserve the last encountered top-level entry whose extension is exactly `.moproj`, without adding a sort. `runCase` does not require that candidate to be a regular file during selection. The serial work counter is a function-static `seq`; the discovery ordinal is separately reset. For the current one-invocation test these align, but repeated test invocation in one process requires an explicit compatibility decision rather than silently assuming ordinal reset matches serial behavior.

## Scratch lifetime and cleanup

The design correctly identifies the main asynchronous-comparison hazard: baseline compares and attempts to remove case N before calling conversion N+1. Keeping N alive can make a stale engine path readable during a later conversion. An immutable snapshot followed by original-leaf removal is a possible separate experiment, with the original relocation target retained.

Two details need explicit preservation:

- On copy failure, baseline returns without deleting the partially copied leaf. It stays until the final root cleanup attempt. Early cleanup of failed copies is a lifecycle change even though no conversion occurs for that case.
- Baseline passes `error_code` to per-case and root `remove_all` and does not fail if removal fails. A completed cleanup stage means an attempt finished, not that the path disappeared. A pipeline must not declare the lifetime boundary restored solely because it invoked removal. Record removal outcome separately; do not silently change the baseline tally/return decision to a hard failure as part of concurrency work.

Copy-prefetch creates future ordinal paths earlier. Disjoint target leaves prevent direct helper collisions but do not prove the converter confines all path reads to its current leaf. Start with one future leaf and retain a small bound over all copies, active conversion, pending comparisons and failed partial trees. Counting only successful post-processing jobs misses retained partial-copy storage. Validate assigned scratch paths with the existing containment helpers; lexical ordinal naming alone does not inspect reparse-point ancestors.

Reap all owned helpers before root removal, including after malformed IPC, timeout or partial helper output. On infrastructure failure retain enough artifacts to distinguish pending, completed and uncertain jobs. Do not print a complete successful summary from a prefix of validated jobs.

## Converter and comparator output

Baseline case output consists of converter writes followed by comparator/refusal rows, followed by cleanup/profile output and later events. If conversion N+1 begins while comparison N is pending, its direct stdout/stderr writes must not pass the delayed N row. Capture is therefore mandatory for the asynchronous-comparison increment, even with a single converter.

The design calls for per-case captures but should make the combined-stream contract explicit. Separate stdout and stderr strings preserve each stream's own order; they cannot reconstruct arbitrary interleaving in the merged CTest log. Choose an experimentally verified capture/replay scheme for the exact observable being compared. Flush before descriptor changes and after conversion, restore both CRT descriptors and Win32 handles on every exit, and check redirection/restore/read/write failures. A retained native handle or independent runtime buffer can bypass or defer an apparent redirect; a source-level `SetStdHandle` call alone does not prove complete capture. Keep helper diagnostics private. Do not mix profile rows into parity comparisons without an explicit filter.

The existing sharder redirects CRT stdout and Win32 stdout, opens the capture in text mode, and replays bytes in binary mode to avoid translating CRLF twice. Its stderr is worker-wide and causes a successful worker to be rejected if nonempty; that code is evidence of an intentionally incomplete stderr transport, not a complete per-case output solution. The new pipeline must either retain that conservative rejection or validate a stronger framed transport before allowing successful stderr.

## Comparator extraction and thread safety

The comparison helpers primarily own local maps, strings and vectors. `maskView` has a function-local static const regex. That does not establish whole-`runCase` thread safety: it also touches `Tally`, process globals, stdout, optional captures and a static sequence. A separate process executing an extracted pure comparison operation is easier to constrain than running `runCase` concurrently. No comparator thread-safety claim is required for the proposed process-based first experiment.

Extraction must preserve the existing raw-equality-first decision, expected-only path relocation, exclusions and case sensitivity, lowercased relative keys, masks, banner classification, older-window exceptions, map traversal order, and eight-entry diagnostic truncation. Keep `resultRoot` distinct from `relocationTarget` before experimenting with immutable output snapshots.

Historical `readAll` does not check open/read status: unreadable content can become an empty string. Preserve that behavior for faithful comparator extraction. Strict checks for IPC and stdout capture are separate harness requirements; replacing comparator reads with strict transport reads would alter comparison failure semantics. New raw inventories/hashes are validation evidence, not permission to treat unreadable comparator content as a newly defined conversion refusal or skip.

## Acceptance gates

1. Freeze a serial candidate and exact ordered manifest on unchanged fixtures. Record predecessor sequence, selected `.moproj`, ordinal, raw status/message, count deltas, complete vectors, full generated/expected inventories and output bytes. A stable serial baseline must precede comparison with the pipeline.
2. Implement copy-prefetch alone behind an explicit opt-in gate. Keep conversion, comparison, output and cleanup in baseline order. Compare repeated raw output inventories and ordered rows against serial, including B:107 and every refusal/skip; do not select a worker count because one adjusted result happened to match.
3. Exercise synthetic copy failure with partial output, refusal, removal failure, helper launch/crash/timeout, malformed/truncated/misordered IPC, missing output capture and stdout/stderr replay. Verify no duplicate conversion, no skipped successful conversion, no partial-success summary and no cleanup racing a surviving helper.
4. For asynchronous comparison, separately establish original-leaf lifetime and combined output order. Re-run same-path raw parity after moving comparator allocations and before adding copy concurrency or more helpers. If immutable snapshots are needed, verify snapshot completeness and original relocation semantics separately.
5. Only after semantic gates pass, measure repeated paired wall times for the full folder test and then unchanged full-suite membership and launcher fixture passes. Count helper startup, IPC, captures, output replay, cleanup and snapshot cost. Report measured speed separately from the design's optimistic phase models.

The current serial default should remain until these gates establish an equivalent implementation. No standalone folder optimization or ideal dependency-chain model establishes a tenfold full-launcher improvement.
