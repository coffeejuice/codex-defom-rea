## Objective

Evaluate REA/Ghidra plus Codex capability to completely recover and reconstruct an original application, or a precisely bounded part of it, in modern C++. This stage covers the full headless MOPROJ Open-to-Save subsystem of DEF_GUI_MO_64 v11.0.2 and the dependencies needed for that behavior. The full GUI reconstruction remains outside this takeover.

Success requires both internal and external fidelity: recovered function responsibilities and decomposition, class/data ownership and relationships, relevant layouts/interfaces, call and state-transition order, branch decisions, arithmetic, state lifetime, file/process effects, errors and externally observable results. Where original source-level names or structures cannot be established, label the inference and retain the uncertainty. Successful sample outputs alone do not establish architectural recovery or completeness.

The reference is the original binary/application, not Claude's port, its prose or assumptions. Modern C++ is the reconstruction language, not permission to redesign the original. Any deliberate difference must be separated from the faithful baseline and identified explicitly in the research results.

## Fidelity evaluation

Define the selected subsystem's entry points and complete reachable dependency inventory before claiming completeness. Maintain per-function links among original address, static evidence, reconstructed function, state/data contracts and validation. Explicitly account for reused shared functions, external libraries, exclusions and unresolved indirect calls.

Compare the original and reconstruction under equivalent initial state, environment and action sequences. Record process/session history where it affects output. Preserve the original's validation order, write order, partial effects, return values and messages; successful-path byte equality is only one part of the benchmark.

Acceptance cases use one project per fresh reference session. Historical cases affected by previously opened projects remain preserved and explicitly qualified; their outputs cannot serve as fresh-session expectations. Repeated converter calls must each satisfy this isolated-project contract. The mechanism for isolating state remains an implementation question to resolve from evidence.

Use frozen candidate versions and separate exploratory/training cases from held-out evaluation cases. Record all failures, refusals, waivers and unsupported paths, with denominators. Never derive expected behavior from the reconstruction itself or silently tune comparators to accept discrepancies. Internal structure claims require static evidence as well as suitable runtime observations.

The first Save investigation is static, not a runtime fault-injection experiment. Runtime confirmation remains required for representative failure scenarios and externally observed caller behavior.

## Efficiency evaluation

Speed and token efficiency of recovery/reconstruction are separate research outcomes. Seek the fastest method that retains the same scope, fidelity and evidentiary standard.

Record a baseline for each comparable work unit: scope and complexity, starting evidence/cache state, selected method, tool/runtime versions, elapsed wall time, active tool time when observable, retries, artifacts produced, validated functions/cases and unresolved findings. Record model/token metadata only when actually available, separating input, cached input and output. Do not estimate token savings from file/output bytes or attribute elapsed waiting time to model reasoning without evidence.

Compare methods on matched work units or declared strata; distinguish cold acquisition, reused evidence and incremental recovery. Preserve full artifacts on disk while presenting bounded source views. Batch independent reads, reuse source-qualified evidence, and use parallel workers only for distinct scopes with clear ownership. Avoid multiple analysis owners changing the same database.

An efficiency change is successful only if its measured gain does not weaken compatibility, evidence retention, independent evaluation or required tests. Review the method at safe checkpoints; do not interrupt live captures, frozen comparisons or builds to perform an audit. Do not claim a universally fastest method from a single favorable measurement.
